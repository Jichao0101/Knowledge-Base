## 0.1 摘要

只靠静态 contracts 还不够。  
只要高风险路径能在运行期绕过 route、role、review 或 writeback 语义，边界最终还是会失效。

因此需要最小 runtime gate，把“结构上应该禁止”的路径变成“执行时会失败”的请求。

## 0.2 必须门禁化的四类边界

### 0.2.1 reviewer 独立性

- reviewer 必须使用独立阶段或实例
- reviewer 输入只能是最小证据包
- reviewer 不得继承 author / investigator 的全量上下文或推理过程

如果证据不足，review 输出应是：

- `blocked`
- `evidence_gap`

而不是为了推进流程硬给 `pass` 或 `rework_required`。

### 0.2.2 board 取证边界

review 态的板端能力只能用于证据采集：

- 允许：`artifact_collect`
- 禁止：`board_execute`
- 禁止把 reviewer 滑入部署、调参、rerun ownership

同时，board action 必须依附明确的 board-enabled route，而不是只凭角色就可执行。

### 0.2.3 writeback pass 语义

writeback 不应接受模糊单一状态，例如 `review_passed`。  
应改为显式 pass 语义，例如：

- `repo_review_passed`
- `functional_review_passed`

并将 route、scenario、required gate、allowed writeback level 绑定到同一张 matrix。

### 0.2.4 incident 调查边界

incident investigator 可以：

- 读 artifact
- 生成人工假设
- 组织 rerun / probe
- 发起 debug 级 repo change 请求

incident investigator 不可以：

- 直接持有 `repo_write`
- 直接给最终 review 结论
- 直接裁决更高等级 writeback

## 0.3 负向测试优先

门禁收敛时，不应只证明 happy path 可通过，还应至少覆盖以下反例：

- legacy reviewer 仍被引用
- review 态请求 `board_execute`
- incident investigator 请求 `repo_write`
- functional review 伪装为 repo review
- 使用模糊 pass 状态推进 writeback
- incident skill 被当作万能总 skill 调用

如果这些反例不能稳定失败，说明治理边界仍停留在文档层。
