# 1 开源模型结构与执行过程分析

面对一个开源模型，能够调用 `generate()` 之后，常见的问题是某个后端是否生效、batch 在哪里被拆开、某一阶段的输入有多大，以及输出为什么发生变化。回答这些问题，需要把 Python 模型对象、实际函数调用、张量状态和 GPU 工作连接起来。

起点是一个能够加载并执行最小输入的模型。此时先确认processor生成了什么输入、加载对象包含哪些模块，以及公开推理入口怎样进入这些模块。随后在少量边界安装hook，观察调用顺序、张量形状和状态，再把确认过的边界标成trace中的阶段。时间线出现值得解释的现象后，才进一步包装内部接口、检查分支和中间特征。

本文按这条认识过程组织方法。Qwen3.5的视觉attention拆分作为后半部分的深入案例，用来展示已经建立初步执行地图之后，怎样继续缩小观察范围。

## 1.1 从最小推理入口建立问题

面对尚不熟悉的模型，先用一条样本跑通项目的正常入口，保留输入、输出和实际加载配置。沿入口确认预处理、模型调用与输出处理分别在哪里发生。此时要回答的是“输入经过哪些主要模块”“模块接收和返回什么”“一次请求会重复调用哪些部分”，由这些问题决定最初的观测位置。

这一步也适用于图像分类器、检测器或语音模型。生成式模型还要关注循环调用与缓存更新。下表按认识逐步加深的顺序列出可用方法；发现具体疑点后，再选择需要的观察层级。

| 当前问题 | 优先使用的方法 | 得到的证据及下一步 |
|---|---|---|
| 模型由哪些部分组成？ | 配置、模块和参数遍历 | 找到候选模块及真实参数布局，再检查相关forward |
| 哪个分支可能被执行？ | 运行时配置与源码检查 | 列出分支条件，用动态观测核验实际路径 |
| 某模块何时调用、输入如何变化？ | forward pre-hook / forward hook | 得到模块边界与输入输出状态 |
| 张量组织或数值是否异常？ | 元数据、边界值或统计量检查 | 选择需要加深观察的位置 |
| 这些调用启动了什么GPU工作？ | Torch Profiler及关联信息 | 把阶段、算子、形状与kernel联系起来 |
| 一个模块内部调用了几次函数？ | 包装实际调用入口 | 得到接口次数及Q/K/V等参数 |
| 某个kernel为什么慢？ | 定向NCU | 仅在硬件判断会影响工程决策时继续 |

固定样本、模型、精度、生成参数及版本后再比较。优先完成一次短窗口观测，性能对照另行使用无 profiler 的重复测量。

## 1.2 从实际模型对象找到观察位置

先查看已加载对象的模块树，而后阅读目标模块的实现。配置中的层数和隐藏维度帮助理解设计，实例对象则告诉我们当前加载到了什么类、实际参数处于什么设备和精度。

下面的示例假设已经有加载完成的 `model`。先限定遍历深度以控制输出，选中路径后再核对类与源码。

```python
import inspect

modules = dict(model.named_modules())
# 先看根模块及前两级结构，再按需要展开其中一个分支。
for path, module in modules.items():
    if not path or path.count('.') <= 1:
        print(path or '<root>', type(module).__module__, type(module).__name__)

# 以下路径来自Qwen3.5；其他模型应使用上一步发现的实际路径。
vision = modules['model.visual']
print(inspect.getfile(type(vision)))
print(inspect.signature(vision.forward))
print(inspect.getsource(type(vision).forward))
```

`inspect.signature` 用于确定位置参数与关键字参数，`getsource` 展示本环境中安装的实现。查看包装后的函数时还要注意 `__wrapped__` 指向的原函数；C++/CUDA扩展或部分编译对象可能没有可读取的Python源码，此时转向其调用方与接口定义。关键分支可以保存源码快照，连同包版本和模块类名记录，便于解释运行当时的行为。

还应查看项目实际调用的公开入口，例如 `forward()`、`generate()` 或pipeline，沿源码确认它们怎样进入这些子模块。先阅读参数处理和主要调用位置，遇到尚未影响当前理解的算子实现可以暂时跳过。

模块树描述注册关系。共享模块可以被多次调用，单次forward也可以包含循环，因此执行次数仍需动态记录。调用前传入的后端配置应与加载后子模型的实际配置比较。本次仓库读取 vision/text 各自的 `_attn_implementation`，这是配置核验的一环；具体函数和设备路径由后续调用记录确认。

## 1.3 用hook捕获模块边界，用状态识别阶段

沿源码找到主要模块后，先在这些边界上运行一次最小输入，核对真实调用顺序与输入输出。hook通常是最直接的入口。pre-hook在forward前取得参数，forward hook在调用后取得输出。观测型hook返回 `None`，并原样保留参与计算的对象。

下面是一个短窗口教学实现。它只记录直接张量的shape、dtype、device和stride；复杂输出先记录类型，需要时按已知结构提取字段。`model`、输入和模块路径由调用者提供。

```python
from contextlib import contextmanager
import torch


def tensor_meta(value):
    if isinstance(value, torch.Tensor):
        return {
            'shape': list(value.shape),
            'dtype': str(value.dtype),
            'device': str(value.device),
            'stride': list(value.stride()),
        }
    return {'type': type(value).__name__}


@contextmanager
def observe_module(module, events):
    handles = []

    def before(module, args, kwargs):
        events.append({
            'event': 'enter',
            'args': [tensor_meta(value) for value in args],
            'kwargs': {key: tensor_meta(value) for key, value in kwargs.items()},
        })

    def after(module, args, kwargs, output):
        events.append({'event': 'exit', 'output': tensor_meta(output)})

    try:
        handles.append(module.register_forward_pre_hook(before, with_kwargs=True))
        handles.append(module.register_forward_hook(
            after, with_kwargs=True, always_call=True))
        yield
    finally:
        for handle in handles:
            handle.remove()


# 在已经准备好inputs的诊断窗口内运行。
events = []
with observe_module(model.model.visual, events):
    output = model.generate(**inputs, max_new_tokens=32)
```

`@contextmanager` 将安装与清理组织成 `with` 作用域。即使推理抛出异常，`finally` 也会移除已安装的hook。`always_call=True` 让后置hook在forward异常时也有机会执行；输出为 `None` 的退出记录本身不代表调用成功，仍需保留外层异常。上述简例适用于单线程、无重入的观察窗口，多层并发关联需要额外的调用ID与栈。

PyTorch正常的 `module(...)` 调用经过模块hook机制。手动调用 `module.forward(...)` 可能绕过这层入口。编译、融合或其他运行时接管执行后，也应重新核验hook是否覆盖目标工作。

## 1.4 按问题选择需要记录的中间特征

分析张量组织时，先记录shape、dtype、device和stride。这些信息通常足以解释矩阵行数、转置布局和拼接方式，同时避免持有完整中间张量。若要识别分段，就补充 `cu_seqlens` 这类小型结构值；若要定位数值异常，再增加有限值比例、范围、均值或两种实现的输出差异。

prefill/decode识别的关键是cache状态，后文的B8拆分案例还需要观察序列边界。另一项processor检查则用 `image_grid_thw` 和merge大小推算视觉token数，再与输入中实际图像token数量比较。选择记录项应能回答明确问题，不能把保存所有特征作为默认做法。

在训练中保存带计算图的输出引用可能延长计算图生命周期。`detach()` 可以断开梯度关联，但仍可能保留同一块GPU存储。复制到CPU、读取GPU张量标量或计算统计量又可能引入传输、同步与额外kernel。因此数值诊断应使用独立短窗口，并限制样本和记录量。

## 1.5 用已确认的模块边界生成并解读trace

初步hook记录已经说明哪些模块被调用，以及cache等状态怎样变化。现在可以把这些信息接入profiler，观察一次请求的执行时间线。Torch Profiler能自动记录支持的框架算子与CUDA活动；要让时间线出现vision、prefill等业务阶段，则需要用前面建立的模块认识加入语义标记。

具体做法是在目标模块的pre-hook中进入 `record_function` 上下文，在post-hook中退出，并在异常清理时关闭尚未结束的上下文。外层仅在预热后的短窗口启用profiler。模型输入、生成方式与普通推理一致，阶段名称由模块路径及进入时的状态决定。本次代码据此生成 `experiment/vision`、`experiment/language_prefill` 和 `experiment/language_decode` 等区间。NCU工作负载使用同样的阶段判定生成NVTX范围。

第一次带标记的trace用于检查阶段调用与设备成本。例如某阶段占时较高、同名kernel随batch增加，才构成继续深入内部函数的理由。此时可以缩小到相关子模块，通过下一节的接口包装区分外层调用与内部拆分。

这些标记描述CPU侧提交范围。GPU异步执行时，应沿trace关联信息连接框架算子、CUDA API和kernel。本次prefill的一个实际例子如下。

| 记录层 | 名称及字段 |
|---|---|
| 框架算子 | `aten::mm`，External id=22217，输入 `[38248,2560] × [2560,9216]` |
| CUDA API | `cudaLaunchKernel`，External id=22217，correlation=49561 |
| GPU kernel | `ampere_bf16_s16816gemm_bf16_128x64_ldg8_f2f_tn`，correlation=49561，grid=[72,598,1] |

## 1.6 模块边界解释不了内部行为时，包装接口

一次attention模块调用可能在内部执行多次attention函数。普通模块hook只覆盖外层边界，要回答“内部拆了几次”，需要在函数入口记录调用。

包装的核心是保存原callable，记录必要参数，调用原函数并原样返回结果，最后恢复绑定。下面示例包装一个Python模块对象上的函数属性，适用于独立、单线程、未编译的诊断进程。它复用前文的 `tensor_meta`。

```python
from functools import wraps


@contextmanager
def observe_function(owner, name, events):
    original = getattr(owner, name)

    @wraps(original)
    def wrapped(*args, **kwargs):
        event = {
            'call_index': len(events) + 1,
            'args': [tensor_meta(value) for value in args],
            'kwargs': {key: tensor_meta(value) for key, value in kwargs.items()},
            'status': 'entered',
        }
        events.append(event)
        try:
            result = original(*args, **kwargs)
        except Exception as error:
            event['status'] = 'failed'
            event['error_type'] = type(error).__name__
            raise
        event['status'] = 'returned'
        return result

    setattr(owner, name, wrapped)
    try:
        yield
    finally:
        setattr(owner, name, original)
```

这里 `@wraps` 保留原函数的名称、文档及 `__wrapped__` 等信息；调用记录由wrapper函数体完成。这个示例不处理类方法descriptor、后端注册表或跨线程同时修改绑定。遇到这些入口，需要沿源码找到实际读取callable的位置，再采用相应的恢复方式。

包装模块级共享函数会影响使用它的所有调用者。诊断进程应限定作用域，记录所属模块和调用序号，并在退出时恢复原入口。包装回调抛出的异常也会打断推理，因此日志提取应保持简单，先用最小输入验证。
