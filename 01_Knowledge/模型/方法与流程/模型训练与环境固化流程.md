# 1 模型训练与环境固化流程

环境固化要回答的是：一次成功的模型任务，能否由其他人根据保存的材料恢复，并在约定条件下得到可接受的结果。为此需要同时管理软件、代码、模型、数据、配置和宿主机条件，让每次验证结果都能对应到明确的输入。

本文是决策与验收总纲，先确定每一步需要解决的问题。具体拉取、构建、测试、冻结和迁移命令统一放在 [[01_Knowledge/模型/方法与流程/模型容器分阶段构建与迁移实操]]。若需要理解 Dockerfile、镜像、容器与归档的区别，先读 [[01_Knowledge/Docker/Docker镜像基础与构建交付]]。

## 1.1 从任务定义进入流程

先固定模型 revision 和任务：图文推理、LoRA/SFT、批量评估或在线服务。公开权重的运行环境需要正确解释模型结构和执行计算；训练进一步要求反向传播、优化更新和保存恢复链路。不同任务可以使用不同环境，不必寻找模型公司的内部预训练镜像作为起点。

完整流程如下。已有成功环境时，可以从记录其输入与验证范围开始；尚无成功环境时，先形成候选版本组合。

| 阶段 | 核心问题 | 本阶段产物 | 进入下一步的条件 |
|---|---|---|---|
| 明确任务 | 哪个模型、哪条执行路径、在哪里运行？ | 模型与代码身份、硬件、输入规模和验收目标 | 运行范围明确 |
| 形成候选 | 模型实现与硬件支持在哪些版本上相交？ | 候选组合、基础镜像及未决项 | 有支持依据和可执行验证路径 |
| 分阶段验证 | 环境、模型、训练或服务分别是否成立？ | 候选镜像与逐层验证记录 | 本次任务要求的链路通过 |
| 固化输入 | 怎样恢复本次成功环境？ | 构建文件、依赖锁定、代码/数据/配置身份 | 所需输入明确且可获取 |
| 构建交付 | 目标机器收到什么，怎样启动？ | 发布候选、挂载和运行约定 | 新容器中重新验证通过 |
| 独立验收 | 目标硬件和规模是否满足要求？ | 验收结果、适用范围与未覆盖项 | 质量、资源、性能达到约定标准 |

“先验证后固化”约束的是发布质量。可以先在本地 Conda 开发，也可以从一开始就在容器内验证；构建文件应伴随开发维护，使成功变更有明确出处。

## 1.2 用模型与硬件两侧约束选择环境

软件侧从模型卡、官方实现和所选框架的版本说明开始，确认目标任务及后端是否支持，再检查 Python、PyTorch 和扩展库要求。文档中的“安装最新版”可以帮助发现支持路径，正式记录仍要落实到发行版或源码 commit。

硬件侧核对 CPU 架构、GPU 架构、宿主机驱动和容器支持。最终选择两侧约束的交集：同一 PyTorch 版本可能有多种 CUDA 构建，扩展也可能要求额外编译工具。因此单个版本号通常不足以决定整个环境。

```text
模型、任务、实现与扩展要求       GPU、CPU 架构、驱动与平台
             └──────────┬──────────┘
                   兼容约束求交集
                        ↓
              候选版本组合与官方基础镜像
                        ↓
                    运行验证
```

| 选型对象 | 判断依据 | 需要留下的决定 |
|---|---|---|
| 模型实现与任务框架 | 模型卡、版本源码、任务支持说明 | 固定 revision、接口和目标路径 |
| Python、PyTorch 与扩展 | 包依赖、发布信息和编译要求 | 共同支持的版本范围及可选加速项 |
| CUDA 与 GPU | 框架构建、GPU 架构和驱动兼容说明 | 实际二进制或编译路径可用 |
| 基础镜像 | 官方标签、组件清单、平台和摘要 | 保留哪些组件、补充哪些依赖 |
| 宿主机 | 驱动、容器 GPU 支持、采集权限和负载 | 镜像外的运行前提 |

框架镜像适合复用已组合的 Python、PyTorch 和计算库；CUDA 开发镜像适合自行安装框架或编译扩展；Python 镜像适合从框架 wheel 补起。选择最接近需求的起点，可以减少无关安装与版本冲突。

需要分别记录驱动支持的 CUDA 信息、PyTorch 的 CUDA 构建和 CUDA 编译器版本。运行预编译算子与编译扩展的要求不同；若运行时还会即时编译，工具链也属于交付环境。驱动和 NVIDIA Container Toolkit 由宿主机提供，镜像保存用户态依赖。对应查询命令见实操篇第1—2节。

## 1.3 验证从基础算子逐步推进到目标任务

先检查关键版本、GPU 可见性和一个实际 CUDA 运算，再加载固定模型处理真实输入。小模型、低分辨率和短输出可以降低首次验证成本，让接口问题尽早暴露；目标模型和真实输入规模仍需单独验证。

推理通过后，根据任务进入训练或服务验证。训练链路至少覆盖数据读取、前向、反向、优化更新、检查点保存和重载；服务则需要检查并发、延迟、吞吐和输出质量。最终指标与容差由项目约定，首次实验也可用标签、参数更新和保存恢复一致性建立验收证据。

| 验证范围 | 支持的结论 | 后续需要补足的证据 |
|---|---|---|
| 包安装、导入及基础 GPU 运算 | 候选环境与基础计算可用 | 模型真实输入链路 |
| 小模型生成 | processor、权重加载与生成链路成立 | 目标模型、目标输入规模及质量 |
| 最小训练或服务任务 | 对应执行链路成立 | 保存恢复、目标规模和性能 |
| 加速后端与 NCU | 实际后端生效或计数器可采集 | 独立 benchmark、正确性及热点归因 |
| 目标硬件完整验收 | 约定配置满足本次要求 | 未测硬件、模型或规模需另验 |

按依赖组逐步构建，每次通过保留可回退版本。安装新的加速库可能改变执行路径，应同步记录实际后端并重测输出与性能。NCU 的采集时间服务于诊断，端到端性能以无 profiler 的 benchmark 为准。具体阶段命令见实操篇第3—6节。

## 1.4 固化成功输入，并明确交付边界

一次成功运行提供了基线，但恢复它还需要完整输入。基础镜像摘要固定已有内容，项目依赖与传递依赖需要明确版本和来源；源码扩展还要记录构建条件。使用 Conda 时保留其环境声明和适用平台，采用框架镜像默认 Python 时维护项目增量依赖即可。

代码提交、模型 revision、样本或数据身份、配置、随机种子、启动命令、硬件驱动和指标应与镜像记录关联。冻结文件帮助恢复依赖，实际训练结果还受到数据、随机性和算子行为影响；项目需按目标规定对照方式及容差。

交付物由三个部分共同组成：

- **镜像内部**：系统与 Python 依赖、完整项目代码、配置入口、自检入口和版本记录。需要即时编译时保留相应工具。
- **镜像外部输入**：有身份记录的模型权重和数据，离线运行需预先备齐。
- **运行约定**：宿主机要求、GPU 选择、资源设置、挂载路径和持久化输出位置。

将临时修复回写构建输入后，创建新容器复验，再从锁定输入进行干净构建。实操篇第7—8节说明如何记录依赖和迁移镜像；第9节保留 NVIDIA 官方镜像组成及两种训练构建参考。

## 1.5 在目标环境验收后确定发布版本

镜像交付采用仓库或归档都可以，选择取决于网络与团队条件。传递镜像的同时传递构建说明、模型和数据身份、启动方式与验证记录，目标机器才有足够信息执行同一任务。

验收依次确认镜像身份与依赖、挂载和 GPU 访问、模型或训练链路，再比较约定指标。更换 GPU、模型大小、输入规模或后端后，对相关资源和性能结论重新测量；涉及多卡时补通信和分布式执行验证。

若结果偏离基线，按镜像、代码、模型、数据、配置与宿主机条件逐项排查。有效修复进入构建输入，重新验收后发布新版本。这样每个发布版本都对应明确的通过范围，后续使用者也知道哪些条件仍需验证。
