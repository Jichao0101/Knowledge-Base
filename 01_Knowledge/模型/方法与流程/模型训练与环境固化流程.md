# 1 模型训练与环境固化流程

环境固化要解决的是：一次能跑通的训练，能否由其他人依据保存的材料恢复，并在约定条件下得到可接受的结果。因此需要同时记录依赖、代码、数据、配置与运行前提，而不是只留下一个环境文件或镜像。

本文按“验证训练 → 冻结依赖与实验输入 → 确定训练镜像组成 → 构建交付 → 独立验收”展开，把镜像设计直接绑定到固化过程。若尚不熟悉 Dockerfile、镜像和容器，先读 [[01_Knowledge/Docker/Docker镜像基础与构建交付]]；后续训练主线可以在本文连续阅读。

## 1.1 先验证训练链路，再确定交付基线

开发阶段首先确认数据读取与增强、模型前向与反向、损失计算、日志和检查点保存能正常衔接。可以先用小规模数据进行验证，再扩大训练规模，避免把数据或训练逻辑问题误判为环境问题。

如果项目适合本地 Conda 开发，可以先在本地迭代；如果依赖已由团队镜像管理，也可以从一开始就在容器中开发。两条路线都应在保存交付基线前完成约定的训练验证。“先验证后固化”约束的是交付质量，不要求本地 Conda 必须先于 Docker。

创建和维护 Conda 环境的具体操作见 [[01_Knowledge/模型/工具与平台/Conda使用指南]]。试验阶段允许调整版本，但要记录产生有效结果时的环境；正式基线则需同时具备明确的代码与配置版本、数据身份，以及可用于比较的验证结果。指标是否必须达到某个业务目标，由项目的基线验收要求确定。

## 1.2 记录可恢复的依赖与实验输入

训练链路验证后，先回答“恢复环境需要哪些输入”，再选择冻结方式。以下两种导出服务于不同目的，不应把其中任何一种称为训练结果的完全复现保证。

项目采用 Conda 时，在已经激活的训练环境中执行：

```bash
conda env export > environment.yml
conda list --explicit > conda-explicit.txt
```

`environment.yml` 便于阅读和维护环境声明；分享前应检查机器专属路径、平台依赖及 pip 项目是否适合目标环境。`conda-explicit.txt` 记录具体 Conda 包，通常用于同一平台恢复；它不能替代对 pip 安装项、项目代码和外部文件的记录。[Conda 环境管理](https://docs.conda.io/projects/conda/en/stable/user-guide/tasks/manage-environments.html)

项目应选择清晰的依赖维护方式。例如将 pip 依赖维护在 `environment.yml` 的相应部分，或由独立的 `requirements.txt` 管理并明确安装顺序，避免两份文件对同一依赖给出不同要求。冻结文件描述的是依赖输入；能否安装成功仍受平台和软件包可获取性影响。

若使用 NVIDIA 等提供的默认 Python 环境，则记录基础镜像身份与其中的包版本，并单独维护经过验证的项目增量依赖；不要求为此重新创建 Conda 环境。第 1.3、1.4 节以这一方式说明真实基础镜像如何变成项目镜像。

依赖之外，还需为这次基线记录代码提交、训练配置、数据版本或清单、随机种子、启动命令、关键硬件与驱动信息，以及用于对照的日志和指标。只有知道“哪次实验使用了哪些输入”，后续差异才有解释依据。

## 1.3 确定完整训练镜像的组成与交付边界

依赖记录完成后，需要决定交付什么。“框架环境能用”与“项目能够开始训练”是两个不同阶段：通用训练基础镜像提供框架及计算库，项目训练镜像还要固定完整代码、配置入口和启动方式。完整性的判断是：提供约定的宿主机条件、数据、权重和参数后，能够直接启动任务，而无需现场补装依赖或寻找缺失代码。

### 1.3.1 真实基础镜像：NVIDIA PyTorch 24.10

以 `nvcr.io/nvidia/pytorch:24.10-py3` 为具体对象。这个镜像引用出现在 [NVIDIA 官方使用文档](https://docs.nvidia.com/nurec/archives/26.03/fixer/model.html)中，组件版本依据 [PyTorch 24.10 发布说明](https://docs.nvidia.com/deeplearning/frameworks/pytorch-release-notes/rel-24-10.html)。选择固定旧版本是为了说明组成，不是推荐将它用于所有新项目；以下是官方文档事实，本轮没有拉取或运行该镜像。

| 层次 | 该版本实际提供的内容 | 对训练的意义 | 如何核对 |
|---|---|---|---|
| 用户空间与解释器 | Ubuntu 22.04、Python 3.10 | 提供系统库和 Python 执行环境 | `/etc/os-release`、`python --version` |
| 训练框架 | PyTorch `2.5.0a0+e000cf0ad9` | 提供张量、自动求导与训练框架能力；版本含 NVIDIA 所用构建标识 | `torch.__version__` |
| GPU 计算库 | CUDA 12.6.2、cuDNN 9.5.0.50 | 为框架提供 GPU 计算与深度学习算子支持 | `nvcc --version`、`torch.version.cuda`、`torch.backends.cudnn.version()`，再执行算子 |
| 多 GPU 通信库 | NCCL 2.22.3 | 为使用 NCCL 的分布式训练提供通信组件 | `torch.cuda.nccl.version()`；实际多卡通信另测 |
| 训练观察工具 | TensorBoard 2.16.2 | 用于查看训练写出的事件日志 | `python -m pip show tensorboard` |
| 框架源码与安装结果 | 框架源码位于 `/opt/pytorch`，已安装到默认 Python 环境 | 无需为了使用 PyTorch 再从源码构建；源码是框架本身，不是用户项目 | `torch.__file__`、查看 `/opt/pytorch` |

因此，“完整训练镜像需要 Python 与框架”在这个实例中就落实为具体解释器、构建版本和可检查的安装位置。该容器采用默认 Python 环境，不应假定存在 `train` Conda 环境，也不应直接套用另一项目导出的完整依赖文件去覆盖它。

开始使用前还要检查发布说明中的硬件与驱动要求。24.10 起官方不再测试 Volta；不能把这个表格当作 V100 的已验证兼容方案。宿主机驱动及 NVIDIA 容器运行支持属于运行前提，不由上表中的用户空间库替代。真实部署应结合 [该版本发布说明](https://docs.nvidia.com/deeplearning/frameworks/pytorch-release-notes/rel-24-10.html)和 [NVIDIA Container Toolkit 安装说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)核对。

在满足这些前提的机器上，可执行以下检查。命令用于产生实际证据，下面没有预填“成功输出”；`torch.version.cuda` 表示框架编译所用 CUDA，通常不提供完整补丁号；cuDNN 查询可能返回数字编码。应结合工具链信息与对应 API 判读，而不是要求所有输出与表格字符串逐字相等。

```bash
docker pull nvcr.io/nvidia/pytorch:24.10-py3
docker image inspect nvcr.io/nvidia/pytorch:24.10-py3

docker run --rm --gpus all -i nvcr.io/nvidia/pytorch:24.10-py3 python - <<'PY'
import sys
import torch
print('Python:', sys.version)
print('PyTorch:', torch.__version__)
print('Torch path:', torch.__file__)
print('CUDA build:', torch.version.cuda)
print('cuDNN:', torch.backends.cudnn.version())
print('CUDA available:', torch.cuda.is_available())
assert torch.cuda.is_available(), 'GPU is not available'
print('GPU:', torch.cuda.get_device_name(0))
print('NCCL:', torch.cuda.nccl.version())
x = torch.randn(8, 8, device='cuda', requires_grad=True)
(x @ x).sum().backward()
torch.cuda.synchronize()
print('CUDA forward/backward smoke check passed')
PY
```

上述检查证明的范围限于版本、设备可见性及一个 GPU 前向/反向计算。它没有验证项目数据链路、优化器更新、检查点保存或多机通信。

### 1.3.2 从官方框架环境补齐项目训练镜像

NVIDIA 镜像已经解决上表中的公共环境问题，但无法替项目决定训练哪种模型、如何读标注、采用什么损失和配置。因此，下表继续用具体文件说明还缺什么。这些路径是本文的项目组织示意，不是 NVIDIA 镜像内已存在的文件。

| 项目补充项 | 示例中的具体内容 | 与环境固化的关系 | 验收方式 |
|---|---|---|---|
| 项目额外依赖 | `requirements-project.txt`，只列在所选基础镜像上验证过的增量依赖 | 保留基础框架组合，明确项目增加了什么 | 安装后核对关键版本、执行 `pip check` 与项目导入检查 |
| 数据与模型代码 | `src/data.py`、`src/model.py`、`src/loss.py`，以及实际需要的其他模块 | 固定预处理、网络和训练语义 | 项目入口能导入所有模块，小批量数据能完成训练步骤 |
| 训练入口 | `tools/train.py`，包含训练调度、优化更新、评估及检查点读写 | 固定“怎样开始并完成一次训练”的执行路径 | 在新容器中按约定命令运行 |
| 默认配置 | `configs/train.yaml`，描述模型、数据参数、超参数和路径约定 | 把环境与本次实验配置区分开，并保留覆盖关系 | 日志记录最终生效配置 |
| 版本与依赖证据 | 代码提交标识、镜像 ID/摘要、`env/` 下的依赖记录 | 将实验结果关联到明确输入 | 将启动日志与交付记录对照 |
| 项目自检入口 | `tools/smoke_train.py` 或训练入口的短任务模式 | 给接收者提供可重复的最小验收方法 | 完成前向、反向、参数更新和检查点保存 |

Conda 是管理 Python 环境的一种方式，不是镜像完整性的必要标志。对于这个 NGC 实例，优先围绕它已有的 Python 与框架组合验证增量依赖；若项目决定改用另一个环境，则要把框架与计算库的组合重新作为待验证输入。

编译工具也取决于实际执行路径。扩展已在构建阶段编译完成时，运行时通常保留产物和运行依赖即可；启动时还会即时编译 C++/CUDA 扩展，则需对应编译工具链。`import torch` 成功不能覆盖这项验证。[PyTorch 扩展说明](https://docs.pytorch.org/docs/stable/cpp_extension.html)

### 1.3.3 明确镜像之外的训练输入与输出

镜像负责固定程序及环境，每次训练的输入、输出和机器条件需要配套说明：

| 配套项 | 示例位置 | 固化与交付要求 |
|---|---|---|
| 数据集与标注 | `/data`，来自宿主机挂载或外部存储 | 记录数据版本、目录结构与读取方式 |
| 预训练权重及配套文件 | `/models` 或明确的受控缓存 | 固定版本或校验值；需要时一并准备分词器、词表、模型配置 |
| 实验参数 | 镜像中的 `configs/train.yaml`，可由外部实验配置覆盖 | 说明优先级，保存最终生效参数 |
| 检查点、日志与评估结果 | `/outputs`，连接持久化存储 | 确认写权限及容器删除后的保留方式 |
| 宿主机与资源 | GPU、驱动、容器运行支持及任务所需资源 | 按镜像版本与实际训练规模验证 |

离线训练应提前备齐运行所需文件，避免启动时隐式下载。输出不能只依赖容器可写层；持久化存储是运行约定的一部分。[Docker 数据持久化说明](https://docs.docker.com/get-started/docker-concepts/running-containers/persisting-container-data/)

至此，交付目标明确为：**固定的项目训练镜像 + 有身份记录的数据和权重 + 明确的启动、资源与输出约定**。下一步才把这些决定写入构建文件。

## 1.4 将训练环境构建为项目镜像

### 1.4.1 沿用 NVIDIA 默认 Python 环境的构建路径

下面是基于真实 NGC 镜像的项目派生示意，项目文件与参数接口需由实际工程提供；它不是 NVIDIA 官方完整训练项目，也没有在本轮执行构建。示例约定 `tools/train.py` 接受 `--config`，配置使用 `/data`、`/models` 和 `/outputs`，项目以 `src` 包组织代码。

```text
project/
├── docker/Dockerfile
├── requirements-project.txt
├── env/
│   └── base-constraints.txt
├── src/
│   ├── __init__.py
│   ├── data.py
│   ├── model.py
│   └── loss.py
├── tools/
│   ├── train.py
│   └── smoke_train.py
├── configs/train.yaml
└── README.md
```

先在所选基础环境中导出包版本作记录，审查后形成 `env/base-constraints.txt`，再安装已经验证的项目增量依赖，可以及早暴露“项目要求的版本与基础镜像冲突”。遇到冲突应调整依赖方案或基础镜像，不把绕过约束当作验证完成；版本约束也不能替代运行验收。不要将含 editable 安装或不可访问本地路径的 `pip freeze` 输出直接当作可用约束文件。

```dockerfile
FROM nvcr.io/nvidia/pytorch:24.10-py3
WORKDIR /opt/train/app

RUN python -m pip freeze > /opt/base-installed-packages.txt
COPY env/base-constraints.txt /tmp/base-constraints.txt
COPY requirements-project.txt /tmp/requirements-project.txt
RUN python -m pip install --no-cache-dir \
        -c /tmp/base-constraints.txt -r /tmp/requirements-project.txt && \
    python -m pip check

COPY src/ ./src/
COPY tools/ ./tools/
COPY configs/ ./configs/
COPY env/ ./env/
ENV PYTHONPATH=/opt/train/app
RUN python -m pip freeze > /opt/train/app/env/resolved-packages.txt
CMD ["python", "tools/train.py", "--config", "configs/train.yaml"]
```

依赖文件在这里负责声明增量要求，Dockerfile 负责安装并复制完整项目代码。发布时记录实际基础镜像摘要、派生镜像身份和代码版本；固定标签只是便于阅读，不替代这些记录。若基础镜像带有入口脚本，还需核对它与上述 `CMD` 的组合。

从项目根目录构建：

```bash
docker build -f docker/Dockerfile -t project-train:ngc24.10-v1 .
docker image inspect project-train:ngc24.10-v1
```

README 应说明三个外部目录、GPU 与资源条件、启动命令和配置覆盖方式。运行时挂载 `/data`、`/models`、`/outputs`，保留镜像中的 `/opt/train/app`，避免挂载整个代码目录后遮住已经固化的版本。镜像保存与加载操作见 [[01_Knowledge/Docker/Docker镜像基础与构建交付#1.3 镜像交付与重建依据]]。

### 1.4.2 项目确实采用 Conda 时的另一条路径

如果经过验证的项目环境由 `environment.yml` 描述，并已选择有可用 Conda 的基础镜像，可以用下面的构建片段恢复环境。它是另一种环境方案，不应直接追加到上面的 NGC 示例中。

```dockerfile
WORKDIR /opt/train/app
COPY env/environment.yml /opt/train/env/environment.yml
RUN conda env create -n train -f /opt/train/env/environment.yml
COPY src/ ./src/
COPY tools/ ./tools/
COPY configs/ ./configs/
ENV PYTHONPATH=/opt/train/app
CMD ["conda", "run", "--no-capture-output", "-n", "train", "python", "tools/train.py", "--config", "configs/train.yaml"]
```

该片段仍以项目完整代码和明确配置为输入。使用 `conda run` 指定环境，避免依赖交互式 shell 初始化。[Conda 命令说明](https://docs.conda.io/projects/conda/en/stable/commands/run.html)

## 1.5 在独立环境验收，而不是只检查镜像存在

交付前，应在新的容器或约定的目标环境中执行验证，减少对开发容器残留状态的依赖。按下面的顺序推进，后一阶段以前一阶段通过为前提：

| 阶段 | 要验证的问题 | 应保留的证据 |
|---|---|---|
| 环境恢复 | 依赖能否安装或镜像能否加载，关键包能否导入 | 镜像身份、依赖与版本检查结果 |
| 运行连通 | 数据、权重与输出目录是否可用，GPU 是否可访问 | 实际路径、设备检查与启动日志 |
| 最小训练 | 小规模前向、反向、优化更新和检查点保存是否完成 | 命令、日志及检查点 |
| 结果对照 | 约定数据和配置下的指标是否落在可接受范围 | 基线指标、当前指标、容差与差异说明 |

环境恢复成功说明运行前提得到部分验证；最小训练成功才说明训练链路能执行；结果对照通过才支持本次实验的复现判断。若项目要求更强的确定性，还需控制相关随机性与算子行为，并明确硬件和框架边界。

发现差异时，先按镜像身份、依赖、代码、数据、配置和宿主机条件逐项对照。修复应进入相应构建说明或依赖记录，再重新验收；不要只在一个容器里临时修好便把旧镜像作为交付基线。
