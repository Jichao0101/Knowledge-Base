# 1 基于 SDK 基础镜像构建开发镜像

本篇解决一个具体问题：供应商已经交付 SDK 环境，如何在其基础上增加日常开发工具，并让团队可以重复构建和使用。这里的产物是用于开发与调试的衍生镜像，验收重点是 SDK 工具链仍能工作。

## 1.1 明确基础镜像与衍生镜像的职责

SDK 基础镜像提供供应商定义的工具链和环境；衍生开发镜像保留这个起点，再增加项目需要的编辑、版本管理、构建和调试工具。扩展前应先确认 SDK 版本、宿主机架构和供应商约束，避免安装额外依赖时破坏已有工具链。

```text
SDK 基础镜像 ── Dockerfile.dev 添加开发工具 ──> 衍生开发镜像
                                                  │
                                           挂载代码并运行
                                                  ↓
                                              开发容器
```

若还不熟悉 Dockerfile、镜像与容器的区别，先读 [[01_Knowledge/Docker/Docker镜像基础与构建交付]]。模型训练环境的组成、依赖冻结和训练验收则在 [[01_Knowledge/模型/方法与流程/模型训练与环境固化流程]] 中独立说明。

## 1.2 基于地平线 SDK 构建开发镜像

假设项目已有适用的地平线 SDK 基础镜像，希望增加 git、vim、gdb 等工具。下面保留原笔记的 `horizon/sdk:1.0` 作为占位名称，实际执行前须替换成项目可访问的镜像及版本。示例假设基础镜像使用 Debian/Ubuntu 系包管理、具有 Bash，且允许安装所列软件；不据此判断所有地平线 SDK 都缺少这些工具。

将下面内容保存为项目中的 `Dockerfile.dev`：

```dockerfile
# 占位镜像名：替换为项目实际使用的 SDK 镜像。
FROM horizon/sdk:1.0

USER root
RUN apt-get update && \
    DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends \
        git vim less tree cmake ninja-build gdb strace \
        net-tools iproute2 htop openssh-client ca-certificates python3-pip \
    && rm -rf /var/lib/apt/lists/*

# 假设基础镜像中尚无 dev 用户。
RUN useradd -ms /bin/bash dev && \
    mkdir -p /workspace && chown dev:dev /workspace
USER dev
WORKDIR /workspace
CMD ["/bin/bash"]
```

这里先以 root 安装系统工具，再切换为普通开发用户。若基础镜像已有合适的用户，应复用并调整配置；挂载宿主机目录时还要核对 UID/GID 和写权限。Python 的 numpy、pytest、ipython 等按项目需要写入依赖文件，并在兼容 SDK 的 Python 环境中安装，不默认向 SDK 自带环境追加未固定版本的包。

在 `Dockerfile.dev` 所在目录执行：

```bash
docker build -f Dockerfile.dev -t my-horizon-dev:1.0 .
docker image inspect my-horizon-dev:1.0
```

`-f` 指定构建说明，`-t` 为产物命名，最后的 `.` 指定当前目录为构建上下文。检查镜像配置时，应确认工作目录是 `/workspace`、默认用户是 `dev`，并查看继承的 `Entrypoint` 与默认 `Cmd`。构建成功只说明安装步骤完成，仍需验证 SDK 工具能否工作。

## 1.3 启动、验证与复用开发容器

开发时希望宿主机修改代码后，容器能直接看到，因此把项目目录挂载到 `/workspace`。先将下面的宿主机路径替换为实际已存在的项目目录，再运行：

```bash
docker run -it \
    --name horizon-dev \
    --mount type=bind,src=/path/to/your/project,dst=/workspace \
    my-horizon-dev:1.0
```

`-it` 提供交互终端，`--name` 便于后续找到容器，挂载目标与 `WORKDIR` 保持一致。此命令使用镜像默认命令；若继承的 SDK 入口脚本有额外要求，应按供应商说明配置。

进入容器后，先检查位置与工具，再执行项目自己的最小构建或 SDK 验证任务：

```bash
pwd
id
git --version
cmake --version
gdb --version
```

预期 `pwd` 为 `/workspace`，用户符合预期，各工具能返回版本。随后确认项目文件可见且写权限满足开发需要；这些基础检查不能替代交叉编译或板端运行验证。上面的预期值是验收方法，不是本笔记已经取得的运行结果。

退出交互式 Bash 后，容器通常停止。恢复同一个容器可执行：

```bash
docker start -ai horizon-dev
```

如果容器已经运行，需要再开一个终端，则执行 `docker exec -it horizon-dev /bin/bash`。再次执行 `docker run` 会创建新容器，不是恢复旧容器。

安装在容器可写层中的工具不会自动写回原镜像。试验确认后，应把需要保留的环境变更补入 Dockerfile 或依赖文件并重新构建。挂载的代码存放在宿主机，不能把它当作已经包含在镜像中的交付内容。

不再需要容器时，可先 `docker stop horizon-dev`，再 `docker rm horizon-dev`；删除前保存可写层中需要保留的文件。镜像不再被使用后，可用 `docker image rm my-horizon-dev:1.0` 清理。

## 1.4 开发镜像与目标运行环境的边界

开发环境服务于编译、调试和迭代，运行环境服务于执行交付程序。两者依赖不同，因此不应从开发镜像较大就推导出交付镜像必须包含同样内容。

| 内容 | 开发镜像 | 运行镜像 |
|---|---|---|
| 编译器、构建工具、完整 SDK | 按开发任务配置 | 通常不需要完整集合 |
| 调试工具 | 按调试需要配置 | 按交付与诊断要求配置 |
| 程序及运行库 | 用于开发验证 | 保留程序运行所需内容 |
| 主要验收目标 | 能否完成开发、构建和调试 | 能否在目标运行环境执行程序 |

若项目使用容器交付，可以通过多阶段构建从构建阶段复制所需产物，并配置相应运行库；这不是“把开发镜像直接变成板端运行环境”。交叉编译宿主机与板端的架构、ABI、驱动和部署方式仍需分别核对，板端是否使用容器由项目决定。[Docker 构建最佳实践](https://docs.docker.com/build/building/best-practices/)

## 1.5 交付与维护

开发验证通过后，记录 SDK 基础镜像身份、Dockerfile.dev 与依赖版本，再交付开发镜像。保存、加载和重建依据的通用操作见 [[01_Knowledge/Docker/Docker镜像基础与构建交付#1.3 镜像交付与重建依据]]；接收者应重新执行本文第 1.3 节及项目 SDK 验证。示例 apt 包未全部锁定，不承诺每次构建得到完全相同产物。
