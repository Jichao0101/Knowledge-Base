# 1 Nsight Systems与CPU-GPU协同分析

## 1.1 从算子耗时转向执行关系

知道某个算子提交了哪些kernel以后，仍可能解释不了GPU为什么空闲。后续工作可能还没有被CPU提交，也可能已经提交却在等待前序工作、数据传输或其他stream。只看算子累计时间，无法区分这些情况。

Nsight Systems的价值在于把主机线程、CUDA提交和设备活动放在同一条时间轴上，让分析从“谁用了多少时间”转向“谁在等谁”。torch.profiler也能观察CPU/GPU和部分执行关系；当已有报告不能解释线程调度或跨组件时序时，再补充系统采集。

## 1.2 分析思路：从GPU空隙向前追溯

先在目标迭代或请求中找到待解释的空隙，再检查空隙之后的工作是什么时候提交的。

如果提交发生得晚，就沿CPU线程向前看：主机是否仍在准备输入，是否被调度出去，或者正阻塞在某个调用中？如果提交早已完成，就沿设备侧依赖看：同stream前序工作、跨stream事件或资源条件是否推迟了执行？这两条路径指向不同的优化对象。

因此，API返回到kernel开始的间隔不能全部叫launch开销；GPU活动连续也不表示计算管线饱和。时间线用于解释执行关系，kernel内部效率仍需其他证据。

确定要追查的关系后，再配置采集。仅需要提交与执行关系时可以先采CUDA活动；要解释CPU为何没有推进，还需要相应的线程状态或调用栈信息。

## 1.3 采集操作：为目标关系选择轨道

### 1.3.1 用标记确定业务范围

NVTX让应用在时间线上标记阶段、迭代或请求身份。标记不是同步屏障，CPU范围结束后，它提交的GPU工作仍可能继续。阅读时应沿关联关系归属，不能直接按CPU范围截断GPU事件。

应用必须实际发出NVTX标记；torch的record_function不因名称相同就自动成为NVTX。先控制为稳定且足够短的窗口，再采集所需活动。长进程应使用工具支持的capture-range等机制，不宜把初始化和全部训练都放入一次诊断。

### 1.3.2 最小命令与扩展条件

下面是Bash下的CUDA/NVTX采集示例，workload.py为待替换路径，假设应用已控制为短运行：

```bash
nsys --version
nsys profile --help
nsys profile --trace=cuda,nvtx --sample=none -o timeline python workload.py
```

这里关闭了CPU采样。若需要定位CPU调用栈或线程调度，应按目标操作系统、权限及工具版本增加相应采集器。缺少某条轨道只说明当前没有这类证据，不说明该活动没有发生。[用户指南](https://docs.nvidia.com/nsight-systems/UserGuide/)

## 1.4 阅读时间线：把诊断分支落实到证据

报告中先定位业务窗口，再看GPU活动及对应API，随后检查提交线程、拷贝和其他stream。不要先从全部进程的汇总百分比推断某个请求的原因。

| 轨道或标记 | 阅读时的问题 |
|---|---|
| 业务范围 | 当前是哪次迭代、哪个阶段或请求？ |
| kernel与memory活动 | 目标工作何时执行，哪里有空隙或重叠？ |
| CUDA API | 对应工作何时提交，是否存在同步调用？ |
| CPU采样与线程状态 | 提交线程当时在计算、等待，还是没有运行？ |

沿这条顺序得到的线索，可以继续组织为以下诊断分支：

| 现象 | 下一项证据 | 可尝试的受控验证 |
|---|---|---|
| 后续kernel直到空隙末尾才提交 | 主机预处理、线程调度、同步调用 | 固定输入并单独改变主机准备路径 |
| API早已提交，GPU晚执行 | 前序工作、stream事件、跨stream依赖 | 检查依赖链，而非先删同步 |
| 很多短kernel与间隙交替 | 调用频率、CPU提交节奏、工作规模 | 比较融合或图执行方案，同时核对输出 |
| 拷贝与计算未重叠 | 内存类型、stream与数据依赖 | 在正确性允许时改变传输安排并复测 |
| 某rank持续等待 | 各rank工作量、到达通信的时间 | 先检查负载不均，再判断通信硬件 |

上表是待验证的解释，不是看到某种图形就能得出的根因。例如，多个短kernel之间有间隙，既要看提交节奏，也要看依赖；不能直接把融合当作必然有效的方案。[分析指南](https://docs.nvidia.com/nsight-systems/AnalysisGuide/index.html)

## 1.5 验证解释，再决定是否下钻

选择一个受控修改后，先检查预测的时间关系是否变化，再检查真实任务是否变快。若主机准备确实是原因，减轻对应工作后应能看到提交更早或相关空隙缩短；只看到吞吐变化还不足以确认唯一解释。

系统报告已经定位到某个热点内部问题时，再把阶段、工作量与实例身份交给[[01_Knowledge/性能分析/Nsight Compute基础与性能分析]]。最终比较仍遵循[[01_Knowledge/性能分析/性能测量与瓶颈验证]]，不把profiler内的时间直接当作正常运行基线。

## 1.6 补充：工具所说的“库支持”如何理解

库支持描述观测能力，不保证完整暴露实现。CUDA API与kernel关联连接提交和执行；cuBLAS、cuDNN等库追踪用于观察受支持API；TensorRT等还可通过自身NVTX标记提供阶段语义。OpenACC追踪面向相应运行时活动。

库API、NVTX语义和底层kernel是不同层次，需要分别检查版本、选项与插桩。看到库名不等于能读到库内部源码，也不等于已经取得硬件瓶颈结论。这个区别影响采集配置，但不改变前面沿时间关系排查的主线。
