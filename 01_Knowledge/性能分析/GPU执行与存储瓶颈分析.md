# 1 GPU执行与存储瓶颈分析

时间线能定位慢的工作，硬件报告则提供解释这些工作的线索。要把指标读成原因，需要依次区分三个问题：是否提供了足够的并行工作，已经驻留的工作是否能继续执行，以及执行过程中哪一类资源形成限制。本文沿这条因果关系展开，采集命令与报告操作另见Nsight Compute篇。

## 1.1 先检查工作是否足够，再检查单元是否高效

首先区分“总共有多少工作”和“同时能执行多少工作”。CUDA将工作组织成多个block，再由设备安排到SM上；工作总量足够大，不代表这些工作能够同时驻留，单个block里线程很多，也不保证覆盖所有SM。

在报告中，grid描述总工作规模，block描述协作线程。总block数除以SM数反映平均分配的工作量，不是同时驻留block数。驻留容量还受到寄存器、共享内存、线程/warp和block上限约束，并受资源分配粒度影响。

因此，并行不足可能来自两处：总工作太少，或资源限制了同时驻留的工作。小grid和执行末尾的尾波属于前一类；每block资源需求很高则可能属于后一类。需要区分后再选择干预。

先确认热点、shape和启动资源，再考虑改善并行组织。不要为提高occupancy盲目减少寄存器：spill与重计算可能抵消驻留收益。这里讨论的上限均依具体架构，不使用固定warp槽数代表所有GPU。

## 1.2 驻留、就绪和发射是三个问题

即使SM中驻留了很多warp，它们也不一定能立即推进。例如，一条后续指令需要先前访存的结果，在结果返回之前，相关warp仍占用驻留资源，却不能发射这条指令。其他就绪warp能否接替，决定等待是否被隐藏。

报告中的active/resident表示warp已驻留，eligible表示下一条指令具备发射条件，issued表示调度器实际发射。三者对应“有位置”“能执行”“被选中执行”，不是同一个利用率。高occupancy只说明驻留多，不保证就绪多。

官方V100数值示例见[[01_Knowledge/性能分析/Nsight Compute基础与性能分析#1.5 官网报告案例：驻留充分，为什么仍发射不足]]。不将该报告的warp上限复制成架构常数。

先看发射是否不足，再用stall信息解释不足。高stall比例未必主导总耗时：其他warp可能已经隐藏了等待，或当前工作本来很短。对stall采样、active/elapsed周期和聚合范围分别核对。[Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)

## 1.3 存储瓶颈不只等于DRAM带宽

当发射不足与访存有关时，还要区分容量、流量和请求组织。容量回答工作集能否放下；流量与执行时间共同描述带宽；指令和请求数量则影响访问管线及队列压力。一个工作集很小的kernel，也可能因为访问组织不佳而产生大量请求，所以“显存占用不高”并不能排除存储侧问题。

下面把常见现象映射到下一项证据。它的用途是缩小解释范围，而不是按一行指标直接给kernel贴标签。

| 线索 | 需要补看的证据 | 可能的解释，不是结论 |
|---|---|---|
| DRAM接近相应上限 | 实际字节、耗时、访问模式 | 外存流量可能限制性能 |
| DRAM不高，L2或其他层忙 | 层级吞吐、命中和请求 | 局部层级而非DRAM受限 |
| 实际事务显著多于理想事务 | 线程地址布局、sector/request口径 | 合并访问不足或额外流量 |
| shared访问代价高 | bank conflict、指令和吞吐 | 冲突、访问次数或管线压力 |
| 延迟高但吞吐不高 | eligible、依赖和并行规模 | 不足以隐藏等待，未必带宽饱和 |

Long Scoreboard指向相关访存结果依赖，不自动证明DRAM拥塞；LG Throttle指向local/global指令队列压力，仍需结合访问模式；其他stall名称也必须按当前架构定义解读。看见某个名称不能直接指定优化手段。

对数据布局、融合、tile、共享内存复用等修改，先预测应改变哪些流量或指令，再看绝对耗时。减少请求不保证端到端变快，额外同步或资源压力可能成为新的限制因素。

## 1.4 用Roofline判断上限，用其他指标解释差距

读完吞吐和调度指标后，Roofline提供一个定量参照：这份工作在当前计算路径和存储流量下，理论上能有多快？定义同一范围的计算量为FLOPs、某一级存储流量为Bytes、执行时间为T：

```text
算术强度 I = FLOPs / Bytes      （FLOP/byte）
实际性能 P = FLOPs / T          （FLOP/s）
简化上界 = min(计算峰值, 带宽 × I)
```

横轴是每搬运一字节做多少计算，纵轴是每秒完成多少计算。带宽形成斜线，所选计算路径形成水平上限。若一个点离屋顶很远，位置在交点哪一侧都不足以确定真实瓶颈，还要回到访存、并行规模、指令与依赖证据。[Roofline说明](https://developer.nvidia.com/blog/accelerating-hpc-applications-with-nsight-compute-roofline-analysis/)

例如另一个纯教学算例：100 GFLOP、20 GB实际DRAM流量、10ms执行时间，得到I=5 FLOP/byte、P=10 TFLOP/s。假设相应计算上限100 TFLOP/s、DRAM带宽2 TB/s，则简化屋顶为10 TFLOP/s；接近这一屋顶才支持带宽限制。如果只达到2 TFLOP/s，还需解释差距。

这里的“相应”十分重要。BF16 Tensor Core和普通FP32路径不能混用上限；DRAM、L2、L1的Bytes必须分别计量，输入tensor大小不等于实际DRAM流量。框架按shape估算的FLOPs也不一定等于硬件实际工作量，padding等可能增加执行量。Roofline不能回答后端是否支持batch，或为什么按图拆分调用，那仍需检查实现路径。[官方性能排查](https://docs.nvidia.com/nsight-compute/ComputeTriage/index.html)

## 1.5 什么时候下钻源码和SASS

只有确认热点影响任务、采集可信且高层指标不足以解释主要限制因素时，才进一步看源码关联和指令。源码行信息和可读实现是前提；闭源库通常不能像自定义CUDA代码一样任意修改。

应能说清“需要区分哪两个假设、预期哪个指令/事务证据可以区分”，再下钻；不是把全部SASS读完才算理解。实际应用中换布局或后端也可能是合理干预，但这与证明某条指令是唯一原因不同。官方排查强调一次聚焦一个主要限制因素，优化后重新分析。[Compute Triage Guide](https://docs.nvidia.com/nsight-compute/ComputeTriage/index.html)
