# 1 性能分析总览

性能分析的目标不是完成一次工具采集，而是解释真实任务的主要限制因素，选择干预，并验证收益。按“任务 → 框架执行 → 系统协同 → kernel内部 → 任务复测”组织知识；根据缺失证据选择工具，不要求每次按固定顺序使用全部工具。

Torch Profiler与Nsight Compute的核心差异是观测层级：Torch Profiler关联模型算子与CPU/GPU执行，Nsight Compute解释选定CUDA kernel内部的执行限制；这不是精度高低的排序。前者帮助判断哪些工作值得分析，后者帮助区分计算、各级存储与调度方面的原因。NCU既能解释资源为何利用不足，也能支持某种资源已接近吞吐上限的判断。

| 工具 | 主要观测对象 | 从记录走向判断的步骤 |
|---|---|---|
| Torch Profiler | 阶段、框架算子、输入shape、CPU/API与GPU活动 | 事件关联 → 同类工作分组 → 次数与耗时归一化 → 阶段贡献与扩展趋势 |
| Nsight Systems | 主机线程、CUDA提交、传输、stream及其时序 | 等待区间 → 提交与依赖追溯 → 重复性与关键路径 → 系统限制因素 |
| Nsight Compute | 选定kernel的计算、存储、驻留与发射指标 | 对象核验 → 多指标约束竞争解释 → 源码或访问证据 → 局部机制与验证预测 |

Torch Profiler也能观察CPU/GPU协作；需要进一步解释线程调度与跨组件等待时再使用Systems。三种工具的覆盖有交集，选择依据是缺少哪层证据。最后都要回到独立benchmark，检查局部解释是否转化为任务收益。

工具篇既负责采集与字段解释，也负责从原始记录推导到各自观测范围内的判断；机制篇进一步解释硬件关系，测量篇统一比较合同和结论强度。模型篇串联应用，不重复维护三套工具教程。模型生命周期知识仍从[[01_Knowledge/模型/模型知识总览]]进入。

第一次阅读先建立测量口径，再从框架篇理解一份工作如何落到GPU。遇到执行等待，进入Systems篇；遇到kernel内部效率问题，进入Compute篇并结合机制篇。工具篇的采集参数集中放在操作章节，可以在理解分析思路后按需查阅。

## 1.2 学习深度与停止条件

第一层是共同基础：异步时间、CPU/GPU关联、容量与带宽区别、计数器口径和独立benchmark。第二层是工程重点：对真实热点建立可证伪假设，做一次受控修改，检查预测与任务收益。第三层是按问题下钻到源码、SASS和架构细节，不作为启动微调或部署的统一前置条件。

完成一个可信诊断闭环后即可将方法迁移到backward、optimizer或服务请求链路；不要求先读完所有指标。没有改变决策价值的继续下钻应暂停，转向下一个主要限制因素。训练和部署共享诊断能力，但有不同任务合同和验证指标。
