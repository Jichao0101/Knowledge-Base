# 1 主代理越权执行规范硬化优化记录

## 1.1 结论

原草案方向正确，应继续推进。

需要优化的不是制度目标，而是执行颗粒度。当前草案已经覆盖：

- 角色权限表
- 阶段状态机
- 违规处理机制

但距离“运行时可阻断、可审计、低灰区”仍有以下缺口：

- 动作定义不够原子
- 状态机过重
- `conditional allow` 过多
- 检测信号未分层
- `writeback` 风险分层不足

本轮建议采用“更小、更硬”的落地策略：

1. 只对高风险动作做默认 deny。
2. 状态机压缩为四个核心门禁状态。
3. `writeback` 拆成三层。
4. 检测信号拆成机械可检与语义审计。
5. `conditional allow` 必须列举条件，未逐项记录时按 deny。

## 1.2 1.1A 术语对齐

本记录引入的“核心门禁状态”和“高风险动作”不替代既有正式规范术语，只作为运行时硬门禁 overlay。

新增术语必须映射到现有闭环骨架后才能写入正式规范，避免形成两套并行语义。

| 新增硬门禁术语                  | 对应既有正式规范语义                                                      | 说明                                           |
| ------------------------ | --------------------------------------------------------------- | -------------------------------------------- |
| `analysis`               | `context_retrieved -> plan_ready` 之间的分析与计划形成阶段                  | 只用于阻断高风险动作，不替代 `plan_ready`                  |
| `implementation`         | `execution_approved -> implementation_done`                     | 只允许 `repo-coder` 执行 `repo_write`             |
| `review`                 | `implementation_done -> repo_review_done`                       | 对应 repo-reviewer 独立审查，不等同于 knowledge-auditor |
| `writeback`              | `knowledge_sync_checked -> convergence_ready -> writeback_done` | 包含项目区记录、current 更新和知识提升的分层写回                 |
| `project_log_write`      | modification record / run_log / audit_log / 项目区草案记录             | 不改变 current，不作为默认恢复入口                        |
| `project_current_update` | current 文档更新、决策基线更新、`single_pass_recoverable` 入口更新              | 对应 existing current 体系，必须进入 writeback gate   |
| `knowledge_promotion`    | `promotion_review` 后写入 `01_Knowledge` 或标记 `verified`            | 对应正式知识区转正，不等同于普通项目记录                         |
| `review_decision`        | `repo_review_result`                                            | 仅指 repo 侧质量裁决；知识转正审查由 `knowledge-auditor` 承担 |
| `S0-S3`                  | 违规恢复链路中的审计严重度                                                   | 不替代原状态机，只决定 freeze scope 和 recovery owner    |

## 1.4 A. 角色权限表优化

### 1.4.1 当前风险

现有权限表覆盖动作较多，但部分动作边界不清：

- “修改正式知识区”与“正式知识提升”重叠。
- “writeback 准备”与“writeback 执行”边界不清。
- “运行验证”没有区分只读验证与会生成或覆盖产物的验证。
- “质量裁决”和“review 结论产出”重复。
- `conditional allow` 太多，容易重新软化硬门禁。

### 1.4.2 优化原则

权限表不应覆盖所有低风险动作，应优先覆盖高风险动作。

新增默认规则：

```text
高风险动作默认 deny。
未在权限表中显式 allow 的高风险动作，不得执行。
```

高风险动作最小集合：

- `repo_write`
- `verification_write`
- `review_decision`
- `project_current_update`
- `knowledge_promotion`
- `rollback_or_discard`

### 1.4.3 动作定义修订稿

```markdown
#### 高风险动作定义

- `repo_write`：修改代码、脚本、配置、构建文件、测试文件或会进入仓库的工程文件。
- `verification_write`：运行会改变仓库内容、项目 current、正式知识、持久化工程产物、模型产物、基线报告或可被后续任务默认消费的状态文件的写入型验证命令。
- `verification_read`：运行不修改仓库、不更新 current / 正式知识、不覆盖持久化产物，或仅在临时目录生成一次性检查输出的验证命令。
- `review_decision`：对实现产物给出 `pass / rework_required / blocked` 的质量裁决。
- `project_log_write`：写入项目区临时记录、运行记录、分析草案、review 记录或审计记录。
- `project_current_update`：更新项目 current、决策记录、状态基线或会影响后续任务入口的项目文档。
- `knowledge_promotion`：新增或更新正式知识区条目，或将条目标记为 `verified`。
- `rollback_or_discard`：回滚、废弃、降级或标记已有产物为 invalid。
```

### 1.4.4 最小高风险权限表修订稿

| 高风险动作 | workflow-orchestrator | repo-coder | reviewer | knowledge-closer / auditor |
|---|---|---|---|---|
| `repo_write` | deny | allow | deny | deny |
| `verification_write` | deny | allow | deny | deny |
| `verification_read` | allow | allow | allow | allow |
| `review_decision` | deny | deny | allow | conditional allow，仅限知识 promotion 审核 |
| `project_log_write` | allow | allow，仅限实现记录 | allow，仅限 review 记录 | allow |
| `project_current_update` | conditional allow | deny | deny | conditional allow |
| `knowledge_promotion` | deny | deny | deny | allow，且必须通过 promotion gate |
| `rollback_or_discard` | conditional allow，仅限调度和标记 | conditional allow，仅限被授权返工 | conditional allow，仅限提出建议 | conditional allow，仅限知识条目降级 |

### 1.4.5 conditional allow 收紧规则

```markdown
#### conditional allow 约束

`conditional allow` 不得解释为“角色可自行判断是否执行”。

只有当权限表下方列出的全部条件满足，并且 audit_log 已逐项记录 `gate_result`，才允许执行。

若条件未被逐项记录，按 deny 处理。
```

### 1.4.6 建议删除、合并与保留

建议删除：

- 删除“修改正式知识区”独立动作，统一合并为 `knowledge_promotion`。

建议合并：

- 合并“质量裁决”和“review 结论产出”为 `review_decision`。

建议保留：

- 保留 `workflow-orchestrator` 不得 `repo_write`。
- 保留 reviewer 不得修改被审对象。
- 保留未审内容不得进入正式知识区。

## 1.5 B. 阶段状态机优化

### 1.5.1 当前风险

原状态机把所有状态都作为强约束，容易造成小任务执行形式化。

风险表现：

- `intake / context_collect / dispatch / closed` 被过度门禁化。
- 小型 read_only 或 spec_update 任务需要填过多状态字段。
- 状态机从“阻断高风险动作”退化为“流程表演”。

### 1.5.2 优化原则

状态机应拆成两层：

- 核心门禁状态：用于阻断高风险动作。
- 管理辅助状态：用于 run_log，不作为每次动作前的硬阻断。

### 1.5.3 核心门禁状态修订稿

```markdown
#### 核心门禁状态

核心门禁状态只保留四个：

1. `analysis`
2. `implementation`
3. `review`
4. `writeback`

只有高风险动作需要检查核心门禁状态。
```

### 1.5.4 管理辅助状态修订稿

```markdown
#### 管理辅助状态

以下状态用于 run_log 与任务可恢复性，不作为每次工具调用的硬阻断条件：

- `intake`
- `context_collect`
- `dispatch`
- `closed`

小型 read_only 或 spec_update 任务可以合并记录管理辅助状态，但不得跳过核心门禁状态。
```

### 1.5.5 核心状态门禁表修订稿

| 核心状态 | 允许的高风险动作 | 必须阻断的动作 | 进入条件 |
|---|---|---|---|
| `analysis` | `project_log_write`，仅限草案或审计记录 | `repo_write`, `verification_write`, `project_current_update`, `knowledge_promotion`, `review_decision` | 已确认 allowed_paths，已读取必要上下文 |
| `implementation` | `repo_write`, `verification_write`, `project_log_write` | `review_decision`, `knowledge_promotion` | 已形成 implementation package，执行者为 `repo-coder` |
| `review` | `review_decision`, `verification_read`, `project_log_write` | `repo_write`, `verification_write`, `knowledge_promotion` | 已存在 artifact，reviewer 独立 |
| `writeback` | `project_log_write`, `project_current_update`, `knowledge_promotion` | `repo_write`, 未授权 `verification_write` | review gate 或 spec_update gate 通过 |

### 1.5.6 最小禁止跃迁修订稿

```markdown
#### 必须阻断的最小跃迁

以下跃迁必须阻断：

1. `analysis -> implementation`，且执行者为 `workflow-orchestrator`
2. `analysis -> writeback`，且无 review gate 或 spec_update gate
3. `implementation -> writeback`，且无 `review_decision = pass`
4. `review -> writeback`，且 `review_decision != pass`
5. 任意状态 -> `knowledge_promotion`，且 promotion gate 未通过
```

## 1.6 C. 违规处理优化

### 1.6.1 当前风险

原违规处理覆盖范围充分，但缺少分级：

- 没有 severity，轻微审计缺失和正式知识污染被同等处理。
- 没有 freeze scope，容易默认冻结全部任务。
- 没有 recovery owner，恢复责任不清。
- 检测信号未区分机械可检与语义审计。

### 1.6.2 violation severity 修订稿

```markdown
#### 违规等级

- `S0_observation`：轻微记录缺失或审计字段不完整，未产生错误产物。
- `S1_gate_miss`：gate 记录缺失或状态记录不完整，但未发生高风险写入。
- `S2_invalid_artifact`：产生了越权 artifact，但尚未进入 writeback 或正式知识区。
- `S3_invalid_writeback`：未审或越权内容已进入项目 current、正式知识区或影响后续任务入口。
```

### 1.6.3 freeze scope 修订稿

```markdown
#### 冻结范围

- `freeze_none`：仅补审计记录。
- `freeze_action`：冻结同类动作，例如继续 `repo_write`。
- `freeze_artifact`：冻结受影响 artifact，不得作为 review / writeback 输入。
- `freeze_writeback`：冻结所有 writeback。
- `freeze_promotion`：冻结正式知识提升，但允许项目区 draft 记录。
- `freeze_task`：冻结本轮任务，必须重新调度。
```

### 1.6.4 recovery owner 修订稿

| 违规类型 | recovery owner |
|---|---|
| orchestrator 越权 `repo_write` | independent reviewer + workflow-orchestrator |
| reviewer 不独立 | workflow-orchestrator + new reviewer |
| 未审内容进入 writeback | knowledge-closer + reviewer |
| 正式知识条目缺元数据 | knowledge-auditor |

### 1.6.5 检测信号分层修订稿

```markdown
#### 检测信号分层

违规检测信号分为两类：

1. 机械可检信号：可由路径、角色、状态、文件写入、frontmatter、audit_log 字段直接判断。机械可检信号命中时，应立即阻断或冻结对应动作。
2. 语义审计信号：需要 reviewer 或 knowledge-auditor 判断。语义审计信号命中时，应进入 `pending_review`，不得直接标记 `verified`。

若机械可检信号与语义审计信号冲突，以机械可检信号先冻结，再由语义审计决定恢复路径。
```

### 1.6.6 重点违规处理修订稿

#### 1.6.6.1 orchestrator 越权 repo_write

```markdown
违规定义：
当前角色为 `workflow-orchestrator` 时执行 `repo_write` 或 `verification_write`，且未通过显式角色切换、未进入 `implementation` 核心状态。

机械可检信号：
- `current_role = workflow-orchestrator`
- 发生 repo 文件写入
- `current_core_state != implementation`
- 无 `repo-coder` artifact

语义审计信号：
- 写入是否可作为有效实现保留
- 是否存在合理 emergency override

默认等级：
- 未 writeback：`S2_invalid_artifact`
- 已 writeback：`S3_invalid_writeback`

立即动作：
- `freeze_artifact`
- `freeze_writeback`
- 标记 `invalid_execution`
- 停止继续 `repo_write`

恢复责任人：
- independent reviewer 判断 artifact 是否可保留
- workflow-orchestrator 重新调度
```

#### 1.6.6.2 reviewer 不独立

```markdown
违规定义：
reviewer 参与实现、修改被审 artifact，或由 implementer 自行给出 `review_decision`。

机械可检信号：
- reviewer 与 implementer 为同一角色实例
- reviewer 写入被审文件
- review_result 作者与 implementation artifact 作者一致

语义审计信号：
- review 是否缺少独立判断
- review 是否只复述实现说明
- review 输入是否未经裁剪导致偏置

默认等级：
- `S1_gate_miss`
- 若已进入 writeback，则升级为 `S3_invalid_writeback`

立即动作：
- 标记 `invalid_review`
- `freeze_writeback`
- 要求 new reviewer
```

#### 1.6.6.3 未审内容进入 writeback

```markdown
违规定义：
未通过 review gate 或 spec_update gate 的内容被写入项目 current、正式知识区，或被表述为已确认结论。

机械可检信号：
- 无 `review_decision = pass`
- 无 `spec_update_gate = pass`
- 已写入 project current 或 `01_Knowledge`
- `status = verified` 但缺 evidence / source / review record

语义审计信号：
- 内容是否事实上仍可保留为 draft
- 内容是否影响后续任务入口
- 是否需降级为项目日志

默认等级：
- 项目日志误写：`S1_gate_miss`
- 项目 current 误写：`S3_invalid_writeback`
- 正式知识误写：`S3_invalid_writeback`

立即动作：
- `freeze_promotion`
- 受影响条目降级为 `draft` 或 `pending_review`
- 记录 `invalid_writeback`
```

#### 1.6.6.4 未完整标注内容进入正式知识区

```markdown
违规定义：
写入 `01_Knowledge` 的条目缺少标题、摘要、来源、适用范围、不适用范围或风险、状态，或 status 与证据等级不匹配。

机械可检信号：
- frontmatter 缺字段
- `status = verified` 但无 sources
- target_path 位于 `01_Knowledge`
- 无 promotion gate

语义审计信号：
- 是否具备复用价值
- 是否属于项目特例
- 适用边界是否足够清晰

默认等级：
- `S3_invalid_writeback`

立即动作：
- `freeze_promotion`
- 降级为 `pending_review`
- 必要时移动到 `02_Projects`、`03_Inbox` 或 `04_Sources`
```

## 1.7 writeback 分层修订

### 1.7.1 当前问题

`writeback` 仍是模糊总称，混合了三类风险不同的动作：

- 写一条项目运行日志
- 更新项目 current / 决策状态
- 把条目提升为正式知识

这三者必须拆分。

### 1.7.2 writeback 三层定义

| writeback 层级 | 风险等级 | 最低 gate | 允许状态 | 独立 review |
|---|---|---|---|---|
| `project_log_write` | 低 / 中 | allowed_paths + `draft / pending_review` | `analysis / implementation / review / writeback` | 默认不需要 |
| `project_current_update` | 中 / 高 | review pass 或 spec_update gate | `writeback` | 默认需要 |
| `knowledge_promotion` | 高 | promotion_review + knowledge-auditor pass | `writeback` | 必须需要 |

### 1.7.3 project_log_write

```markdown
`project_log_write` 可用于记录过程、草案、审计与未决问题。

该层写回不得改变项目 current，不得作为正式决策入口，不得标记为 `verified`。
```

### 1.7.4 project_current_update

```markdown
`project_current_update` 会改变后续任务入口，默认需要 review gate。

未通过 review 的内容只能写入 project_log，不得写入 current。
```

### 1.7.5 knowledge_promotion

```markdown
`knowledge_promotion` 是最高风险 writeback。

任何未完成 promotion gate 的内容，即使已在项目中验证，也只能保留在 `02_Projects` 或 `03_Inbox`，不得进入 `01_Knowledge` 的 verified 条目。
```

## 1.8 最小优先落地项

### 1.8.1 默认 deny

修改项：

- 增加“高风险动作默认 deny”。

解决的问题：

- 防止未列动作被默认解释为允许。

优先级原因：

- 收益最高，落地成本最低。

### 1.8.2 writeback 分层

修改项：

- 将 writeback 拆为 `project_log_write / project_current_update / knowledge_promotion`。

解决的问题：

- 防止项目日志、current 和正式知识提升混用同一个 gate。

优先级原因：

- 直接降低知识污染和 current 污染风险。

### 1.8.3 四核心状态门禁

修改项：

- 将硬状态压缩为 `analysis / implementation / review / writeback`。

优先级原因：

- 保留关键阻断能力，同时减少小任务成本。

### 1.8.4 检测信号分层

修改项：

- 拆分机械可检信号与语义审计信号。

解决的问题：

- 明确哪些信号可直接冻结，哪些需要 reviewer 判断。

优先级原因：

- 提升可阻断性和审计一致性。

### 1.8.5 限制 conditional allow

修改项：

- `conditional allow` 必须逐项记录条件，缺失则按 deny。

解决的问题：

- 防止 conditional allow 被泛化为软许可。

优先级原因：

- 直接修复原草案最大的软化风险。
