### 1.4.2 步骤1：确定输入规模

#### 1.4.2.1 理论与预期

单张静态图像先按patch划分，再在空间上合并：

```text
N_patch ≈ (H / p) × (W / p)
N_visual ≈ N_patch / m² = H × W / (p² × m²)
```

H、W是processor处理后的图像高和宽，p是patch边长，m是每个空间方向的合并数。真实token数由processor输出的grid及合并规则确定。

本地配置p=16、m=2，相当于每个合并后的视觉token覆盖约32×32像素。不同尺寸的估算结果如下：

| 处理后尺寸（宽×高） |   视觉token近似值 |
| ---------- | -----------: |
| 1024×768   |          768 |
| 1536×1152  |         1728 |
| 1920×1200  |         2250 |
| 2592×1944  | 约4921，仍需尺寸对齐 |

上下文还需容纳文本、特殊token和生成内容，因此4096上下文不能直接覆盖所有原图。原始整图可整体缩放，但不裁剪；像素预算还需保留眼部可判别性。

```text
输入长度 = 视觉token + 文本及模板token
所需context预算 ≥ 输入长度 + 预留生成token
```

#### 1.4.2.2 测量重点

本步关注原图与处理后尺寸、grid、视觉token和总输入长度，以验证理论估算。CPU上的processor处理即可得到这些量，无需加载模型权重。初始配置沿用本地默认整图缩放、关闭thinking；单样本结果只反映该样本，不能代表全数据的容量需求。

**本步只调用processor，不调用模型前向计算。** 文本token ID、图像patch数据和模型embedding是不同阶段的产物：

| 分支 | processor阶段完成的工作 | 尚未执行的模型计算 |
|---|---|---|
| 文本 | tokenizer将文本及特殊标记转换为整数token ID，形成input_ids | 按ID查找模型的可训练embedding矩阵，生成文本向量 |
| 图像 | image processor完成缩放、归一化、patch展开，产生pixel_values和grid；多模态processor据grid及合并规则确定视觉token数量，并展开输入中的图像占位token | patch embedding、视觉编码器及空间合并/投影，生成供语言模型使用的视觉向量 |

image processor不把图像编码成离散视觉码，也没有生成视觉embedding；pixel_values仍是展开的预处理像素数据。预处理阶段可按grid确定合并后的token数量，无需实际执行模型中的空间合并。

因此，本次4536个视觉token表示将占用的视觉序列位置数，4732表示包含这些占位位置的输入ID序列长度；两者都不表示embedding已经生成。图像占位token ID不承载图像内容，图像内容由pixel_values在后续模型前向计算中编码。仅加载模型权重也不会完成上述计算，需要到单图推理步骤才执行。

#### 1.4.2.3 结果与决定

以下为新检测prompt的processor测量结果。视觉token保持4536，文本及模板token为196，总输入4732。processor阶段暂预留128；2026-09-21运行采用256，见1.4.4.3。

| 观察项 | 理论预期 | 当前实测与决定 |
|---|---|---|
| 处理后尺寸与视觉token | 由patch、合并和缩放共同决定 | 原图宽高1808×2592，处理后1792×2592；grid=[1,162,112]，视觉token=4536 |
| 总输入长度 | 视觉token＋文本及模板token | 4732，其中非视觉输入196 |
| Context预算 | 输入长度＋生成预留 | 预留128时需要4860；5600预算可容纳，剩余740 |

上表128为历史processor预算。本次运行输入4732、上限256，合计预算4988，在5600内余612；实际生成95 tokens但格式不合约，不能据此认定完整合约输出或全数据预算已验证。

### 1.4.3 步骤2：加载模型并建立显存基线

#### 1.4.3.1 理论与预期

BF16为主、少量FP32的非量化checkpoint，权重header统计结果如下：

| dtype | tensor数 | 元素数 | tensor字节数 |
|---|---:|---:|---:|
| BF16 | 727 | 9,653,100,528 | 19,306,201,056 |
| FP32 | 48 | 3,840 | 15,360 |
| 合计 | 775 | 9,653,104,368 | 19,306,216,416，约17.9803GiB |

按名称分组约语言/其他16.68GiB、视觉0.85GiB、MTP0.45GiB；不是GPU常驻分配实测。框架是否加载MTP、dtype转换和权重重排仍需实测。

#### 1.4.3.2 测量重点

加载常驻量与加载过程峰值应分别观察，前者用于建立推理前的显存基线，后者包含临时加载开销。有效比较需对应相同设备和实际dtype，并区分allocated、reserved与设备总占用。

#### 1.4.3.3 结果与决定

以下为此前仅加载、尚未forward阶段的结果；后续推理结果见1.4.4.3：

| 指标 | 加载前 | 加载后 |
|---|---:|---:|
| allocated（GiB） | 0 | 17.5272193 |
| reserved（GiB） | 0 | 17.5410156 |
| peak allocated（GiB） | 0 | 17.5272293 |
| peak reserved（GiB） | 0 | 17.5410156 |
| 设备总占用（GiB） | 0.3341675 | 17.9279175 |
| 设备空闲（GiB） | 70.7895508 | 53.1958008 |

allocated与参数字节数仅相差80,928 bytes；reserved比allocated多约14.13MiB；加载allocated峰值比结束值仅高10.5KiB，本次没有出现明显的额外GPU加载峰值。设备总占用比reserved高约396.19MiB，属于不同统计口径的差额，不能仅凭该JSON逐项归因。

checkpoint存储量与实际参数字节数相差486,588,928 bytes，恰好等于本地MTP分组486,581,248 bytes加3,840个FP32元素转BF16节省的7,680 bytes。数值支持“MTP分组未进入本次参数集合、少量FP32参数按BF16加载”的解释，但完整加载日志/参数名仍待核对，不能只靠总量认定逐项加载行为。

模型加载可行性已确认，保留BF16配置并进入步骤3。此时没有模型前向产生的activation或KV缓存，未创建优化器状态。

### 1.4.4 步骤3：跑通单图推理并测量开销

#### 1.4.4.1 理论与预期

```text
推理运行时占用 ≈ 实际加载权重 + 视觉/prefill中间结果
               + full-attention KV与线性attention状态
               + logits/workspace + runtime
```

prefill是处理整个输入序列的阶段；KV及线性attention状态用于后续生成；workspace是算子临时工作空间。峰值取决于这些对象的同时驻留情况，不能直接累加各项各自的最大值。

传统KV缓存按层数、序列长度及每个KV头的大小计算：

```text
M_KV = L_full × 2 × B × S × n_kv × d_head × b_kv
```

L_full是full-attention层数；系数2代表K和V；B是batch size；S是已缓存序列长度；n_kv是KV头数；d_head是每头维度；b_kv是每个缓存元素的字节数。

本模型32层中有8层full attention、24层linear attention。采用BF16缓存（每元素2 bytes），B=1、S=4096、n_kv=4、d_head=256时，传统KV缓存约为**128 MiB**。

该值仅覆盖full-attention的传统KV，不含线性attention状态、视觉计算开销或推理引擎预分配缓存池。

logits的通用大小公式及完整序列示例见步骤4。推理实际保留多少位置的logits取决于实现，不能把训练用完整序列的估算直接加到推理预算里。vLLM预分配量也不能当作单请求必要内存；本阶段先沿用Transformers链路，服务引擎容量后续单独评估。

#### 1.4.4.2 测量重点

首次推理与预热后的稳定推理分别反映初始化开销和持续运行开销，结果需同时注明输入规模及生成长度。延迟的统计范围须说明是否包含预处理和数据搬运；GPU异步执行要求正确同步。allocated属于reserved的一部分，两者不能相加。

#### 1.4.4.3 结果与决定

**单图生成已跑通，严格输出格式未通过。** 本样本输入4732 tokens，生成95 tokens，正常EOS结束且未触及256上限；首次及3次重复输出一致，格式失败不是输出截断造成的。

首次生成约43.30秒，后续3次平均约2.77秒；最大allocated峰值约18.55GiB，相对推理前增加约0.97GiB。计时仅覆盖同步后的generate。本样本推理容量有余量，但首次额外开销尚未归因，少量重复不能代表稳定性能或训练容量。

主要问题是输出带代码围栏、顶层为列表、字段采用bbox_2d/label，与约定的裸JSON对象及bbox字段不符；仅去掉围栏不能通过。预测框数值在界内且左右顺序正确，但尚未叠框或对照GT，定位、坐标尺度和状态质量仍未知。

**下一步：先叠框核对定位与坐标尺度，再单独处理格式合同。** 保留原生格式失败结果，不将后处理转换计为模型通过。S01继续进行，LoRA更新与正式质量基线待验证。截图来源、精确测量及分析边界见[[02_Projects/AI-Career-Transition/30_实践记录/Qwen3.5-9B睁闭眼分类微调与部署实验附录#K 2026-09-21 单图推理运行报告与状态接替]]及附录L。

### 1.4.5 步骤4：验证LoRA完整更新

#### 1.4.5.1 理论与预期

```text
LoRA运行时占用 ≈ 冻结底座 + adapter参数/梯度/Adam状态
               + backward保存的activation
               + 视觉计算与logits/loss临时空间 + runtime
```

其中activation是反向传播需要的中间结果；它随输入、batch和梯度检查点等配置变化。推理KV缓存的估算不能代替训练activation预算。

**可训练参数与状态：**

对于一个输入维度为d_in、输出维度为d_out的线性层，秩为r的LoRA使用两个低秩矩阵。对所有目标层求和：

```text
N_LoRA = Σ[r × (d_in + d_out)]
M_LoRA_states = N_LoRA × (b_param + b_grad + b_Adam_m + b_Adam_v)
```

b_param、b_grad、b_Adam_m、b_Adam_v分别是adapter参数、梯度及Adam一阶、二阶状态每个元素的字节数。此式只统计这四项，不包含activation或额外副本。

假设r=16，覆盖主语言层二维投影，排除视觉、MTP、embedding与输出头，候选adapter参数量约为**43,278,336**。若参数、梯度及两份Adam状态均为FP32，每个可训练参数共需16 bytes，合计约**0.6449 GiB**。

冻结视觉/底座不意味着全部训练activation消失；LoRA减少可训练状态，单个micro-batch的activation仍可能主导显存。

实际注入名单和dtype尚未冻结，以上仍为候选估算。正式测量前需确认实际可训练参数量及各状态dtype。

**完整logits与loss临时空间：**

若模型为每个序列位置输出整个词表的logits，其张量大小为：

```text
M_logits = B × S × V × b_logits
```

B是batch size，S是参与输出的序列长度，V是词表大小，b_logits是每个logit的字节数。

B=1、S=4096、V=248320时，完整logits使用BF16约占**1.8945 GiB**，使用FP32约占**3.7891 GiB**。

这里计算的是完整logits张量；loss可能产生额外临时副本，也可能采用节省空间的实现。短JSON监督不保证只计算回答位置的logits。各项能否同时驻留、何时达到峰值仍需实测；vLLM的预分配量不能当作单请求必要内存。

#### 1.4.5.2 测量重点

首次完整更新的测量范围需覆盖forward、backward、optimizer.step与清梯度，才能观察优化器状态初始化；稳定更新需单独统计。结果需对应实际LoRA模块、rank、可训练参数量、dtype与micro-batch。梯度检查点和像素预算对资源的影响应通过单变量比较解释。

#### 1.4.5.3 结果与决定

候选adapter状态约0.6449GiB；实际注入、完整更新、activation开销和峰值均待测。本步只确认更新正确性与资源可行性，正式训练收益、收敛和恢复验证留到S03。根据实测决定是否开启梯度检查点，以及输入预算是否需要修订。
