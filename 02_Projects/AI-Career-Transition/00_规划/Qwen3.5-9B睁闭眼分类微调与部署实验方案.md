# 1 Qwen3.5-9B驾驶员眼睛检测与状态分类实验方案

## 1.1 目标、决定与文档边界

本方案定义任务合同、实验方法、条件分支与验收标准，作为执行依据。执行按所选工作包生成实验记录，保存采用的设计版本、实际配置、测量结果、分析和下一步。阅读本方案即可理解完整方法；实际进度由记录维护。

目标是形成可评测、可微调、可恢复、可部署和可回滚的模型服务。围绕实际训练与部署需要选择工程实验，质量候选通过相关验收后即可推进部署。

- 最终部署目标和蒸馏学生均为Qwen3.5-9B。
- 质量训练优先使用GT监督与困难样本/类别平衡的针对性SFT；稳定能力缺口仍存在时，评估更大教师。学生与部署模型始终保持9B。
- 主任务为整图驾驶员眼睛检测＋状态分类，输出眼睛框、画面左右字段及四类状态。基线与优化围绕这一任务展开；纯分类对照和GT裁剪仅在需要区分错误原因时使用，部署始终接收整图。
- 双卡LoRA DDP保留为工程学习与扩展实验，完成情况独立记录；质量候选按自身评测结果进入部署验证。资源不可用时记录延期。
- 全参数训练、ZeRO/FSDP、TP/PP实作和在线logits蒸馏属于扩展内容，按具体问题选择；蒸馏按E4条件触发。
- 文档沿用独立方案、连续主记录与证据附录的结构。本方案保存跨阶段方法，P2A学习文档保存机制，阶段学习记录保存个人诊断，全局检查点保存学习位置，主实验记录保存执行结果。

### 1.1.1 Track A：模型质量主线

本轨回答：Qwen3.5-9B在驾驶舱真实整图输入下，能否满足双眼检测＋四类状态的业务要求，以及最小需要什么干预。起点是已有Qwen3.5-9B checkpoint，固定整图、任务指令与输出合同后建立zero-shot / limited few-shot基线。

```text
Qwen3.5-9B + 固定整图输入/输出合同
                    ↓
          zero-shot / limited few-shot baseline
                    ↓
                 错误归因
      ┌──────────┬───────────┬───────────┐
 prompt/schema  resolution   grounding   state/类别分布
      ↓             ↓            ↓             ↓
 模板/解码修正  整图像素预算调整  定位监督     GT/类别平衡SFT
      └──────────┴───────────┴───────────┘
                    ↓
                validation
          ┌─────────┴─────────┐
        达标                 未达标
          ↓                    ↓
     冻结最终候选        困难样本 / 扩大适配范围
          ↓             教师评估（有依据时）
       冻结测试                 ↓
          ↓                返回validation
       部署回归
```

每轮先确定一个主要错误组，再选择能检验原因的最小改动。是否存在模型容量不足，结合输入细节、标注、训练曲线和干预结果判断。

训练时分别确定监督来源、训练目标与参数更新范围。例如，用GT答案开展SFT，再选择语言侧LoRA作为更新方式；引入QLoRA时，还需单独评估底座量化。

E0～E6是可按需要组合的工作包：基线达标时采用E1→E5；需要微调时采用E1→E2→E5；SFT后仍有稳定能力缺口时，再评估E4教师分支。工程学习进度独立记录。

先用验证集选择并冻结候选，再用冻结测试集验收。测试后继续修改模型或配置时，返回开发/验证侧，并标记原测试集已被观察。

每轮记录要解决的错误、改动假设、监督来源、训练目标、更新范围、预算和接受条件，复评后决定继续、调整或结束。困难样本从训练集或开发集选取，先处理错标、不可判定输入和重复帧，同时保留普通样本回归。数据隔离规则统一见1.3.2。

DPO按偏好信号的可靠性与比较收益另行论证；RL保留为教学内容，主实验采用上述评测与监督优化路径。

### 1.1.2 Track B：模型工程学习线

本轨解释模型更新、资源消耗、扩展效率与服务行为。沿用原生PyTorch＋Transformers＋PEFT＋Accelerate训练栈，使用同一9B底座和可追溯产物。

```text
LoRA forward/backward生命周期 + label masking + optimizer state
    → gradient accumulation与checkpoint save/resume
    → 单卡 / 双卡DDP：归一化、no_sync、rank一致性与扩展成本
    → profiler归因
    → vLLM服务 / 量化对照 / multi-replica serving
    → failure / recovery / rollback
```

这条线用于组织学习内容，按需要选择实验。工程学习完成与否独立于质量候选的部署资格；例如，达标候选可先验证部署，DDP学习随后继续。真正用于该候选的训练正确性、引擎质量回归和服务安全恢复检查，仍需在对应工作包完成。

两轨共享底座、adapter/checkpoint、输入合同和评测工具，各自维护验收证据。工程练习产物成为部署候选时，同样接受Track A质量评测。

## 1.2 执行前固定的条件

正式比较前固定三组条件：

- 数据与任务：划分及样本清单、缺失/遮挡规则、图像几何和坐标转换。
- 实现与预算：模型及processor版本、训练配置、样本与更新预算。
- 验收：质量下限、允许退化和服务SLO。

历史运行满足相同合同且证据可追溯时可复用；合同、版本或关键变量改变时，重新验证受影响部分。复用范围与实际缺口写入该轮记录。

## 1.3 任务、数据与评测合同

### 1.3.1 输入输出

输入为方向已统一的整图与固定指令，由VLM生成眼睛位置和状态。首轮沿用生成式输出与监督方式；专用检测头或框回归损失留作有证据支持的架构候选。文件路径保持稳定，任务以正文定义为准。

**左右按最终输入图片中的眼睛位置定义。** 图片原点位于左上角，x向右、y向下。双眼都有可靠位置时，框中心x较小者为image_left_eye，较大者为image_right_eye。左右字段只由这一排序赋值，

输出字段结构：

```text
image_left_eye:  {bbox: [x_min, y_min, x_max, y_max], state: 四类之一}
image_right_eye: {bbox: [x_min, y_min, x_max, y_max], state: 四类之一}
```

bbox与state属于同一只眼。原始annotation保留pixel xyxy；model adapter将其转换为0～1000整数xyxy训练目标，模型生成采用同一尺度。该约定与[ms-swift Qwen3.5 grounding文档](https://swift.readthedocs.io/en/v4.1/BestPractices/Qwen3_5-Best-Practice.html)一致，本项目原生adapter显式执行转换。实现依据见[[04_Sources/模型工程/2026-09-15_Qwen3.5与DDP微调部署来源证据卡]]的2026-10-01核对。

设W、H为进入任务合同的整图实际宽高：

```text
x_norm = round(x_pixel / W * 1000)
y_norm = round(y_pixel / H * 1000)
x_pixel = x_norm / 1000 * W
y_pixel = y_norm / 1000 * H
```

原始标注保持像素坐标，读取时显式标记pixel或norm1000。model adapter负责一次性转换，按统一round规则生成训练目标。

评测先把预测框还原为像素坐标，保留浮点精度，再在原图上计算IoU。越界、退化或非法框计为失败，并保存原始预测。

输入采用原图和对应像素GT。调整方向、整体缩放或padding时，记录原图到最终输入的变换，同步变换GT框，再按最终输入坐标定义左右。processor内部缩放也按同一几何关系核对。

预测先还原到最终输入的像素空间，再通过逆变换回到原图评分。评测保存原图与输入尺寸、几何变换、坐标尺度、round规则，以及转换前后的预测框。

解析器接受裸JSON或完整单个JSON围栏，剥离围栏后严格解析，按模型原始框和左右字段评分。原标注两点转为xyxy后按中心x排序，框与状态保持对应；镜像增强后重新变换框并排序。评测保留漏框和左右错误，不通过补框或交换字段修正。

四类沿用eye_open→open、eye_closed→closed、eye_occluded→occluded、eye_narrow→narrow。

occluded表示受光线、头发等影响，状态无法判为open、closed或narrow；可理解为这三类之外的other语义，输出标签仍固定为occluded。状态不可判定与眼睛能否定位分别评估，物体遮挡只是可能原因之一。缺框、漏检和拒答另行计错。

正式基准前，结合现有标注约定固定只有一眼、位置不确定、中心x相同及完全遮挡时的输出和评分规则；明确遮挡框表示推定眼睛区域还是可见部分。单眼的左右归属与缺失状态按这些规则处理，避免按框数量或缺失情况直接赋类。

检测prompt只接收整图和任务指令；待测文件名、GT框、标注和答案保留在监督或评分侧。验收范围为单帧检测与状态判断。

### 1.3.2 复用预处理与批次划分

复用用户已预处理的整图/JSON，按批次划分训练/验证/测试，采用同一人员id不跨集合的数据约定。正式基准前固定批次映射和完整样本清单，记录隔离约定的依据及独立核验范围。数据入口使用整图及其标注。

直接读取同名同目录JSON的dataList[].coordinates与properties.eye_status，以图片实际像素尺寸作为几何依据，保持图片方向与GT原值。复用已有预处理结果，读取异常作为运行错误报告；本实验沿用跳过重复GT尺寸、框和ID审计的约定。

训练集用于监督、困难样本挖掘和量化校准；开发集与验证集用于提示比较、教师评估、阈值调整和候选选择。已展示或用于调参的样例保持开发用途。冻结测试集只用于最终候选验收，与上述优化过程隔离。

### 1.3.3 评测

评测直接针对检测＋状态任务，分别报告：

- 定位：先按固定IoU阈值作一对一位置匹配，再统计precision/recall、漏检、多余框、越界/无效框及IoU分布。匹配只依据位置，状态在匹配后单独评估。
- 画面左右关联：位置匹配后，检查模型的左右字段是否对应正确眼睛，按原字段计分。
- 状态：报告成功匹配眼睛的四类macro-F1/balanced accuracy、各类precision/recall及混淆矩阵，同时给出匹配覆盖率。
- 微调复评补充：另报对应侧四类混淆矩阵，使状态分析覆盖定位未匹配的情况；解析失败单列并计入总体失败。匹配后macro-F1注明实际覆盖的类别，例如仅有open样本时，结论限于该类。定位另报框面积比和中心偏差，区分框偏大与位置偏移。
- 端到端：报告位置、画面左右和状态同时正确的单眼比例，以及双眼完全正确率。分母包含全部GT眼睛；漏检、解析失败、非法标签和重复预测均按协议计错，后三项另行统计。

正式基准前冻结阈值、框尺度、缺失/遮挡规则和匹配协议。上述指标用于分别诊断定位与状态错误；获得可靠且一致的置信分数后，可补充mAP。按人员/session聚合分析，使相邻帧的相关性体现在结论中。

正式调参前冻结质量下限、允许退化和延迟目标。性能以整图端到端p50/p95、图像请求吞吐、失败率和显存为主，TTFT与输出token/s作为辅助。已有业务SLO时按其验收；其余情况报告测得的能力边界。

## 1.4 工作包E0：环境与兼容性（两轨共用）

E0验证模型加载、processor、图文生成与训练实现的兼容性。先在单GPU检查实际输入，再完成一次LoRA更新及资源测量；多GPU资源按所选工程实验需求安排。

执行时固定GPU型号/容量与可用范围、驱动、Python/CUDA、训练及服务依赖版本、模型路径和revision。实际机器配置与检查结果随运行保存。

实现角色分别为：

| 角色 | 选用方式 |
|---|---|
| 训练实现 | 原生PyTorch＋Transformers＋PEFT＋Accelerate |
| 正确性参考推理 | Transformers，使用固定processor与任务合同 |
| Reference implementation | ms-swift Qwen3.5 multimodal / grounding / LoRA，仅用于实现核对 |
| Serving benchmark | vLLM，完成同请求质量回归后测量服务表现 |

先固定镜像digest、模型/processor revision、依赖、代码hash、GPU UUID/驱动、随机种子和处理配置，再确认工件空间与GPU拓扑。

模型加载后，测量一次完整LoRA更新的峰值，依据更新所需显存及余量选择训练配置。加载检查与训练容量检查分别给出结论。

### 1.4.1 Reference implementation的使用范围

[ms-swift Qwen3.5文档](https://swift.readthedocs.io/en/v4.1/BestPractices/Qwen3_5-Best-Practice.html)及其官方仓库用于核对dataset representation、bbox normalization、chat template、multimodal processor、LoRA target scope和训练参数。文档示例属于参考配置，本项目按9B实际模块与既有合同检查差异。

运行依赖采用上述原生栈；ms-swift用于实现参考。若原生实现与reference behavior有差异，记录输入、模板、处理器、mask或目标模块的差异并定位。按固定版本核查环境兼容性；版本变更作为独立配置记录。

参考入口及适用版本见[[04_Sources/模型工程/2026-09-15_Qwen3.5与DDP微调部署来源证据卡]]。

## 1.5 工作包E1：整图基线与错误归因（Track A）

基线采用BF16、单卡TP=1、非思考模式、并发1，Transformers承担正确性参考推理。按实际processor输出确定输入长度与生成上限，覆盖样本尺寸分布；扩展prompt、图文示例或像素预算时重新计算输入/输出规模。vLLM服务与并发对照归入E5，显存预算通过容量和稳定性测量确定。

先用固定任务指令建立zero-shot基线，再加入一组固定的文字问答示例，建立few-shot基线。保持模型、图像处理和评测集一致，比较定位、状态分类与输出格式表现。

根据主要错误，每轮只调整一项提示内容，例如指令措辞或类别判定规则。比较前固定示例清单、示例数量、候选配置数与比较轮数，以1.3.3中的质量指标和预设门槛选优。示例从训练集或开发集选择，遵循1.3.2的数据隔离规则。

如需检验图像示例的作用，再增加图文few-shot对照，同时统计质量变化、额外视觉token和输入成本。schema约束解码另设对照，与普通解码比较格式正确率和任务指标；提示、解码与微调的收益分别报告。

固定整图处理合同后，补齐所需质量基线及参考推理的单请求成本，保持图像集合、像素预算、输出规则和版本一致。记录输入/输出token数、延迟测量范围及失败率；超预算样本显式记录和处理。多并发服务技术内容移入E5，质量归因优先保持单卡、单请求配置。

验收：取得质量、主要错误组及输入成本依据，明确最小干预。候选达标可直接进入E5；需要训练则进入targeted E2，独立执行所用训练配置的correctness gate。

### 1.5.1 错误归因与优先策略

| 类型 | 优先排查/非训练干预 | 证据支持后的训练候选 |
|---|---|---|
| instruction / format following | 模板、停止条件、输出长度、schema | SFT |
| domain adaptation | 类别定义、标注一致性、few-shot | 领域SFT |
| 基础感知/识别不足 | 输入细节、视觉编码、教师差异 | 视觉适配、targeted SFT/KD |
| grounding / localization | 对象位置、左右语义、目标尺度 | 定位相关监督或架构适配 |
| 候选排序/偏好错误 | 正确候选是否存在、评分与解码 | 难负例/ranking loss，必要时DPO |
| reasoning / decision | 核对任务规则与视觉证据 | targeted SFT；教师优势经验证后考虑KD |
| input information bottleneck | 分辨率、缩放、token预算、采集信息 | 优先修输入路径 |
| model capacity bottleneck | 排除数据、优化失败、监督不足 | 扩大适配范围或架构/容量调整 |

先按表中线索排查，再用对照选择干预。普通样本表现稳定而长尾较差时，挖掘困难样本开展针对性SFT，并保留普通样本回归。判断容量问题时综合数据、优化和干预证据；类别混淆优先比较监督损失、重采样与KD，具备可靠偏好信号后再评估DPO。

RL保留为教学内容。开展奖励优化实验需先具备可靠奖励、值得探索的行为空间与可承担成本。

### 1.5.2 视觉瓶颈归因与conditional oracle diagnostic

先在真实整图上排查视觉瓶颈。固定其他条件，分别比较像素/视觉token预算或整体缩放策略；观察IoU、框面积比、中心偏差、定位错误分布和匹配眼睛的状态指标。

每次输入预算变化同步测量视觉token和延迟，判断质量收益与服务成本是否可接受。

若整图对照仍无法区分目标尺度、分辨率、定位与状态识别问题，再用GT裁剪作辅助诊断：从训练集或验证集选少量困难样本，由GT提供裁剪位置，类别答案保持隐藏。这一条件性诊断用于观察模型在已知眼睛区域上的表现。

辅助诊断独立记录样本、裁剪方式、问题和结果，用于提出下一轮假设。裁剪会同时改变尺度、上下文和背景，假设随后通过整图单变量实验检验。

裁剪结果单列报告，与正式整图基准分开；使用范围限于训练/验证侧诊断，测试集和部署候选保持原始整图输入。

整图失败而裁剪成功时，重点检验空间细节、背景或定位假设；高质量输入仍失败时，继续检查任务定义、标注与识别能力。诊断结论服务于整图模型的后续优化。

## 1.6 工作包E2：targeted SFT与单卡正确性（Track A / B）

### 1.6.1 第一轮训练问题与更新范围

第一轮回答：在已确定的baseline错误组上，最小语言侧LoRA能否改善整图定位与四类状态指标？质量主实验优先使用单卡，依据GT开展targeted SFT，保留普通样本回归；困难样本与类别平衡采样按训练/开发侧分布安排。

首轮冻结vision encoder与连接模块，只更新经过检查的language-side LoRA。候选r=16、alpha=32、lr≈1e-4用于smoke与初始比较，最优配置由validation决定。

语言侧候选效果不足时，先复查整图分辨率、视觉token与定位证据，再选择下一轮更新范围：

- 跨模态映射问题：评估projector / connector。
- 视觉域适配问题：评估视觉侧更新。
- 语言侧适配不足：评估LoRA rank或目标模块范围。

每轮选择最有证据的候选做对照。全参数微调保留为最后候选，QLoRA按容量和成本另行比较。

正式训练前，明确E1中的目标错误组、干预假设、独立验证集和预算，再检查所用配置的监督mask、参数更新、显存容量及保存重载。通过这些正确性检查后开展质量训练。生命周期对照与DDP学习按Track B单独验收。

### 1.6.2 初始配置与正确性

| 项目 | 试运行起点 |
|---|---|
| 底座 | Qwen3.5-9B BF16，冻结 |
| 视觉编码器 | 首轮冻结，仍处理整图 |
| LoRA | r=16、alpha=32、dropout=0 |
| 目标模块 | 检查语言主干线性投影后冻结显式白名单；不复制其他架构列表 |
| optimizer | AdamW，仅adapter，lr=1e-4、betas=(0.9,0.999)、weight_decay=0.01，固定实现路径 |
| batch | 每卡micro batch=1、单卡累积8 |
| 输入 | 固定整图视觉预算与norm1000答案；总序列上限依据既有processor测量和代表性输入检查冻结 |
| 更新预算 | smoke 20 optimizer updates；首轮200 updates保留为默认工程上限，正式质量预算同时按样本/token暴露量记录，详见1.6.2.1 |
| 其他 | 训练use_cache=False；先不量化底座，不开compile；checkpointing容量需要时启用并记录 |

打印可训练参数名/数/dtype、optimizer实际持有参数；检查loss/梯度有限、adapter变化和冻结参数一致。LoRA初始化可能使个别矩阵首步梯度为零，应结合初始化与后续更新解释。

#### 1.6.2.1 训练预算与checkpoint选择

每次训练同时记录训练清单样本数、optimizer更新次数、有效global batch、计划/实际epoch、实际读取样本数和有效监督token数。重采样或重复读取计入实际读取量，并另记分布；监督token按实际参与loss计算的数量累计。

先用20次optimizer更新完成smoke test。质量短训可从0.25或0.5 epoch开始，再依据验证曲线决定是否继续到1或2 epoch；实际更新次数按数据规模、有效batch与采样策略换算。

首轮保留200次更新的工程上限，同时记录其覆盖的epoch、样本读取量与监督token数。达到上限时复评，再决定下一轮预算；验证表现饱和、退化或明显过拟合时提前停止。上述epoch档位是预算候选，执行前固定所选档位。

class-balanced或重复采样时，另记sampler长度与epoch定义；以实际seen samples/token说明训练暴露量。所有续训预算与停止条件在validation侧决定，checkpoint只按validation选择。

#### 1.6.2.2 Label masking：正式训练correctness gate

先取一个真实batch，对照输入与目标检查input_ids、labels、图像位置/占位符和多模态attention字段，再核对causal shift后的有效监督token数。监督范围按下表确定。

| 位置 | labels合同 |
|---|---|
| System / user prompt及非目标模板 | -100 |
| Image placeholder / 非目标图像位置 | -100，视觉输入仍通过对应attention/多模态字段参与前向 |
| Padding | -100 |
| Assistant bbox/state JSON | 保留目标token ID，参与监督 |
| EOS / end marker | 依固定模板合同监督；记录实际ID与mask边界 |

打印该batch解码后的输入、监督答案和有效监督token数，确认监督覆盖规定答案与结束标记。对照安装版本核查causal shift的执行位置和次数，并检查答案完整性及监督是否为空。

同时核对图像位置数量、pixel_values / grid和实际attention字段与模型输入一致。这些检查在原生collator和训练链路完成；字段与LoRA白名单以实际模型及安装版本为准。

训练配置通过此gate后才开展质量short run。

### 1.6.3 生命周期与性能

先独立测量一次更新的生命周期：加载→forward→backward→首次optimizer.step→zero_grad。在阶段边界同步，记录allocated/reserved、阶段峰值、梯度和optimizer状态字节数。

冻结底座后，activation和反向计算仍会占用资源；按各阶段实测分析显存变化，包括backward期间出现的峰值。

单卡对照S1=1×8、S2=2×4，固定8个样本/更新、样本集合、初始化、图像形状/预算与优化器。变长回答按有效目标token总数归一化。先检查更新一致性，再比较首次峰值和稳定窗口。

性能测量默认预热10次，再连续测量50次完整更新；窗口过短或尚未稳定时，两组统一调整。预热结束并清除梯度后同步GPU、重置峰值，在测量窗口边界再次同步。

独立重复三次，报告完整step耗时、图像样本与有效目标token吞吐、显存峰值及波动。GPU驻留输入测量与包含解码、处理、搬运的端到端测量分别报告。

窗口只保留被测更新，打印、checkpoint保存、empty_cache和profiler安排在窗口外；尤其避免.item打印引入同步。

Profiler独立抓取少量更新，标注forward/backward/optimizer和数据路径，解释一项具体瓶颈；一次只改一个因素。

### 1.6.4 恢复与验收

在完整更新边界保存adapter、optimizer/scheduler、RNG、步数、数据位置和版本。恢复分支与连续运行分支使用相同数据再做三次更新，比较loss、梯度或adapter更新误差。

恢复与资源验证形成工程结论，部署资格另按质量验收判断；首轮质量无提升时，仍可保留有效的工程验证结果。

Track A验收：训练correctness gate通过，验证集目标指标改善且普通样本回归可接受，随后可进入E5。Track B另验收更新/恢复、生命周期与累积对照、一次独立故障定位；其学习任务继续按证据推进。扩大视觉侧适配范围作为新的单变量候选记录。

## 1.7 工作包E3：双卡LoRA DDP（Track B：engineering learning / scaling experiment）

本工作包回答：相同训练目标下，双卡是否保持更新语义一致，获得的加速是否值得GPU成本？它独立于model-quality gate。质量主实验先用单卡减少变量，单卡容量与显存余量由完整更新测量确认。

DDP进入正式训练的触发条件是单卡吞吐过低、总训练时间不可接受，或目标global batch确需扩大；真实多GPU scaling验证可单独作为工程学习理由。普通DDP每卡复制完整底座与本地训练状态，单卡OOM应先定位activation/状态并采用降显存或分片方案，容量满足后再评估DDP。GPU数量按容量前提、训练时间与扩展实验需求选择。


每GPU一个进程，torchrun+NCCL；先注入LoRA再包装DDP。每卡完整冻结底座与adapter，分配不同样本，两个rank更新轮数一致。明确sampler补齐/丢弃行为；正确性实验使用固定全局样本清单，避免重复样本混入。

| 配置 | GPU数 | 每卡micro batch | 累积 | 全局样本/更新 |
|---|---:|---:|---:|---:|
| 单卡 | 1 | 1 | 8 | 8 |
| 双卡 | 2 | 1 | 4 | 8 |

先确定本次全局更新的有效目标token总数N：对所有累积轮的标签计数，再跨rank求和。设W为rank数，S(r,k)为本地该轮token loss总和。

默认DDP平均梯度且框架没有额外缩放时，各轮backward使用W×S(r,k)/N。这一式子已覆盖全局token归一化，保持该缩放值即可；实现时核对框架的自动缩放，避免再次除以累积次数。非最后累积轮的no_sync同时覆盖forward与backward。

先比较前几次全局loss、同步后梯度、adapter更新和rank间一致性，记录绝对/相对误差。BF16按经过核查的数值容差比较；先测参考误差，再固定容差。

超出容差时，依次检查样本、mask、归一化、padding、随机性和数值路径，定位原因后重测。

性能窗口rank对齐、GPU同步，采用最慢rank完成时间；报告单卡/双卡耗时、加速比T1/T2、效率(T1/T2)/2、GPU·秒T1与2T2、通信和等待。增加一组no_sync开关对照，其他条件不变。结果不要求两倍加速；四卡为可选扩展。

在共同更新边界保存状态，以及各rank的RNG和数据位置。演练一个rank中断，检查失败退出、超时和恢复，并核对恢复后的样本顺序与更新次数。

扩展性能实验使用真实多GPU。资源临时不可用时记录延期；单GPU多进程练习只验证进程逻辑。

## 1.8 工作包E4：条件性教师监督与KD（Track A条件分支）

先用GT监督开展SFT，再按错误组评估困难样本训练或类别平衡采样。若9B仍存在稳定能力缺口，使用相同整图输入合同和相同训练/开发/验证侧困难样本，比较更大教师与9B。

教师在关键指标上明显更好，且监督可获取、许可与预算明确时，进入KD实验。教师优势标准在比较前固定，同时检查普通样本表现。

进入KD后，优先评估教师答案或伪标签监督。具备可验证软信号及对齐方案时，再评估概率或排序信号；特征/logit蒸馏需有明确迁移假设。具体类型见下表。

候选已达标或教师缺少优势时，记录跳过理由并继续E5。9B始终是学生与部署目标。

### 1.8.1 蒸馏信号粒度

| 类型 | 适用条件与限制 |
|---|---|
| Response / sequence-level | 教师完整回答用于SFT；跨架构容易，短JSON的额外结构有限 |
| Pseudo-label | 教师补充训练侧未标注样本；区分数据增量、重标与教师信号收益 |
| Logit / probability | 可获得可靠软分布并对齐输出空间；异tokenizer不能直接逐token比较，可优先四类概率 |
| Candidate score / ranking | 存在共同候选集合，教师排序明显更好 |
| Hidden-state / feature / attention / relational | 有明确表征迁移假设，可处理层、维度、空间位置或关系对齐 |

蒸馏类型可按假设组合选择。架构差异大时，优先考虑教师答案、可对齐概率或排序信号，再评估特征对齐。离线答案/伪标签适合作为低成本起点，在线或特征蒸馏按证据选择。

### 1.8.2 GT与教师监督

```text
L_total = λ_gt L_gt + λ_kd L_kd + λ_aux L_aux
```

GT用于保持任务正确性，教师提供软信号或行为示范；损失权重结合尺度与有效样本mask设置。硬伪标签只保留教师的离散答案，软分布和表征信息需通过相应蒸馏方式获取。

GT与教师冲突时，先区分教师错误、标注噪声和定义差异，再决定采用或修正哪一项监督。

先在验证侧用GT校准教师置信度，再据此筛选监督。结合GT、规则、多教师或重复预测检查一致性，同时检查共同偏差。

按类别与困难组抽检保留的样本，确认长尾仍有覆盖。教师自报置信度仅作待校准信号；筛选遵循1.3.2的数据隔离规则。

### 1.8.3 KD与偏好优化

按教师提供的信号选择优化方式：完整答案用于SFT，logits用于相应KD，可靠偏好对用于DPO。KD学习教师的分布、行为或表征；DPO调整chosen与rejected的相对偏好。

引入DPO前，检查偏好对是否可靠，并与简单监督方案比较质量收益。偏好信号迁移和logit蒸馏分别评估。

### 1.8.4 复评与成本

固定输入集合与更新预算，比较无教师和有教师监督的候选。复评整体指标、困难组、普通样本回归和服务成本，据此接受候选或返回错误归因。

额外数据、教师计算及离线logits的存储/对齐成本分别统计。教师生成可按预算分配给多个GPU独立处理；学生优先使用已验证单卡配置，扩展时采用已验证DDP。部署使用9B学生独立完成推理。

## 1.9 工作包E5：9B部署回归（Track A）与量化对照（Track B / 按需候选）

验证集选checkpoint，最终候选才进入冻结测试集。兼容时加载adapter，否则验证合并产物；保存底座/adapter身份、合并精度与脚本，检查合并前后任务指标和输出差异。底座、adapter和合并产物均可追溯。

先用Transformers建立正确性参考，再用vLLM验证接近部署的服务表现。两者使用相同请求清单与模型产物，逐组核对：

- 输入处理：processor、缩放、方向和chat template。
- 输出规则：bbox合同、非思考模式、stop token、输出上限和schema。
- 模型加载：adapter支持与身份、合并产物身份及其行为。

直接adapter和合并产物分别验证加载、生成和质量回归。

在开发/验证请求上比较跨引擎的框有效性、IoU、匹配眼睛状态指标、端到端指标和JSON解析成功率，并固定允许差异。输出差异按任务指标判断，明显回归需解释或修复。

选定并冻结部署配置后，再开展测试与部署回归；配置选择遵循1.3.2的数据隔离规则。

服务性能依次评估并发1/4/8，保持图像集合、像素预算、输出规则、模型和processor版本一致。冷启动与预热后的稳定服务分别记录；先短测筛选，候选窗口延长并重复3次，报告请求数、波动及实际输入/输出token数。

先验证BF16质量和服务链路，再选择当前架构/GPU/引擎明确支持的量化路径。FP8是优先核验的候选，支持性及收益按固定版本与运行证据确认；不适用时记录原因，再选择受支持路径。官方recipe用于定位候选路径，支持性需在固定的实际版本上验证。

```text
BF16质量基线 → supported quantization
    → same-request质量回归 → latency / throughput / VRAM比较
```

量化对照固定processor、输入几何、model adapter与解码规则，仅改变所比较的量化配置。训练侧提供校准数据，验证集用于选择量化方式与阈值。QLoRA训练与部署量化分别比较。

BF16候选通过验收后可部署，量化学习按自身实验结果继续。

比较同请求负载的质量、图像端到端p50/p95、吞吐、失败率、显存；再比较相同显存预算的容量。量化不达质量门槛则拒绝，保留BF16。

## 1.10 工作包E6：多副本服务与故障演练（Track B / 按业务扩容需求）

每卡运行一个完整服务副本，TP=1，由前置路由分配请求。各副本独立推理，训练DDP的梯度同步用于训练场景。

先在相同总负载下比较单副本与双副本，再提高请求到达速率，观察排队和SLO内吞吐。加入处理成本不同的图像请求，检查负载分配。

先验证健康检查、超时、取消、异常输入和限流，再演练单副本中断、摘除、重启加入与回滚。记录整体及每副本的吞吐、尾延迟、排队、错误、显存和恢复耗时，同时核查客户端容量。

中断中的流式响应按既定错误处理和重试协议评估，验收范围不包含无缝续接。

最后对候选做持续负载测试，固定运行时长与请求分布，观察质量和性能漂移。交付启动配置、模型版本、日志指标、长度/并发限制、回归集，以及回滚至原始9B BF16的方法。

该实验验收生产流程演练；正式生产SLO在真实业务负载下另行验证。

## 1.11 工件、停止条件与双轨验收

工件按manifests/configs/data/scripts/runs/adapters/checkpoints/profiles/reports组织，执行时固定根路径。每次记录实验问题、所属轨道、改变变量、预测、实际结果、固定条件和结论边界。每个benchmark注明输入合同、数据split/清单、模型版本、processor及decode参数。

遇到NaN、空监督、冻结参数误更新、DDP不一致、数据泄漏或版本身份变化时，停止后续比较并修复。OOM保留原配置与日志，改动参数后的运行使用新配置身份。

正式运行预算依据smoke test测得的step成本估算；GPU数量和占用时长按所选实验需要安排。

Track A按候选实际使用的路径验收；Track B按独立工程实验验收。各轮记录列明采用的工作包、实际结果及满足或未满足的验收条件。

| 工作包 | 轨道与验收问题 | 应取得的证据 |
|---|---|---|
| E0 | 共用：环境、模型、输入与训练实现是否兼容？ | 固定版本与身份，加载/图文生成检查，LoRA完整更新及资源测量 |
| E1 | A：整图定位、左右关联与四类状态是否达标？ | 固定split上的质量基线、错误组、输入成本及干预依据 |
| E2 | A：targeted SFT是否改善错误组？B：更新与恢复是否正确？ | masking与冻结参数检查，等条件复评，更新/重载/恢复及资源对照 |
| E3 | B：单双卡一致性及扩展收益如何？ | loss/梯度/更新一致性，效率与GPU·秒，rank中断恢复 |
| E4 | A条件分支：教师有优势且KD有收益吗？ | 教师触发条件、信号审核、等预算收益与普通样本回归；未触发时保存跳过依据 |
| E5 | A：部署质量是否保持？B/按需候选：量化收益如何？ | 同请求跨引擎回归，BF16服务质量与性能，候选量化的质量/成本对照 |
| E6 | B/业务扩容：多副本服务是否满足扩展要求？ | 同负载与增压对照，故障摘除/恢复/回滚，持续负载与SLO范围 |

## 1.12 设计依据与修订规则

机制依据为[[02_Projects/AI-Career-Transition/10_学习文档/P02A-01_VLM模型工程认知_学习文档]]第2、3、11章；模型、框架与实现参考见[[04_Sources/模型工程/2026-09-15_Qwen3.5与DDP微调部署来源证据卡]]。设计参数是实验起点，运行测量用于检验其适用性。

执行结果可以提出设计变更建议。改变任务合同、干预方法或验收标准时，先明确修订理由、依据和适用轮次，再按修订后的设计执行；原轮次保留当时采用的版本、结果与结论边界。进度或单次指标更新写入记录，设计在方法或合同改变时修订。
