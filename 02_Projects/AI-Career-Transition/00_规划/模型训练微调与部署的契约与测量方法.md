# 1 模型训练、微调与部署的评估和测量方法

## 1.1 从决策问题建立契约

先明确实验结束后要做什么决定，再选择指标和工具。模型架构影响执行路径，但不直接决定业务成功的定义。本文中的质量指任务质量，区别于BF16、FP8等数值精度。

| 决策问题 | 实验类型 | 主要输出 |
|---|---|---|
| 模型能否完成任务？ | 质量评估 | 整体与关键组质量、错误分布、适用边界 |
| 是否需要微调、应改哪里？ | 错误归因与干预对照 | 数据、输入、监督或更新范围的改进假设 |
| 相同工作能否执行得更快？ | 实现效率对照 | 耗时、吞吐、资源变化及正确性 |
| 哪种训练方法更经济？ | 等预算或达标成本比较 | 质量—成本关系 |
| 设备能否稳定运行？ | 容量与持续运行测试 | 支持的输入、batch、并发范围 |
| 服务能承受多大负载？ | 负载扫描 | 延迟约束内的成功吞吐、错误和积压 |

质量契约规定任务成功、评分分母、整体与关键组门槛；
性能契约规定负载、时间边界、延迟/吞吐和成本；
显存契约规定每卡预算、输入范围与容量余量。
测量契约横跨三者，规定如何取得有效证据。

先检查数据、监督、样本对应和执行正确性，再判断硬门槛，最后在可行候选中取舍。质量失败不能用吞吐补偿。业务门槛未确定时允许探索，但结论限于能力边界，不能宣称业务验收通过。

## 1.2 质量评估：从任务选择指标

### 1.2.1 区分任务质量、输出可用性与诊断指标

CNN输出类别与VLM输出类别名称时，可以共享分类指标；VLM生成JSON、位置和解释时，再增加输出协议与相应任务评分。不要仅按架构分成两套指标。

| 输出形式 | 主指标候选 | 配套检查与边界 |
|---|---|---|
| 有限类别 | 各类precision/recall、macro-F1或balanced accuracy | 类别分布、混淆矩阵、关键错误成本 |
| 位置与类别 | 定位precision/recall、匹配后分类、端到端成功率 | 匹配规则、IoU、漏检和重复预测、条件指标覆盖率 |
| 结构化字段 | 字段正确率、完整记录成功率 | 解析率、缺失/额外字段、非法值 |
| 短答案问答 | 按冻结答案规则计算正确率 | 同义表达、单位、数值容差和拒答规则 |
| 开放式回答 | 事实正确性、所需事实覆盖、证据支持性 | 人工评分准则、一致性及自动评审器偏差 |

输出可解析只是可用性条件，不能替代语义正确。训练loss或token accuracy可以诊断优化过程，但不能替代生成后完整任务的评估。

### 1.2.2 分类指标如何选择

先固定类别集合，并规定未知标签、解析失败和拒答如何计错。不得只在成功解析的样本上给出总体分类结论；条件性分类指标应同时报告覆盖率和端到端结果。

类别不平衡且希望各类等权时，可选macro-F1；主要关注各类召回时可选balanced accuracy，即各类recall的宏平均。关键类别漏检代价大时，另设该类recall下限。

主指标用于选型，诊断指标用于解释，不必把全部指标都设为门槛。阈值只能在开发/验证侧选择。若采用置信分数，应定义其来源和校准方式。

### 1.2.3 定位、结构化输出与生成式模型

定位评分先冻结坐标、匹配阈值、一对一匹配规则及重复预测处理。需要区分定位和分类错误时，先按位置匹配，再评价类别；整体评分还应覆盖漏检、非法输出和额外预测。若使用按置信分数排序的检测指标，必须先定义可比较的检测分数，不能仅为生成框补一个任意常数后按常规排名指标解释。

结构化输出先冻结允许的规范化，例如仅允许空白和键顺序差异；不得在评分中补答案、交换错误字段或用GT修复输出。数值字段分别规定绝对/相对误差或几何容差，字符串按字段语义评分，完整字符串exact match不适合所有任务。

生成式模型还需记录截断、结束标记、输出长度、prompt和解析器版本。格式改善与任务质量改善分别报告；限制输出长度或约束解码后，仍需重新检查语义质量。

### 1.2.4 开放式回答如何建立可复核评分

1. 按问题类型列出必需事实、允许答案、不可接受错误与证据不足时的行为。
2. 建立评分样例，包含正确、部分正确、幻觉、拒答与边界案例。
3. 由评分者独立试评同一批样例，检查分歧集中在哪条规则；修订后冻结rubric。
4. 对正式候选隐藏模型身份并固定答案呈现方式，保留逐条评分和争议处置。
5. 使用模型评审器时，以独立人工样本核查其偏差、重复性及对答案顺序的敏感性；更换评审器或prompt视为评分协议变化。

评审器不等于真值。文本相似度只能作为明确适用任务的辅助；词汇相似不能保证视觉事实正确。人工预算不足时，优先缩小结论范围并报告缺口。

### 1.2.5 数据覆盖和错误归因

先固定评估单位：图像、目标、问题、文档或会话。数据隔离按可能泄漏的实体和采集关系设计；训练、开发/验证和最终测试用途分开。困难样本用于诊断时单列，不能未经加权混入后称为自然分布质量。

按类别、输入大小、遮挡、场景或其他任务相关因素分组，报告数量及失败模式。先检查标注和输入，再检查定位、类别、格式与生成限制；每轮选择一个主要错误假设做最小干预。辅助裁剪、提示答案等改变了可见信息，只能支持条件性诊断，不能替代真实输入验收。

## 1.3 性能评估：何时测吞吐，何时测延迟

### 1.3.1 按待解决问题选择计数单位

| 场景 | 优先指标 | 必须固定 |
|---|---|---|
| 单请求交互 | 端到端延迟、p50/p95、失败率 | 是否含排队、网络、解析与重试 |
| 离线批处理 | 清单总时间、样本/s | 同一清单、尾批、失败处理 |
| 流式生成 | 首次输出时间、后续生成速度、完整响应时间 | token定义、流式协议和输出长度 |
| 在线容量 | 成功吞吐、尾延迟、错误率、积压 | 到达或并发模型、时长与请求分布 |
| 训练执行 | 完整更新耗时、样本/s、有效监督token/s | 全局更新语义、输入规模与归一化 |
| 训练方案 | 等预算质量或达标成本 | 目标质量/预算、评估频率和选择规则 |

图像或业务请求优先使用images/s或requests/s。输出token/s用于诊断生成路径，不能独立评价业务容量；跨tokenizer时token数也不是相同工作量。训练的有效监督token是实际参与loss的非屏蔽目标token，另记输入token、视觉规模及padding，避免把更多无效计算当作有效吞吐。

TTFT须注明从客户端提交还是服务端接收到首个token；第一个token可能只是JSON标点，不等于第一个可用答案。短结构化回答通常更关心完整答案延迟。比较生成速度时同时报告实际长度、完整性与质量。

### 1.3.2 吞吐公式与窗口边界

固定清单实验：清单处理吞吐 = 清单请求数 / 全部请求终结的总时间，失败按协议终结且另报；成功吞吐 = 成功请求数 / 同一总时间。任务答案正确率另外评分，不能把“无异常返回”直接叫任务成功。

固定时间窗口实验：完成吞吐 = 窗口内完成数 / 窗口时长。记录窗口起止时未完成数、提交数、失败数、取消和重试，说明预热请求是否跨入窗口。对一个指定提交批次追踪到全部结束的统计与按时间窗计数的统计分开，避免分母混用。

窗口内吞吐不等于每个请求的平均速度，batch总耗时除以batch大小只是摊销耗时。多个副本的整体吞吐按共同总窗口计算，不能相加不同窗口测得的峰值。

### 1.3.3 在线负载扫描步骤

先选择负载模型：固定并发表示客户端有空位才继续提交；固定到达速率表示按预定节奏提交，两者必须分开报告。系统变慢时，固定并发可能同时降低实际提交速率，因此不能仅凭其结果判断能否承受某个持续到达速率。

从低负载开始，逐档提高；每档保留相同请求分布、超时/重试和运行时长，并记录实际到达速率。观察成功吞吐、p50/p95、失败和队列是否持续增长；确认客户端自身不是瓶颈。终止超载档位时仍保存未完成请求数量与处置。

选择满足延迟和错误约束、无持续积压且保留所需余量的负载；在候选点延长运行确认稳定性。最大瞬时吞吐只作为边界线索。统计成功请求延迟时，必须同时给出失败/超时率，不能删除慢失败后宣称延迟达标。

### 1.3.4 三种训练比较不可混用

- 固定更新语义：保持样本、初始化、全局batch、监督归一化及优化器一致，改变micro batch/累积或执行方式，先检查更新一致性，再比较完整更新成本。
- 固定计算预算：比较同预算下的验证质量，记录实际更新数、样本/token暴露量和评估开销。
- 固定目标质量：比较首次满足预设质量及稳定性条件时的总时间和GPU成本。固定评估频率，防止检查更频繁的方案表面上更早达标。

GPU·秒可按各卡分配运行时长求和，说明计算的是资源分配成本还是其他口径。总成本明确是否包含数据准备、评估、checkpoint和教师生成。未达标候选报告耗尽预算和质量，不虚构达标时间；step更快不自动意味着训练方案更好。

## 1.4 显存与容量：从测峰值到确定运行范围

### 1.4.1 先选统计口径

每卡分别记录allocated、reserved与设备整体占用；前两者有包含关系，不能相加。设备层观察可能含其他进程或非PyTorch分配，不能当作tensor内存。缓存释放改变的是缓存状态，不是已经活跃的tensor需求。[CUDA显存语义](https://docs.pytorch.org/docs/2.14/notes/cuda.html#memory-management)

分别测加载、首次完整训练更新、稳定训练及推理/服务。首次optimizer状态建立、反向activation及服务缓存可能出现在不同阶段；只测加载不能判断训练容量。按窗口重置峰值统计，记录窗口开始占用和窗口内绝对峰值；不能用阶段结束占用代替峰值。

### 1.4.2 容量搜索步骤

1. 固定模型、数值精度、执行路径、设备共存占用及其他条件。
2. 从明确可运行的小配置起步，每轮只扩大batch、序列长度、视觉预算或并发中的一个变量。
3. 完成真实操作生命周期，记录每卡峰值、吞吐、失败位置与输入分布。
4. 发生OOM时保存配置和日志，恢复到干净且条件一致的运行环境后再试新配置；不得静默缩小输入后算作原配置成功。
5. 在候选配置上分别覆盖代表性输入和较大输入，并进行符合使用场景的持续运行。
6. 给出“最大观察到可运行配置”和“推荐配置”，说明余量如何覆盖波动与共存需求。

容量曲线可能受算法选择、padding或缓存策略影响；粗扫后可在边界附近细扫，不预设所有尺寸严格单调。没有实际覆盖的输入组合不能宣称支持；总多卡显存不能掩盖某一卡OOM。

### 1.4.3 结果如何限制结论

采样式设备监控可能漏掉短峰值，报告采样间隔；allocator高水位统计只覆盖相应分配器口径。稳定运行一次不是普遍容量证明。压力清单用于边界判断，不能把其吞吐当作常规分布吞吐。余量由实际输入范围和使用条件决定，不规定通用百分比。

## 1.5 测量尺度与工具：逐层深入再返回整体

### 1.5.1 执行尺度

| 尺度 | 适用问题 | 方法 | 解释限制 |
|---|---|---|---|
| 完整任务 | 全量评估/训练成本 | 墙钟时间和任务日志 | 不能单独定位算子瓶颈 |
| 请求/完整更新 | 响应或一次更新成本 | 请求时间戳、完整窗口计时 | 不能假定全部时间都在GPU |
| 阶段 | 数据、传输还是计算占主导 | 阶段标记、时间线、隔离对照 | 并行重叠阶段不能直接相加 |
| 算子 | 优先优化哪些操作 | profiler算子统计与调用轨迹 | 算子收益不等于整体收益 |
| kernel | 特定GPU执行路径为何低效 | 按已识别热点选底层工具 | 结论受shape、硬件及实现限制 |

先测端到端，发现差距后细分阶段；只有阶段分析不能支持下一步决定时才深入算子或kernel。优化后返回普通模式复测完整工作负载。

### 1.5.2 时间尺度与负载尺度

冷启动测从定义的启动事件到服务可用；首次请求/首次更新单列；稳态窗口用于稳定效率；持续运行用于观察积压、资源增长及漂移。预热条件须对照一致并覆盖目标执行路径，不用统一“10次”保证所有系统已稳定。

单个case检查链路；固定诊断集做受控比较；代表性清单估计目标分布表现；压力负载探测边界。单case耗时不能自动外推全量，重复同一清单不能增加独立质量样本数。

### 1.5.3 计时工具的选择与操作

| 方法 | 适合范围 | 必须注意 |
|---|---|---|
| 单调墙钟，如perf_counter | 含CPU准备、GPU和后处理的隔离端到端窗口 | 开始前排空此前工作，结束前等待被测工作完成 |
| CUDA events | 已确定stream和依赖的GPU区间 | 等待结束event；不含CPU读图、网络和排队，多stream需明确依赖 |
| torch.utils.benchmark | 可重复的小操作或函数实现比较 | 固定输入、线程和状态；不等于在线服务负载测试 |
| 请求级时间戳 | 在线端到端与排队分析 | 使用同一时钟域计算差值，明确开始/结束事件 |
| profiler | CPU/CUDA时间线、算子和内存归因 | 用短窗口，保留普通模式基线 |

CUDA具有异步执行语义；只在CPU侧围住一次GPU调用可能测到提交而非完成。对隔离的单GPU批处理窗口，可使用“预热→同步→墙钟起点→执行整个窗口→同步→墙钟终点”。该方法不应变成在线共享服务中每个请求都全设备同步，否则会扰动并发。[CUDA计时语义](https://docs.pytorch.org/docs/2.14/notes/cuda.html#asynchronous-execution)、[Benchmark教程](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html)

微基准先控制预热和状态，再重复足够工作以降低计时开销占比，保存每轮结果。不要在稳定窗口内插入打印、保存、empty_cache或额外同步。训练微基准须说明参数/优化器是否持续变化；不能把重复有状态更新假定成完全相同的调用。

### 1.5.4 如何使用profiler而不误读结果

用record_function等标记数据读取、预处理、传输、forward/generate、backward和optimizer。先看时间线中的等待与重叠，再看热点算子及调用次数；total与self时间、父子调用不能重复相加。视觉编码、prefill和decode是否能分开，取决于实际执行路径和可用标记，不虚构阶段分解。

使用schedule选择少量代表性步骤，按需要开启shape、内存或调用栈采集；保存配置和trace。首次采集和stack tracing等会增加开销，长任务全程追踪也会产生很大数据量。热点修复后用未开启profiler的普通测量复验。[Profiler教程](https://docs.pytorch.org/tutorials/recipes/recipes/profiler_recipe.html)

逐阶段强制同步可以做隔离诊断，但改变了重叠关系；其阶段耗时不能直接拼成原系统耗时。GPU利用率高或某算子占比大都只是线索，尚需对照证明改动改善目标指标。

## 1.6 实验设计、统计与停止规则

### 1.6.1 选择样本量、重复次数与窗口

先列必须覆盖的类别、场景、输入规模和关键错误，再选择样本；不为所有任务统一规定张数。类别缺失就限制该类结论。相关视频帧按会话等独立单位组织划分与分析；不能把连续帧当成同等数量的独立证据。

先用小型试测估计运行波动，再预先声明正式重复次数、窗口和预算。比较两个候选时使用相同样本，按样本或独立组观察配对差异；训练策略比较还应覆盖需要研究的随机种子差异。可交错运行配置减少时间顺序偏差，并记录设备占用和热状态。

重复测量主要说明系统波动；更多独立数据才扩大质量证据。若使用置信区间或重采样，说明估计对象、独立单位和方法；按会话相关的数据不要未经处理逐帧独立重采样。不能反复追加运行直到偶然出现有利结果再停止。

### 1.6.2 统计量如何对应问题

总处理成本看总时间；典型请求体验看中位数；尾部约束看p95等分位数，并报告请求数、窗口和超时。样本少时尾部分位数很不稳定，不能用少量请求作强验收结论。各轮p95的平均值不等于所有请求合并后的p95，须注明聚合方式。

分类报告每类支持数、整体与分组结果；性能报告各次运行和波动，不只选最快一次。变化小于测量波动时写“当前证据不足以区分”，而非“相同”或“确定更优”。若定义容差，应事先结合业务代价和测量误差设定，不在看到结果后迁就候选。

### 1.6.3 单因素归因与完整方案比较

单因素实验用于解释原因；多因素同时改变可用于比较完整方案，但收益只归于完整配置。相同请求负载下的质量/延迟比较，与相同显存预算下可承载容量比较分开。

冻结模型、processor、代码、依赖、解码、评分协议和数据身份；任何相关变化都建立新配置身份。调参使用开发/验证侧，最终测试不反复用于挑选方法。预先规定预算耗尽、质量退化、错误和收益饱和时如何停止。

## 1.7 结果有效性、验收与归因边界

| 状态 | 例子 | 处置 |
|---|---|---|
| 有效且达标 | 规定负载下质量、延迟和容量均满足门槛 | 在测量范围内接受候选 |
| 有效但不达标 | OOM、质量下降、无加速 | 保留负结果，拒绝或提出下一轮假设 |
| 测量无效 | 漏计GPU执行、样本错配、峰值窗口错误 | 标记受影响指标，修复后重测 |
| 有效但不可直接归因 | 模型、输入和输出预算同时改变 | 保留完整配置比较，补受控实验后再归因 |

有效性按指标和证据判断。评分错误可能不影响独立有效的耗时，但失去“等质量加速”依据。范围不足不是证明没有问题：缺少某类、某负载或某生命周期阶段时，明确缺口。

先排除错误执行，再检查硬约束，在剩余候选中按预定目标选择；互有优劣时保留取舍，不随意压成一个综合分数。先确认版本和条件，再复用历史证据。新契约不把历史缺项追记成已测，也不自动要求所有历史运行重做。

## 1.8 测量契约模板与复验规则

每轮保存具体取值和版本，不以模板代替设计。

| 字段 | 运行前或运行后记录 |
|---|---|
| 决策问题 | 要选择、接受、拒绝或定位什么 |
| 任务与质量 | 输入输出、评分协议、分母、关键组、门槛与容差 |
| 对象身份 | 模型/adapter、processor、代码、依赖、数据清单与hash |
| 性能与资源 | 计数单位、边界、负载、每卡预算、输入与输出范围 |
| 变量与不变量 | 哪个因素变化，其他条件如何一致 |
| 测量方法 | 工具、时钟、同步、预热、窗口、独立重复与运行顺序 |
| 接受与停止 | 质量、延迟、错误、容量门槛，预算与停止规则 |
| 结果与波动 | 每轮原始值、汇总、分组、样本量和不确定性 |
| 有效性与结论 | 结果状态、支持的决定、不能外推的范围 |
| 证据与复验 | 命令、配置、原始输出和trace路径，条件变化时的重测范围 |

改变任务、评分、输入分布、模型或运行路径时，评估影响并重测相关部分。保存原结果及当时契约；更正用明确记录说明，不把旧结果静默替换成新条件下的事实。
