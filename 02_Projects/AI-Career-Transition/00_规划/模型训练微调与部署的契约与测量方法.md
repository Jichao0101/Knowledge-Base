# 1 模型训练微调与部署的契约与测量方法

## 1.1 定位与决策顺序

模型工程需要在任务质量、性能与资源约束下选择可用方案。先明确任务和使用场景，再选择模型、训练方法和部署路径。

本文统一使用“任务质量”，避免与BF16、FP8等数值精度混淆。性能包含吞吐、延迟、失败率及时间或GPU成本。显存既是可行性约束，也是需要按生命周期测量的资源指标。

```text
任务与使用场景
  → 正确性前提
  → 质量／性能／显存契约
  → 测量契约与基线
  → 有假设的受控干预
  → 验收、选择与结论边界
```

质量、性能和显存契约定义“需要满足什么”；测量契约横跨三者，定义“用什么证据证明”。数据泄漏、错误监督、错误样本对应或错误计时应先修复，不能用更高吞吐补偿。

## 1.2 三类目标契约

### 1.2.1 质量契约

实验开始前明确以下内容：

- 任务：允许的输入、期望输出、不可判定与拒答规则、适用人群或场景。
- 数据：训练、开发、验证、测试的用途，隔离单位、代表性与排除范围。
- 指标：主指标、诊断指标、分子与分母，失败样本如何计入。
- 门槛：整体质量下限、关键分组下限、允许退化及候选选择规则。
- 结论：覆盖哪些分布与群体；样本量、类别缺失及样本相关性如何限制结论。

主指标应反映完整任务成功，条件性诊断指标应同时报告其覆盖范围。例如，仅在成功定位目标上计算分类指标，不能替代端到端任务质量。重复同一固定清单只能帮助观察运行波动，不能凭重复次数扩大数据覆盖或证明泛化。

### 1.2.2 性能契约

先区分工作负载，再定义速度与成本：

| 场景 | 主要问题 | 建议记录 |
|---|---|---|
| 离线推理 | 完成固定数据清单需要多久？ | 总完成时间、样本吞吐、失败率、GPU数量与GPU·秒 |
| 训练实现对照 | 同样的全局更新工作，哪个实现更高效？ | 完整更新耗时、样本与有效监督token吞吐、更新一致性 |
| 训练方案对照 | 哪个方案更经济地获得目标质量？ | 达标时间、实际暴露样本/token、更新数、总GPU成本；未达标注明预算耗尽或提前停止 |
| 在线服务 | 指定负载下，能稳定服务多少请求？ | 端到端p50/p95、排队、成功吞吐、失败率、SLO内吞吐 |

固定全局更新语义的实现比较与固定质量目标的方案比较分开解释。训练step更快不自动意味着更早达到质量目标。总成本应注明是否包含评估、checkpoint、数据准备及教师生成等开销，优化窗口与完整任务耗时分开报告。

在线服务须明确到达速率或并发模型、输入大小及输出长度分布、运行时长、超时和重试规则。延迟应注明统计对象；超时和失败不能因没有完整响应而从报告中消失。batch耗时除以样本数只是摊销耗时，不等于在线单请求延迟。

### 1.2.3 显存契约

固定每卡容量、可用预算、其他进程占用、模型与运行配置，以及允许的输入大小、序列长度、batch和并发范围。

分别测量加载、首次训练更新、稳定训练、推理或持续服务。加载成功不能替代完整更新或峰值输入下的容量验证。记录每卡峰值及余量；不能用多卡总容量掩盖某一卡容量不足。

allocated、reserved和设备整体占用分别记录测量来源、范围与窗口，不相加。allocator口径与设备整体口径用于不同层次的判断；设备采样峰值还须说明采样频率的限制。

代表性负载用于常规性能比较，较大输入或高并发用于容量压力测试，分别报告。余量由目标输入范围、部署共存条件和波动证据确定，不统一代填一个比例。OOM是该配置在该条件下不可行的有效证据；改变batch或输入后必须使用新配置身份。

## 1.3 测量契约：每个实验一张卡

下表同时作为可复制模板。实例可引用已经冻结的任务合同，不必重复正文；关键执行取值与缺口必须可直接定位。

| 字段 | 填写要求 |
|---|---|
| 决策问题 | 实验后要选择、接受、拒绝或定位什么？ |
| 对象与身份 | 模型/adapter、代码、依赖、processor、数据清单及版本或hash |
| 测量对象 | 指标、单位、分子分母、统计对象与聚合方法 |
| 条件与变量 | 硬件、输入/输出规模、负载、随机性；不变量和有意改变的因素 |
| 方法与边界 | 开始/结束位置、GPU同步、预热、重复次数、窗口、包含/排除项、失败处理 |
| 接受与停止 | 质量和资源门槛、允许退化、预算、停止条件及选择规则 |
| 结果与波动 | 每次独立运行的结果、聚合值和波动；样本覆盖与统计限制 |
| 解释范围 | 支持的结论、不支持的归因或外推 |
| 证据与失效 | 命令、配置、逐样本结果/原始测量路径；何种变化要求重测 |

运行前填写设计字段，结果字段保留待测；不得填入推测数字。
计时先说明端到端边界，再按需要增加GPU驻留输入或阶段窗口。预热、冷启动、首次optimizer状态建立和稳定窗口分开。独立profiler用于归因，普通测量用于性能比较；profiler观察不直接替代服务或训练稳定性能。

## 1.4 比较、归因与有效性

### 1.4.1 先保证可比，再解释收益

机制归因优先一次改变一个因素，并保持任务语义、样本集合和度量口径一致。系统方案比较可以同时改变多个因素，但结论只归属于完整配置，不把收益单独归于某一技术。

同请求负载比较与同资源预算容量比较回答不同问题，分开报告。量化、输入分辨率、输出上限、batch和并发变化均需检查质量影响；更短或不完整的输出不能被直接解释为等质量加速。

### 1.4.2 区分三种结果状态

| 状态 | 示例 | 处置 |
|---|---|---|
| 有效但不达标 | 正确测得OOM、质量下降、无加速 | 保留结果，拒绝候选或形成下一轮假设 |
| 测量无效 | 异步计时漏掉执行、样本错配、峰值窗口错误 | 保留原始记录并标记问题，修复后重测受影响指标 |
| 有效但不可直接比较/归因 | 模型、分辨率和输出预算同时改变 | 作为完整配置结果保留；若需单因素结论，补受控对照 |

有效性可以按指标判断：质量评分错误不必使独立且边界明确的耗时记录同时失效，但不能继续声称质量等价加速。未覆盖的类别、场景或负载属于结论范围限制，不能用“未发现问题”补足。

### 1.4.3 选择与停止

先检查正确性，再判断质量底线、延迟限制、失败率和每卡显存预算等硬约束。只在满足约束的候选中，按事先声明的目标选择更低成本或更高吞吐的配置；多个指标互有优劣时保留候选及取舍理由，不任意压成单一总分。

遇到数据泄漏、监督错误、样本错配、版本漂移或不能解释的明显质量变化，暂停受影响比较并修复。预算耗尽、收益饱和或无可行候选时允许结束实验并报告负结果，不以完成某项技术练习替代业务验收。

## 1.5 版本与增量采用

每轮保存所用指导/方案版本、具体契约取值、配置身份和原始结果。任务定义、评分协议、输入分布、硬件或执行路径变化时，先判断影响哪些指标，再重测这些部分。

历史记录按原契约解释；复用时明确条件是否一致、哪些证据缺失。新模板不能将历史缺项追记成“已测”，也不默认要求所有历史实验重跑。
