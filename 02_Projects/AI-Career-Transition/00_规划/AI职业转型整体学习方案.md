# 1 多模态 AI 职业转型学习方案

## 1.1 项目背景与隐私边界

本方案以知识库中已经存在的工程项目为背景，而不是从完全抽象的能力画像出发：

- DMS Model Training 与 EyeStatus 项目提供视觉感知、数据处理、模型训练、量化部署、后处理和端侧约束场景。
- Agent 原型、workflow、agent-trajectory 与知识库治理项目提供工具调用、状态、轨迹、证据链和异步处理场景。
- 已有项目中的 AI 辅助设计和实现只能作为实践材料，不能直接视为独立掌握证据。

上述内容只描述已授权项目的技术事实和可复用资产，不记录学历、雇主、任职时长，也不声明个人在这些项目中的任职关系或职责范围。默认每周投入约 10 至 12 小时；若投入下降，优先延长阶段而不是压缩验证。

路线以通用多模态任务和可复现实验形成“模型质量 + 推理部署 + 性能诊断 + 服务可靠性”的工程闭环。DMS/OMS提供真实约束与可授权复用的背景，Agent项目作为后续系统能力扩展。

## 1.2 职业定位与目标能力

主攻多模态模型推理与部署，定位于 ML Systems / AI Infra 的模型执行、性能与可靠性方向。以视觉任务和端侧约束为实践特色，通过一个完整VLM系统证明从任务质量到部署成本的工程判断。Agent runtime、可观测性与可靠性保留为第二方向，待主项目稳定交付后按求职需求选择。

目标能力围绕同一条交付链展开：

1. 解释LLM/VLM输入、视觉token、前向、prefill/decode与输出解析的数据流。
2. 建立可复现的质量基线、分组指标和错误分析，识别适配、精度或后端变化引入的退化。
3. 完成目标平台的模型加载、批量推理与服务部署，测清容量、延迟、吞吐和资源成本。
4. 从端到端时间线定位到框架、算子或数据移动问题，用受控干预和回归决定是否采纳优化。
5. 按质量缺口选择参数高效微调，并验证所用训练路径的更新、保存与恢复正确性。
6. 实现服务并发控制、观测、超时处理、版本回退与必要的恢复机制。
7. 独立解释、修改或排查关键模块，明确AI辅助部分和个人贡献边界。
8. 完成一个可用于求职讲解的多模态推理部署旗舰项目；第二个Agent项目按实际岗位需要启动。

CUDA/Triton算子、编译器与GPU微架构优化作为后续专业化选择。当前硬件基础以支持上述工程判断为深度边界，具体范围与验收见1.6.1。本定位接替旧多方向并列路线，原文与替代依据见 [[02_Projects/AI-Career-Transition/Current Maintenance Records/职业定位与实践优先级调整-2026-11-18]]。

## 1.3 优先级与范围控制

### 1.3.1 三层优先级

| 优先级 | 内容 | 范围规则 |
|---|---|---|
| Must | VLM数据流、输出合同、质量评测、单卡推理部署、性能诊断、基础服务可靠性与硬件基础 | 以主项目交付和独立验证验收 |
| Should | 有依据的LoRA、后端/精度对照、批处理与缓存、端云约束、多副本；计划内DDP教学实验 | 按问题和前置条件执行，候选部署验收自身使用路径 |
| Later | 高性能kernel、编译器、逐周期SASS调优、大规模训练集群、第二个Agent旗舰项目 | 主项目稳定交付后，按性能缺口、兴趣和岗位需求选择 |

硬件基础通过小例子和实际profile持续补齐；已完成的性能专题按停止条件收束，下一轮优化由明确目标缺口触发。

### 1.3.2 执行约束

- 同一时段只维护一个主项目；第二个旗舰项目在第一个项目形成稳定 benchmark 后再启动。
- 每两周只承诺一个可验证交付物，阅读和课程必须服务于该交付物。
- 优先使用最小可行模型和最小数据集验证链路，再决定是否微调、扩模型或引入新框架。
- 新增学习主题时必须同时删减或推迟一个低优先级主题。

### 1.3.3 每周节奏

默认每周投入 10 至 12 小时，但学习早期和项目阶段采用不同配比。

Phase 0 与 Phase 1 前半段按“教学骨架—主动重建—最小实现—复盘”分配：

- 2 至 3 小时：建立本周主题的最小教学骨架，先看定义、数据流、关键变量、边界和一个可运行或可观察例子。
- 2 小时：主动重建，闭卷画图、费曼复述、对比相邻概念和回答 1 至 3 个诊断题。
- 4 小时：最小实现、受控实验、基线运行或故障定位。
- 1 至 2 小时：根据诊断结果补最小缺口，更新阶段学习文档、代码复核和下周范围冻结。

形成 benchmark 草案后按“构建—评测—复盘”分配：

- 5 小时：当前阶段的模型或系统实现。
- 3 小时：benchmark、测试、失败样本与性能测量。
- 2 小时：补齐直接阻塞交付物的理论与源码阅读。
- 1 至 2 小时：闭卷复述、代码复核和下周范围冻结。

若每周只有 6 小时，学习早期保留核心机制、最小实现和复盘，推迟评测集扩充；形成 benchmark 草案后再保留实现、评测和复盘。始终暂停扩展阅读与第二技术栈。

### 1.3.4 主动学习使用规则

主动学习用于暴露和修补心智模型，不等同于复习，也不等同于连续考试。每个主题先判断知识覆盖状态，再选择教学与诊断比例：

| 覆盖状态 | 学习顺序 | 不应做什么 |
|---|---|---|
| 大面积缺失 | 先给最小教学骨架，再做主动重建和检查题 | 不要求凭空回答未知材料 |
| 局部混淆 | 用短诊断题定位最小缺口，再做微型补课 | 不把所有概念重新讲一遍 |
| 主干已通 | 用边界题、反例题和迁移题检查是否能应用 | 不停留在术语复述 |
| 准备交付 | 用实践、失败样本和可复现证据验证能力 | 不用对话正确替代运行证据 |

一次学习闭环默认按以下顺序进行：

```text
确认阶段边界
→ 建立阶段学习文档骨架与学习记录
→ 按骨架教学
→ 主动重建
→ 缺口诊断
→ 微型补课
→ 迁移或实践题
→ 诊断结果写入学习记录
→ 按缺口受控更新学习文档
→ 实践证据写入实践记录
→ 更新滚动检查点
```

教学骨架必须先回答五件事：

1. 这个概念或系统解决什么问题。
2. 输入、输出和中间状态是什么。
3. 关键模块如何连接，哪些变量控制结果。
4. 哪些边界条件会让结论失效。
5. 后续实践如何观察它是否真的工作。

诊断题只用于决定补什么、练什么和是否进入实践。除阶段关闭或明确复测外，不把诊断题包装成正式测试；对话中的 `working` 只表示当前问答范围内的可用理解，不替代代码、基线、样本、指标或失败分析。

阶段学习文档只承载稳定教学内容；个人回答、诊断结论、掌握状态、环境快照和当前下一步写入学习记录；真实配置、命令、原始输出、指标与失败分析写入实践记录。详细职责、更新边界和模板见 [[02_Projects/AI-Career-Transition/00_规划/学习文档维护规范]]。

## 1.4 Phase 0：能力诊断与范围冻结（第 1 至 2 周）

### 1.4.1 目标

建立真实能力基线，判断 LLM、Transformer、VLM、Agent 和评测分别处于什么理解层级，防止把“看过、让 AI 写过、运行过”误判为“独立掌握”。本阶段不建立正式 benchmark。

### 1.4.2 任务

- 不使用 AI，解释 token、embedding、next-token prediction、causal mask、logits、decoding、上下文窗口和 KV cache；不会的内容如实标记，不要求一次答对。
- 不使用 AI，解释 self-attention、cross-attention、ViT patch embedding 和 VLM projector，区分“能复述术语”和“能画出数据流”。
- 限时阅读或补全一段最小 LLM/Transformer 推理代码，用于判断代码理解、实现和调试起点；不以完成复杂模型为目标。
- 对现有 `agent_from_scratch` 做一次轻量代码审计，列出工具调用、状态、错误处理、测试和可观测性缺口，不在本阶段展开 Agent 重构。
- 从已有 DMS/OMS 项目中选择一个可公开描述、数据使用合规的场景，定义端侧快路径与云端语义路径的输入输出。
- 候选题目最多保留两个，只允许一个进入实现；另一个只保留一页 problem statement。
- 记录 3 至 5 个用于暴露认知缺口的诊断样例；这些样例不计为 benchmark，不用于宣称模型或方案效果。

### 1.4.3 退出条件

- 形成能力矩阵：`可独立实现 / 能解释但需参考 / 仅使用过 / 未学习`。
- 形成 LLM/VLM 前置缺口清单，并按“阻塞后续实践 / 可边做边补 / 暂不需要”分级。
- 形成一个主项目的一页式 problem statement，写清问题、非目标、数据边界、指标和两周内首个交付物。
- 能画出最小 LLM 推理数据流；若不能，则 Phase 1 首个交付物必须先补齐该闭环。
- 未完成基线测评前，不进入大规模框架学习。

## 1.5 Phase 1：LLM、Transformer、VLM 与评测基础（第 3 至 12 周）

### 1.5.1 阶段 A：LLM 最小机制闭环（第 3 至 5 周）

- tokenizer、token、embedding、causal language modeling 和 next-token prediction。
- attention、multi-head attention、位置编码、残差、归一化和 FFN。
- encoder、decoder、decoder-only 模型的数据流差异。
- logits、greedy decoding、temperature、top-k/top-p 和停止条件。
- 上下文窗口、KV cache、prompt 输入与模型参数知识的边界。
- 幻觉、无依据结论、引用证据、拒答和不确定性表达的基本机制。

实践任务：

1. 使用可观察的极小模型或最小代码，打通 `文本 → token → embedding → causal attention → logits → decoding → 文本`。
2. 独立实现并测试 scaled dot-product attention；根据 Phase 0 结果决定是否继续实现完整最小 Transformer block。
3. 固定输入，改变 temperature、top-p、最大输出长度和上下文，记录输出变化并解释原因。
4. 构造一个有证据和无证据的对照实验，观察模型何时应回答、引用或拒答。

### 1.5.2 阶段 B：评测基本功与练习集（第 6 至 8 周）

学习内容：

- 区分确定性任务、开放生成任务、检索/证据任务和工具执行任务。
- 区分 exact match、规则评分、语义评分、模型评分和人工评分的适用边界。
- 理解 gold answer、acceptable answer、evidence requirement、abstain、失败标签和评分一致性。
- 理解数据泄漏、样本重复、指标漂移以及“为了当前模型定制评分规则”的风险。

实践任务：

1. 从已冻结的 problem statement 中选择一个范围足够小、结果可以复核的子任务。
2. 构造 3 至 5 个评测练习样例，逐个写清输入、预期行为、可接受答案、证据要求、拒答条件和失败标签。
3. 由本人隔天重复评分一次；若同一样例评分不一致，先修订任务或 rubric，不扩充数据。
4. 跑一个最简单基线，目标是验证任务和评分是否可用，不宣称模型能力优劣。

本阶段产物称为“评测练习集”或 `seed cases`，不得称为真实 benchmark。

### 1.5.3 阶段 C：VLM 基线与 benchmark 草案（第 9 至 12 周）

学习与实践任务：

1. 学习 ViT、视觉 token、图像 encoder、projector 和语言模型连接方式。
2. 理解图像/视频采样、上下文长度、KV cache 和推理成本。
3. 运行一个开源小型 VLM，完成图像问答与批量推理。
4. 从公开、合成或明确授权的数据构造小型座舱多模态任务集；若使用外部数据，先按知识库规则建立来源记录。
5. 先完成 zero-shot 与 few-shot 基线；只有错误分类表明微调可能解决主要误差时，才进行一次参数高效微调。
6. 除总体指标外，至少按输入质量、场景难度和任务类型做分组评测。

只有同时满足以下条件，才把练习集升级为 benchmark 草案：

- 能解释模型的输入输出和至少三类主要失败模式。
- 每个 case 都有可复核的期望行为或证据边界。
- 评分规则经过至少一次重复评分检查。
- 已存在一个最简单基线和可复现命令。

### 1.5.4 交付物

- LLM 最小推理数据流说明、受控实验记录和必要的最小实现测试。
- 评测练习集、评分一致性记录和最简单基线。
- VLM 数据说明、基线配置、评测脚本和实验报告；若执行微调，再补充训练配置。
- 至少一份失败样本分类，不以平均准确率作为唯一结论。

### 1.5.5 退出条件

- 能独立解释 LLM 从文本输入到生成输出的数据流，并说明采样、上下文和证据约束的作用。
- 能独立画出并解释 VLM 从图像输入到文本输出的数据流。
- 能定位一次数据、显存、输出格式或评测错误，而不是只依赖 AI 修复。
- benchmark 草案包含 15 至 30 个可复现 case；先保证评分可复核和失败类型覆盖，不为满足数量下限填充低价值样本。
- 只有经过重复评分或第二评分者检查、主要失败标签基本稳定后，才冻结首版评分规则。
- 若执行微调，能说明其相对最简单基线的增益、代价和适用边界；若不执行，记录不微调的证据。

## 1.6 Phase 2：多模态推理与部署实践

本阶段围绕质量、可复现执行、服务观测与优化验证完成一个VLM系统。方法入口为[[02_Projects/AI-Career-Transition/00_规划/模型训练微调与部署的契约与测量方法]]；具体任务、配置与验收继续由[[02_Projects/AI-Career-Transition/00_规划/Qwen3.5-9B睁闭眼分类微调与部署实验方案]]承载，实际进度以全局检查点指向的实验记录为准。

保留9B综合工作包的模型角色、数据与任务合同。4090/4B是本轮性能诊断环境，其结果按模型和平台范围解释。既有Phase 1范围关闭有效；Phase 2-A保持active，能力完成度依实际验证逐项确认。

### 1.6.1 硬件基础补齐到什么程度

目标是能从“工作在哪里执行、数据何时到达、时间如何测量”解释性能现象，并选择下一项可区分原因的实验。先建立具体数据流，再用小例子观测，最后回到VLM的profile做迁移。

| 必学范围 | 最小实践与验收 |
|---|---|
| 执行模型：host/device、kernel、grid/block/thread、SM/warp；驻留、就绪、发射、执行 | 用向量加法画线程映射和数据移动；改变block配置，解释逻辑并行度与硬件驻留限制 |
| 存储模型：寄存器、shared memory、L1/L2、显存；容量、带宽、延迟与复用 | 计算tensor字节数；比较连续与跨步访问，说明数据量、访问方式与计时结果的关系 |
| GEMM基础：M/N/K、计算量、tile、合并访存、同步和软件流水 | 对比简单与分块矩阵乘，验证正确性并解释复用收益；修改一个tile或缓冲配置，记录资源与耗时取舍 |
| 可信测量：异步执行、同步、预热、CUDA event、profiler扰动；峰值显存与allocator | 对同一负载重复计时；说明端到端与单算子窗口、active/elapsed分母及采样比例 |
| 性能判读：occupancy、eligible warps、stall、计算/存储吞吐；prefill/decode差异 | 对已有profile写出观察、假设、证据与待验证项；独立解释新形状或batch下的预测与实测偏差 |

小实验以可读、可修改和正确测量为标准；高性能GEMM、bank映射细节、SASS逐周期调度与编译器代码生成留到专题阶段。验收采用独立解释、关键修改或故障定位，并保存运行证据。每轮主项目只搭配一个直接相关的基础小实验，硬件补齐与部署实践共同推进。

### 1.6.2 后续实践按什么顺序推进

当前优先级接续实验记录中已收束的prefill/vision性能专题，先补齐质量与部署证据。

| 顺序 | 主要问题与实践 | 交付及进入条件 |
|---|---|---|
| 1 | 修复输出合同，统一prompt、解析、坐标转换与评分，开展开发集回归 | 保留原始输出与失败分母，核对结构、同侧定位、四类状态及batch/后端差异 |
| 2 | 冻结执行配置与验证清单，建立正式质量baseline | 完整验证集结果、分组覆盖与错误分析；已有40图与32图继续作为开发诊断 |
| 3 | 建立可复现的单卡推理服务和负载基线 | 先做兼容性探测；候选验收覆盖质量、延迟分位数、吞吐、显存、失败率、版本与恢复/回退；生成服务按需记录首token和逐token延迟 |
| 4 | 按质量缺口选择输入/监督干预或LoRA，按性能缺口选择后端、batch、缓存、精度等对照 | 一次改变可解释变量，复评质量与资源成本；采用训练时完成更新和保存恢复检查 |
| 5 | 将有效优化接回服务，验证实际负载收益 | 固定可比输入及输出条件，记录性能和质量变化；按容量/吞吐需求推进多副本、故障恢复和扩展 |
| 6 | 有剩余性能缺口时深入GEMM或其他热点 | 先比较实现/配置，再用NCU/SASS解释有效加速，最后依据证据决定定制kernel |

上述顺序是主交付优先级。服务兼容性探测和小型训练机制实验可按前提提前进行；质量未达标的模型可作为工程基线，正式候选仍须满足质量合同。LoRA、教师蒸馏、量化和多副本的采纳依据沿用独立方案。双卡LoRA DDP保留计划内教学实验，安排在单卡更新与恢复基线之后；未采用DDP的部署路径可独立验收。

### 1.6.3 优化与学习怎样收束

Track A负责质量与候选验收，Track B负责机制学习与工程证据。每轮优化交付“可复现现象—原因假设—受控改动—收益与回归—采纳或停止决定”，以实际耗时、质量和服务收益判定效果。已有GEMM已交错组织搬运与计算，后续专题考察流水、tile与资源分配的组合，具体改动由对照证据决定。

当前prefill/vision专题已提供阶段决策依据，未量化问题保留，后续由性能目标缺口或显著负载变化触发重开。硬件基础学习继续进行，现有kernel深挖维持停止点。本节接替的旧工作包排序及继续深挖安排保存在 [[02_Projects/AI-Career-Transition/Current Maintenance Records/职业定位与实践优先级调整-2026-11-18]]；实验历史和已有能力验证边界保持原样。

## 1.9 阶段门禁与验证规则

阶段切换以退出条件为准，月份作为滚动估计，不作为能力完成证据。连续两次复盘未达到退出条件时，必须缩小任务或降低模型复杂度，不得直接把未完成项滚入下一阶段。

六个强制门禁：

1. 不能解释 LLM 的最小推理数据流，不进入 VLM benchmark 采集。
2. 没有可复核任务定义和评分规则，不把诊断样例或评测练习集称为 benchmark。
3. 面向效果改进的微调和架构扩展必须先有稳定 benchmark。小型教学实验可先验证更新语义与资源机制，但不得据此宣称任务收益；实际适配仍按 Phase 2-B/2-C 门禁执行。
4. 没有最简单基线，不声明新模型或新架构有效。
5. 没有失败分类，不优化 prompt、路由或数据。
6. 没有独立验证，不把 AI 辅助产物计入能力完成度。

| 层级 | 用途 | 最低要求 | 允许得出的结论 |

~~~~text
    -> 语义结论与不确定性
    -> Agent 权限和状态门禁
    -> 提醒、解释或模拟车控动作
```

### 1.6.5 必做对照

对以下输入策略进行质量、成本和延迟比较：

- 原始图像或抽帧图像。
- ROI 图像。
- 端侧感知结构化结果。
- 图像与结构化状态组合。
- 本地摘要后再调用云端模型。

云端 API 可以作为主路径之一，但必须实现：

- timeout 和 retry 上限。
- 弱网/断网降级。
- 敏感数据最小化。
- 数据保留周期和脱敏策略。
- 请求和模型版本记录。
- 成本与延迟统计。
- 无法获得可靠结论时的 abstain 行为。

### 1.6.6 退出条件

- benchmark 扩展到至少 50 个真实、合成或可复现 case，并包含边界与拒答样本。
- 报告端侧路径、云端路径和混合路径的质量、延迟、成本及失败模式。
- 路由策略必须相对最简单基线带来可解释收益；否则回退到更简单架构。
- 不把“Demo 能回答”当作任务完成。
~~~~

````markdown
### 1.6.3 多卡实验的边界

最小双卡 DDP 用于验证并行语义与测量方法，无需单独开一个覆盖全部并行技术的大项目。同节点双卡即可作为起点，不要求两节点。硬件不满足时，记录为 deferred_by_resource；可继续 2-B，不能声称多卡实践完成。CPU 多进程或单 GPU 多进程只能辅助验证逻辑，不能作为跨 GPU 性能证据。

### 1.6.4 适配、蒸馏与任务选择

2-B 只选一个主任务，例如公开图像的可核验问答或结构化信息抽取；这些是候选类型，不代表已选数据集。任务合同先写输入可见信息、输出结构、允许答案、证据不足处理和错误分组，再选模型与数据。进入新子阶段前建立对应教学骨架和学习记录，不预建一套空项目。
````
