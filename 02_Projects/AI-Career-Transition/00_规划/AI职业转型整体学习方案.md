# 1 多模态 AI 职业转型学习方案

## 1.1 项目背景与隐私边界

本方案以知识库中已经存在的工程项目为背景，而不是从完全抽象的能力画像出发：

- DMS Model Training 与 EyeStatus 项目提供视觉感知、数据处理、模型训练、量化部署、后处理和端侧约束场景。
- Agent 原型、workflow、agent-trajectory 与知识库治理项目提供工具调用、状态、轨迹、证据链和异步处理场景。
- 已有项目中的 AI 辅助设计和实现只能作为实践材料，不能直接视为独立掌握证据。

上述内容只描述已授权项目的技术事实和可复用资产，不记录学历、雇主、任职时长，也不声明个人在这些项目中的任职关系或职责范围。默认每周投入约 10 至 12 小时；若投入下降，优先延长阶段而不是压缩验证。

路线以通用多模态任务和可复现实验形成“多模态模型 + 评测 + Agent runtime + ML Systems”的工程闭环。已有 DMS/OMS 与 Agent 项目可按授权复用，但不预设后续学习项目或业务场景。

## 1.2 一年后的目标能力

完成本方案后，应能独立完成以下闭环：

1. 解释文本从 tokenization、embedding、causal attention、logits 到 decoding 的 LLM 推理数据流，以及上下文、采样和证据约束如何影响输出。
2. 解释 Transformer、ViT 和 VLM 的核心结构，以及图像 token、projector 与语言模型之间的数据流。
3. 完成一个开源 VLM 的推理、领域数据构造、参数高效微调和分组评测。
4. 设计端侧感知、结构化状态、本地小模型和云端大模型之间的路由。
5. 构建具备结构化工具调用、状态持久化、重试、幂等、降级和审计证据的 Agent。
6. 建立真实 benchmark，报告任务成功率、幻觉/无依据结论、延迟、成本和人工复核时间，并说明评分边界与一致性。
7. 对 AI 辅助生成的关键模块进行独立解释、修改、测试和故障定位。
8. 形成两个能够用于求职的旗舰项目，并能用证据说明独立贡献边界、失败模式和系统取舍。

## 1.3 优先级与范围控制

### 1.3.1 三层优先级

| 优先级 | 内容 | 范围规则 |
|---|---|---|
| Must | LLM/Transformer/VLM 数据流、评测基本原理、结构化 Agent、推理与可观测性 | 未通过阶段门禁不得跳过 |
| Should | 参数高效微调、端云路由、性能与成本优化 | 只在基线和 benchmark 稳定后进入 |
| Later | 基础模型预训练、复杂多 Agent 编排、大规模训练平台 | 不纳入前 9 个月主线 |

### 1.3.2 执行约束

- 同一时段只维护一个主项目；第二个旗舰项目在第一个项目形成稳定 benchmark 后再启动。
- 每两周只承诺一个可验证交付物，阅读和课程必须服务于该交付物。
- 优先使用最小可行模型和最小数据集验证链路，再决定是否微调、扩模型或引入新框架。
- 新增学习主题时必须同时删减或推迟一个低优先级主题。

### 1.3.3 每周节奏

默认每周投入 10 至 12 小时，但学习早期和项目阶段采用不同配比。

Phase 0 与 Phase 1 前半段按“教学骨架—主动重建—最小实现—复盘”分配：

- 2 至 3 小时：建立本周主题的最小教学骨架，先看定义、数据流、关键变量、边界和一个可运行或可观察例子。
- 2 小时：主动重建，闭卷画图、费曼复述、对比相邻概念和回答 1 至 3 个诊断题。
- 4 小时：最小实现、受控实验、基线运行或故障定位。
- 1 至 2 小时：根据诊断结果补最小缺口，更新阶段学习文档、代码复核和下周范围冻结。

形成 benchmark 草案后按“构建—评测—复盘”分配：

- 5 小时：当前阶段的模型或系统实现。
- 3 小时：benchmark、测试、失败样本与性能测量。
- 2 小时：补齐直接阻塞交付物的理论与源码阅读。
- 1 至 2 小时：闭卷复述、代码复核和下周范围冻结。

若每周只有 6 小时，学习早期保留核心机制、最小实现和复盘，推迟评测集扩充；形成 benchmark 草案后再保留实现、评测和复盘。始终暂停扩展阅读与第二技术栈。

### 1.3.4 主动学习使用规则

主动学习用于暴露和修补心智模型，不等同于复习，也不等同于连续考试。每个主题先判断知识覆盖状态，再选择教学与诊断比例：

| 覆盖状态 | 学习顺序 | 不应做什么 |
|---|---|---|
| 大面积缺失 | 先给最小教学骨架，再做主动重建和检查题 | 不要求凭空回答未知材料 |
| 局部混淆 | 用短诊断题定位最小缺口，再做微型补课 | 不把所有概念重新讲一遍 |
| 主干已通 | 用边界题、反例题和迁移题检查是否能应用 | 不停留在术语复述 |
| 准备交付 | 用实践、失败样本和可复现证据验证能力 | 不用对话正确替代运行证据 |

一次学习闭环默认按以下顺序进行：

```text
确认阶段边界
→ 建立阶段学习文档骨架与学习记录
→ 按骨架教学
→ 主动重建
→ 缺口诊断
→ 微型补课
→ 迁移或实践题
→ 诊断结果写入学习记录
→ 按缺口受控更新学习文档
→ 实践证据写入实践记录
→ 更新滚动检查点
```

教学骨架必须先回答五件事：

1. 这个概念或系统解决什么问题。
2. 输入、输出和中间状态是什么。
3. 关键模块如何连接，哪些变量控制结果。
4. 哪些边界条件会让结论失效。
5. 后续实践如何观察它是否真的工作。

诊断题只用于决定补什么、练什么和是否进入实践。除阶段关闭或明确复测外，不把诊断题包装成正式测试；对话中的 `working` 只表示当前问答范围内的可用理解，不替代代码、基线、样本、指标或失败分析。

阶段学习文档只承载稳定教学内容；个人回答、诊断结论、掌握状态、环境快照和当前下一步写入学习记录；真实配置、命令、原始输出、指标与失败分析写入实践记录。详细职责、更新边界和模板见 [[02_Projects/AI-Career-Transition/00_规划/学习文档维护规范]]。

## 1.4 Phase 0：能力诊断与范围冻结（第 1 至 2 周）

### 1.4.1 目标

建立真实能力基线，判断 LLM、Transformer、VLM、Agent 和评测分别处于什么理解层级，防止把“看过、让 AI 写过、运行过”误判为“独立掌握”。本阶段不建立正式 benchmark。

### 1.4.2 任务

- 不使用 AI，解释 token、embedding、next-token prediction、causal mask、logits、decoding、上下文窗口和 KV cache；不会的内容如实标记，不要求一次答对。
- 不使用 AI，解释 self-attention、cross-attention、ViT patch embedding 和 VLM projector，区分“能复述术语”和“能画出数据流”。
- 限时阅读或补全一段最小 LLM/Transformer 推理代码，用于判断代码理解、实现和调试起点；不以完成复杂模型为目标。
- 对现有 `agent_from_scratch` 做一次轻量代码审计，列出工具调用、状态、错误处理、测试和可观测性缺口，不在本阶段展开 Agent 重构。
- 从已有 DMS/OMS 项目中选择一个可公开描述、数据使用合规的场景，定义端侧快路径与云端语义路径的输入输出。
- 候选题目最多保留两个，只允许一个进入实现；另一个只保留一页 problem statement。
- 记录 3 至 5 个用于暴露认知缺口的诊断样例；这些样例不计为 benchmark，不用于宣称模型或方案效果。

### 1.4.3 退出条件

- 形成能力矩阵：`可独立实现 / 能解释但需参考 / 仅使用过 / 未学习`。
- 形成 LLM/VLM 前置缺口清单，并按“阻塞后续实践 / 可边做边补 / 暂不需要”分级。
- 形成一个主项目的一页式 problem statement，写清问题、非目标、数据边界、指标和两周内首个交付物。
- 能画出最小 LLM 推理数据流；若不能，则 Phase 1 首个交付物必须先补齐该闭环。
- 未完成基线测评前，不进入大规模框架学习。

## 1.5 Phase 1：LLM、Transformer、VLM 与评测基础（第 3 至 12 周）

### 1.5.1 阶段 A：LLM 最小机制闭环（第 3 至 5 周）

- tokenizer、token、embedding、causal language modeling 和 next-token prediction。
- attention、multi-head attention、位置编码、残差、归一化和 FFN。
- encoder、decoder、decoder-only 模型的数据流差异。
- logits、greedy decoding、temperature、top-k/top-p 和停止条件。
- 上下文窗口、KV cache、prompt 输入与模型参数知识的边界。
- 幻觉、无依据结论、引用证据、拒答和不确定性表达的基本机制。

实践任务：

1. 使用可观察的极小模型或最小代码，打通 `文本 → token → embedding → causal attention → logits → decoding → 文本`。
2. 独立实现并测试 scaled dot-product attention；根据 Phase 0 结果决定是否继续实现完整最小 Transformer block。
3. 固定输入，改变 temperature、top-p、最大输出长度和上下文，记录输出变化并解释原因。
4. 构造一个有证据和无证据的对照实验，观察模型何时应回答、引用或拒答。

### 1.5.2 阶段 B：评测基本功与练习集（第 6 至 8 周）

学习内容：

- 区分确定性任务、开放生成任务、检索/证据任务和工具执行任务。
- 区分 exact match、规则评分、语义评分、模型评分和人工评分的适用边界。
- 理解 gold answer、acceptable answer、evidence requirement、abstain、失败标签和评分一致性。
- 理解数据泄漏、样本重复、指标漂移以及“为了当前模型定制评分规则”的风险。

实践任务：

1. 从已冻结的 problem statement 中选择一个范围足够小、结果可以复核的子任务。
2. 构造 3 至 5 个评测练习样例，逐个写清输入、预期行为、可接受答案、证据要求、拒答条件和失败标签。
3. 由本人隔天重复评分一次；若同一样例评分不一致，先修订任务或 rubric，不扩充数据。
4. 跑一个最简单基线，目标是验证任务和评分是否可用，不宣称模型能力优劣。

本阶段产物称为“评测练习集”或 `seed cases`，不得称为真实 benchmark。

### 1.5.3 阶段 C：VLM 基线与 benchmark 草案（第 9 至 12 周）

学习与实践任务：

1. 学习 ViT、视觉 token、图像 encoder、projector 和语言模型连接方式。
2. 理解图像/视频采样、上下文长度、KV cache 和推理成本。
3. 运行一个开源小型 VLM，完成图像问答与批量推理。
4. 从公开、合成或明确授权的数据构造小型座舱多模态任务集；若使用外部数据，先按知识库规则建立来源记录。
5. 先完成 zero-shot 与 few-shot 基线；只有错误分类表明微调可能解决主要误差时，才进行一次参数高效微调。
6. 除总体指标外，至少按输入质量、场景难度和任务类型做分组评测。

只有同时满足以下条件，才把练习集升级为 benchmark 草案：

- 能解释模型的输入输出和至少三类主要失败模式。
- 每个 case 都有可复核的期望行为或证据边界。
- 评分规则经过至少一次重复评分检查。
- 已存在一个最简单基线和可复现命令。

### 1.5.4 交付物

- LLM 最小推理数据流说明、受控实验记录和必要的最小实现测试。
- 评测练习集、评分一致性记录和最简单基线。
- VLM 数据说明、基线配置、评测脚本和实验报告；若执行微调，再补充训练配置。
- 至少一份失败样本分类，不以平均准确率作为唯一结论。

### 1.5.5 退出条件

- 能独立解释 LLM 从文本输入到生成输出的数据流，并说明采样、上下文和证据约束的作用。
- 能独立画出并解释 VLM 从图像输入到文本输出的数据流。
- 能定位一次数据、显存、输出格式或评测错误，而不是只依赖 AI 修复。
- benchmark 草案包含 15 至 30 个可复现 case；先保证评分可复核和失败类型覆盖，不为满足数量下限填充低价值样本。
- 只有经过重复评分或第二评分者检查、主要失败标签基本稳定后，才冻结首版评分规则。
- 若执行微调，能说明其相对最简单基线的增益、代价和适用边界；若不执行，记录不微调的证据。

## 1.7 Phase 3：Agent Systems 与 ML Systems 加固（第 7 至 9 个月）

### 1.7.1 Agent 能力

- 使用原生结构化工具调用和参数 schema，替代正则解析工具标签。
- 显式定义任务状态、工具状态、失败状态和终止状态。
- 实现 timeout、有限重试、幂等键、断点恢复和审计日志。
- 区分原始事实、模型推断、不确定性和最终动作。
- 对高风险动作增加权限、确认或 dry-run 门禁。

### 1.7.2 ML Systems 能力

- 模型服务、请求队列、批处理、缓存和并发控制。
- 端云模型路由、fallback 和 circuit breaker。
- tracing、metrics、结构化日志和版本追踪。
- 模型、prompt、tool 和数据版本的回归测试。

### 1.6.2 当前双周交付：单卡训练与 profiling 基线

首个交付是可复现的单卡实验报告，而非再次通读全部 5D 内容。运行前先完成一页实验合同：环境与模型版本、数据与有效 token、训练参数、精度、micro batch、累积次数、测量窗口、预算、预期现象和停止条件。

用户报告设备为“pro5000”；完整型号、显存、卡数和软件环境尚待核实，不据简称推断硬件能力。首先核对环境，再选择能留下测量余量的小模型。复用已有训练实现与 checkpoint 经验，只补本轮资源观测缺口。

最小实验依次完成：

1. 核对输入、labels、loss mask 与可训练参数，确认更新发生在预期位置。
2. 区分首次 optimizer 状态建立、warmup 与稳定测量窗口；GPU 计算计时和包含数据准备的端到端计时分别记录。
3. 固定有效 global batch，先只改变 micro batch 与累积组合；比较完整 optimizer step、样本/有效 token 吞吐及峰值 allocated/reserved，解释差异。
4. 从观测选一个瓶颈做受控验证，例如预处理或 activation；不同时开启多项优化。
5. 保存命令、配置、原始测量、失败分析与独立解释。只生成代码或只观察利用率不算完成。

### 1.6.3 多卡实验的边界

最小双卡 DDP 用于验证并行语义与测量方法，无需单独开一个覆盖全部并行技术的大项目。同节点双卡即可作为起点，不要求两节点。硬件不满足时，记录为 deferred_by_resource；可继续 2-B，不能声称多卡实践完成。CPU 多进程或单 GPU 多进程只能辅助验证逻辑，不能作为跨 GPU 性能证据。

TP、PP、CP、EP 保留机制理解与选型能力；只有任务确有容量、长上下文、流水线或专家路由需求时再展开相应运行。ZeRO/FSDP 也按实际状态显存压力选择，不为凑齐技术栈强行组合。完整多机训练与 kernel 开发继续后置，不安排租卡或购买。

### 1.6.4 适配、蒸馏与任务选择

2-B 只选一个主任务，例如公开图像的可核验问答或结构化信息抽取；这些是候选类型，不代表已选数据集。任务合同先写输入可见信息、输出结构、允许答案、证据不足处理和错误分组，再选模型与数据。进入新子阶段前建立对应教学骨架和学习记录，不预建一套空项目。

LoRA 是参数更新方式，蒸馏是利用教师信号训练学生的目标与数据设计，两者可以组合，也不互相替代。先用 LoRA 建立可控适配闭环，再判断是否值得做教师—学生实验。若输入证据丢失或标注不一致，先修复相应环节；教学性的小实验不作为业务效果证明。

蒸馏实际训练需同时明确：学生资源目标、教师在目标任务上经独立评测的优势、教师信号可获取且获准使用、过滤与抽检方法、独立留出集及计算预算。先选一种信号完成对照，不要求同时实现输出、logits 和特征蒸馏。比较同一学生在无蒸馏与有蒸馏条件下的表现，说明额外数据和计算差异；教师无稳定优势或成本目标不成立时，保留分析并推迟训练。

### 1.6.5 阶段退出与范围控制

Phase 2 完成应能串起“任务与数据 → 基线与错误 → 受控适配 → 资源测量 → 推理回归”，并提供独立解释与故障定位证据。运行顺利或指标提升不是唯一验收条件，可复现的负结果与合理停止决定同样有价值。

每两周只推进一个交付物。以最小 LLM 实验复用训练基础，避免先做完整 LLM 多卡工程再重复一套 VLM 工程。推迟完整 5D 实装、固定车载架构、强制端云对照与大规模平台；它们不占用当前主线预算。条件分支须保留缺失证据，不升级为完成；主线实际适配前仍须具备冻结评测合同。
