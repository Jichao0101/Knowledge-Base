# 1 knowledge-base-structure-builder 子项目总览

## 1.1 子项目定位

`knowledge-base-structure-builder` 是面向 Markdown 知识库结构化、规范化、写入治理和 indexing-prep 的 authoring skill。它把知识库维护成可稳定召回、可追溯、可执行写前门禁的形态，但不拥有自然语言 Query Planning、历史上下文召回或相关性排序的实现权威。

## 1.2 核心职责

- Bootstrap、Migration、Maintenance 和 current lifecycle。
- 知识、项目、候选、来源和归档的分层放置。
- 入口、overview、current 文档组、链接和 supersession 维护。
- 生命周期与门禁 frontmatter 的 schema、lint 和兼容解释。
- retrieval header / Retrieval Summary 的 authoring 规范、完整性检查和 patch proposal。
- 可重建 metadata、trace/indexing projection 的准备能力。
- 基于目标风险、授权、变更类别和 hash 的分层写入门禁；完整 trace/preflight 只用于白名单高风险变更。
- 写后 lint、入口同步和结构审计。

## 1.3 明确不负责

- 从自然语言变更意图生成检索词和检索面。
- 同义词、旧名称、中英文别名和问题症状扩展。
- 多轮历史检索、结果排序和召回充分性判断。
- 把没有检索命中解释为不存在历史约束。
- 为弱结构或其他版本知识库提供通用 RAG 能力。
- 将目标仓库 `AGENTS.md` 打包进 skill 或与 skill 版本绑定。

## 1.4 与 retriever 的协作契约

问题分析阶段需要历史影响分析时，Retriever 可生成 `retrieval_package`，把“这个问题可能属于哪里”的原文证据、候选来源和召回限制传给 Structure Builder。Retriever 不决定写回位置；Structure Builder 仍拥有落点判断、写入门禁、结构同步和最终写入边界。

Structure Builder 可以消费 `retrieval_package`，但不复制其查询和排序实现。Structure Builder 只验证：

1. 检索是否限定在本次授权范围。
2. package 引用的候选来源是否仍可读。
3. `source_sections_read` 是否来自原始 Markdown。
4. `recall_limitations` 是否足以暴露检索边界。
5. 是否存在候选 active constraint、历史修复或 supersession 冲突需要进一步读取和判断。
6. 当前 change policy 应返回 `allow`、`manual_review` 还是 `blocked`。

Retriever 的低置信度、无结果或未解决歧义不得被 Builder 自动解释为安全。

## 1.5 风险分级门禁

| 变更 | 历史检索要求 | 写入门禁 |
|---|---|---|
| 普通 Inbox 新建 | 无或轻量 | 授权和落点检查 |
| Retrieval Summary proposal | 无 | report-only，不跑 trace-index/preflight/hash-check |
| Retrieval Summary approved append | 局部 | `minimal-apply-check`，只做授权、policy、目标 hash 和完整 preflight 升级判断 |
| normal 文档追加且不改变结论 | 局部 | 最小 apply check |
| 项目设计或 current 结构性修改 | 完整 | trace-index、preflight、hash-check、原文读取；仅在语义冲突、召回不足或高风险字段变化时人工复核 |
| guarded、critical 目标上的低风险追加 | 局部 | 目标类型只作为谨慎信号；无语义冲突、无高风险字段变化时不因路径级保护要求确认 |
| supersede、delete、move、promote | 完整 | 关系、证据和双向 supersession fail-closed |

门禁保持确定、窄接口和可审计，不在 gate 内实现检索策略。`current`、`guarded`、`critical`、`verified` 和入口文件本身不再直接触发 `manual_review`；只有发现具体历史修复、约束、决策或 supersession 冲突，检索/原文覆盖不足，高风险字段变化，或执行替代、删除、移动、提升时，才要求复核或阻止。

## 1.6 文档三层契约

### 1.6.1 Frontmatter

只保存门禁和生命周期字段：`status`、`evidence_level`、`evidence_refs`、`review_after`、`supersedes`、`superseded_by`、`protection_level`、`change_policy`。

### 1.6.2 Retrieval header

正文中的稳定检索锚点可包含 topic、component/symbol、alias/previous name、symptom/failure mode、affected path、constraint 和 related decision。它只增强召回，不替代正文事实，不允许关键词堆砌。

### 1.6.3 正文

保存完整解释、背景、设计或修复过程、适用边界和验证证据。Retrieval header 与正文冲突时，以正文及其可读取证据为准。

## 1.7 AGENTS.md 边界

目标仓库 `AGENTS.md` 是本地政策文件。Skill 只发现、读取并执行它，不携带权威模板，不自动创建或覆盖它，也不要求它与 skill 版本同步。运行报告可记录 policy path 和 hash，但该记录只用于证明本次运行采用了哪份政策。

## 1.10 验收标准

- 自动化无门禁或高风险直接改写 verified、guarded、critical 或 active-constraint 文档的次数为 0；低风险追加必须先通过对应 apply check。
- append-only 历史内容不被自动改写或删除。
- 结论替代具备双向 supersession、原因和可读取证据。
- policy、目标或 Builder 已纳入门禁的来源 hash 变化会使 preflight 失效。
- 删除缓存后能够从授权范围内的 Markdown 重建派生物。
- `AGENTS.md` 不作为 skill 资产，也不由 skill 默认创建或覆盖。
- Builder 不包含 Query Planning、同义词扩展或自然语言相关性排序的第二实现；只保留写前门禁所需的确定性候选复读和风险检查。

## 1.11 Retrieval Summary 与 Proposal

Builder 通过 Retrieval Summary / Retrieval Anchors 支持原始历史记录的可检索性增强。该能力只属于 authoring 和 lint，不承担自然语言 Query Planning 或相关性排序。

规则：

- fix / decision / validation / incident 记录应有短小的 Retrieval Summary 或 Retrieval Anchors section。
- Summary 中的 topic、component、symptoms、affected_paths、symbols、constraints、validation 和 aliases 必须能被正文、frontmatter 或 evidence refs 支撑。
- 不得关键词堆砌，不得把 summary 当作事实源替代正文。
- 对缺少 summary 的记录，Builder 生成 report-only patch proposal；verified、guarded、critical 或 current 文档不得被自动改写。
- proposal report 写入 `reports/kb/retrieval-summary-proposals/`，默认只保留最新 3 条。
- proposal 阶段不跑 trace-index、preflight 或 hash-check；人工确认后的 Markdown apply 才执行 `minimal-apply-check`。
- 若 apply 属于 current 结构性更新、正式知识提升、结论替代、supersession、delete/move/promote 或 metadata/status/evidence-level 变更，则升级到完整 preflight；current/guarded/critical 目标类型本身不再是升级或确认理由。

## 1.12 Lint 修复与报告保留

Lint 修复应按风险和确定性分层，不应把所有 finding 当成同等优先级：

1. 先修 `error`：缺失 wikilink target、缺失 supersession target、违反 recoverability 硬约束。
2. 再批量规划 `warning`：正式知识元数据缺失应按主题分批补齐，不在一次 Builder 调用中大面积改写正文。
3. 最后处理 `info`：孤立入链提示只作为导航改善候选，不得为了消除 info 机械添加无意义链接。

Lint report 是可重建派生产物，不是事实源。Builder 默认 timestamped reports 每类最多保留最新 3 条，避免 `reports/kb/` 只增不减；如果某份历史 report 已被项目记录显式引用为验证证据，则不得静默删除，必须先确认引用记录和 hash。

Lint 修复的推荐顺序：

- 对 `KB-LINT-002`，优先确认目标文件是否应恢复、改链到归档/现行路径，或移除失效图片引用。
- 对 `KB-LINT-006`，优先恢复或修正 supersession 目标；不得静默删除替代关系。
- 对 `KB-LINT-008`，若没有独立 recoverability verification，应移除或降级 `single_pass_recoverable: true`。
- 对 `KB-LINT-005`，按主题补最小 metadata，不批量改写正式知识正文。
- 对 `KB-LINT-003`，只在入口导航确有价值时补链接。
