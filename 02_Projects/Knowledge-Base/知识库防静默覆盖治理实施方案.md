# 1 知识库防静默覆盖治理实施方案

## 1.1 目标

本方案的唯一主目标是：

> 防止已有修复、约束和当前事实源在后续写入中被静默覆盖，并保证任何高风险写入都能追溯到相关 Markdown 原文和验证证据。

全文检索、向量检索、知识图谱和自动研究只可能是后续召回手段，不是本项目的目标。

## 1.2 基本不变量

1. 中文 Markdown 是唯一事实源。
2. Index、lint report 和 preflight report 都是可删除、可重建的派生物。
3. 自动化不得绕过 [[AGENTS]]。
4. 写入门禁必须发生在首次修改之前，写后 lint 不能替代写前门禁。
5. Traceability Index 只召回候选，事实判断必须读取命中的 Markdown 原文。
6. 自动化不得直接修改 verified、guarded、critical 或包含 active constraints 的 current 文档。
7. 外部信息不得自动提升到 `01_Knowledge`，会话结晶化候选默认进入 `03_Inbox/Candidates/`。

# 2 四层治理架构

Markdown 是四层治理共同依赖的事实载体。

| 层 | 责任 | 不负责 |
|---|---|---|
| Policy Layer | `AGENTS.md` 定义目录授权、写入分层、提升条件、自动化禁区和门禁触发条件 | lint 算法、索引实现、CLI 细节 |
| Workflow Layer | knowledge-base skill 执行模式诊断、placement、current lifecycle、preflight 调用和写后入口同步 | 自行覆盖仓库政策、保存第二事实源 |
| Pre-write Gate Layer | 在修改前完成召回、原文读取、影响分析和 `allow/manual_review/blocked` 决策 | 只凭索引摘要判断事实、以写后检查替代门禁 |
| Derived Tool Layer | metadata extractor、Traceability Index、lint、metadata index 和可选搜索 | 自动改写事实源、自动关闭冲突 |

权威优先级为：

1. `AGENTS.md`。
2. 项目或模块 `overview_current` 及其列出的当前事实源。
3. knowledge-base skill 的通用流程。
4. 派生工具的默认行为。

# 3 生命周期 Schema v2

## 3.1 显式字段

```yaml
status: draft | active | verified | stale | superseded | archived
evidence_level: unsourced | single_source | corroborated | runtime_verified
verified_at:
review_after:
supersedes: []
superseded_by: []
protection_level: normal | guarded | critical
```

- `status` 表达知识生命周期。
- `evidence_level` 表达证据成熟度，不表达概率。
- `protection_level` 表达修改风险。
- 本阶段不引入 claim-level 浮点 confidence。

## 3.2 历史文档缺省解释

工具必须区分 `declared`、`effective` 和 `value_origin`，不得把推导值回写成已声明事实。

| 缺失字段 | effective 默认值 |
|---|---|
| `status` | `legacy_unknown` |
| `evidence_level` | `unsourced` |
| `verified_at` | `unknown` |
| `review_after` | `unknown`，不得据此直接判定 stale |
| `supersedes` / `superseded_by` | `[]`，只表示未声明 |
| active constraints | `unknown`；current 写入进入人工审查 |

路径保护缺省：

| 路径或类型 | effective protection |
|---|---|
| `*_current.md` | `guarded` |
| `01_Knowledge/` | `guarded` |
| fixes / decisions / validation records | `guarded` |
| `04_Sources/` 原始证据 | `guarded` |
| maintenance records | `normal`，且只作为弱信号 |
| `03_Inbox/` | `normal` |
| `90_Archive/` | `guarded`，禁止自动删除或改写 |

示例派生结果：

```yaml
declared:
  status: null
  protection_level: null
effective:
  status: legacy_unknown
  evidence_level: unsourced
  protection_level: guarded
  constraint_state: unknown
value_origin:
  status: default
  evidence_level: default
  protection_level: path_policy
  constraint_state: default
```

# 4 Traceability 与写前门禁

## 4.1 信号等级

| 等级 | 记录类型 | 门禁作用 |
|---|---|---|
| strong | current、verified knowledge、fixes、decisions、最终 incident 结论、validation records、active constraints | 可触发 `manual_review` 或 `blocked` |
| medium | source cards、已审核设计、active 但未 verified 的项目记录、supersession 关系 | 读取原文后参与影响判断 |
| weak | maintenance records、session summaries、run logs、临时调查、superseded 实验路径 | 只提高召回或提供追踪线索，不能独立形成约束或阻断写入 |

Traceability 元数据应包含：

```yaml
record_type: fix | decision | validation | incident | maintenance | current
project:
module:
affected_paths: []
symptoms: []
constraints: []
evidence_refs: []
supersedes: []
signal_strength: strong | medium | weak
authority_status: authoritative | supporting | historical | superseded
status:
source_document:
recorded_at:
```

maintenance records 若命中，只能作为弱信号；若其链接到 fix、decision 或 validation，必须继续读取对应强信号原文。

## 4.2 Preflight 流程

1. 根据拟修改路径、项目、模块、标题和 aliases 确定检索范围。
2. 用最小 Metadata 和 Traceability Index 召回候选。
3. 读取命中的 Markdown 原文，而不是使用索引摘要作为事实依据。
4. 读取相应 current 入口和 active constraints。
5. 形成可能被覆盖的修复、受影响文件、必须保持的约束和必需验证。
6. 在首次文件修改前输出门禁决策。
7. 写入前重新核验关键原文和目标文件哈希；发生变化则 preflight 失效。

## 4.3 原文读取证据

```yaml
source_documents_read:
  - path: 02_Projects/DMS/04_Tracking/tracking_spec_current.md
    reason: 命中 affected_paths 和 active constraint
    matched_terms:
      - driver-bound
      - body evidence
    sections_read:
      - heading: "Body evidence constraints"
        line_start: 82
        line_end: 116
        section_hash: sha256:...
    document_hash: sha256:...
    status: verified
    protection_level: guarded
    read_at: 2026-06-22T14:30:00+08:00
```

完整 preflight report 至少包含：

```yaml
preflight_snapshot:
  generated_at:
  repository_revision:
  target_files: []
  source_hashes_valid: true
proposed_targets: []
matched_records: []
source_documents_read: []
active_constraints: []
potentially_overwritten_fixes: []
required_validations: []
authorization_gaps: []
gate_decision: allow | manual_review | blocked
```

## 4.4 Current 写入规则

| Current 情况 | 允许行为 |
|---|---|
| draft/active + normal + 无 active constraints | preflight 为 `allow` 后可以写入 |
| verified | 只能自动生成 proposal、patch draft 或 candidate summary |
| guarded | 只能自动生成 proposal 或 patch draft，人工确认后写入 |
| critical | 必须额外生成影响分析和验证计划 |
| 包含 active constraints | 禁止自动直写 |
| 字段缺失或约束状态不明 | 按 guarded 处理 |

所有 current 写入都必须经过 preflight。`allow` 只授权本次具体变更，不形成后续豁免。

# 5 自动化边界

## 5.1 允许

- 生成候选，默认写入 `03_Inbox/Candidates/`。
- 生成 current update proposal、patch draft、candidate summary 和 required validation plan。
- 更新可重建索引。
- 生成只读 lint 和 preflight 报告。
- 标记疑似 stale、broken、orphan 或 supersession conflict。

## 5.2 禁止

- 自动提升正式知识。
- 自动修改 verified、guarded、critical 或含 active constraints 的文档。
- 自动关闭 supersession 冲突。
- 自动删除或改写历史记录。
- 自动提高 evidence level。
- 自动声明 `single_pass_recoverable: true`。

# 6 分阶段实施计划

## 6.1 阶段 0：目标与权威边界收敛

交付四层职责矩阵、目标/非目标、规则权威顺序、自动化边界和 preflight 触发条件。退出条件是每条强制规则只有一个权威定义位置，`AGENTS.md` 不继续吸收工具实现细节。

## 6.2 阶段 1：生命周期 Schema v2

交付显式字段、legacy effective-default policy、校验规则及兼容示例。不批量猜测或迁移历史字段。

## 6.3 阶段 2：只读 Wiki lint

检查标准分区、入口、元数据、断链、孤儿页、current 完整性、supersession 环路/悬空、来源越权、复核到期、保护异常和 current 历史流水。默认只报告，不修复。

## 6.4 阶段 2.5：记录类型与目标目录

先定义新记录的稳定落点，不立即大规模迁移：

| 类型 | 默认落点 |
|---|---|
| 当前事实 | `*_current.md` |
| 修复闭环 | `fixes/` |
| 设计决策 | `decisions/` |
| 验证证据 | `validation_records/` |
| 普通维护过程 | `Current Maintenance Records/` |
| 事故调查 | `incidents/` |
| 外部候选 | `03_Inbox/Candidates/` |
| 外部证据 | `04_Sources/` |

## 6.5 阶段 3A：最小 Metadata Extractor

只提取 Traceability 必需的 path、title、type、project/module、status、protection、affected paths、aliases、supersession、evidence references 和时间字段，并输出 `declared/effective/value_origin`。

## 6.6 阶段 3B：Traceability Index 与 Pre-write Gate

实现强/中/弱信号、候选召回、原文 section/hash 读取证据、影响分析和门禁决策。索引不可用、原文不可读、授权不足或 supersession 冲突未解决时，高风险写入不得降级放行。

## 6.7 阶段 4：Current 去历史化与记录迁移

current 只保留当前事实；fixes/decisions/validation/incidents 保存可追溯历史；maintenance records 保存过程流水；结构审计 current 去除逐次项目流水。迁移前后保持链接和 supersession 可追溯，不默认整组重写 current。

## 6.8 阶段 5：完整 Metadata Index

在最小 extractor 上增加 headings、summaries、aliases、tags/domain、source references、entry relationships、review queues 和 coverage 状态，服务导航、过滤和后续检索。

## 6.9 阶段 6：中文全文检索基准

用固定中文查询集比较 `rg`、FTS5 `unicode61`、FTS5 `trigram`、外部分词及 metadata + traceability 组合。评测 Recall@5、Recall@10、首个相关结果排名、噪声比例和索引成本。未达标方案不得进入正式写入链。

## 6.10 阶段 7：事件驱动维护

允许新来源候选化、会话结晶化候选、索引更新、局部 lint 和定期 stale 检查；所有正式提升、受保护写入、冲突关闭和历史删除继续受人工门禁控制。

## 6.11 阶段 8：高级能力

只有评测证明必要时才考虑 embedding + BM25 RRF、typed relationships、claim-level lifecycle/decay 和多 Agent 合并。

# 7 与外部参考的关系

来源依据见 [[04_Sources/知识库工程/2026-06-22_LLM-Wiki-v2与pro-workflow来源证据卡]]。

可借鉴：

- Markdown 主存储。
- SQLite FTS5 影子索引。
- wiki pages / sources 等派生表结构。
- 可重建 reindex、research seed、lint 和自动检索注入。

不原样照搬：

- 中文 tokenizer 必须独立验证。
- SQLite 不得成为事实源。
- 外部内容不得自动提升。
- 不直接引入浮点 confidence。
- maintenance records 不作为强约束。
- 知识图谱和向量检索必须由查询评测证明必要。

# 8 验收标准

1. 每次 guarded/critical 命中都读取 Markdown 原文，并记录 section、行号和可验证 hash。
2. preflight 后关键原文或目标文件变化会使门禁失效。
3. 所有 current 写入都在首次修改前完成 preflight。
4. 历史修复回放的 Traceability Recall@5 达到 100%。
5. maintenance records 不会单独产生 active constraint 或阻断写入。
6. 自动化直接修改 verified/guarded/critical/active-constraint 文档的次数为 0。
7. active 入口断链为 0，supersession 无环且无悬空目标。
8. current 不再承载逐次维护流水。
9. 删除派生索引后能够从 Markdown 完整重建。
10. 工具不会把 effective 默认值回写成 declared 事实。
11. 中文全文方案必须经过基准后才能进入正式维护链。
