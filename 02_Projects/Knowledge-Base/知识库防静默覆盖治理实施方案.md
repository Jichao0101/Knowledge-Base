# 1 知识库防静默覆盖治理实施方案

## 1.1 目标

本方案的唯一主目标是：

> 防止已有修复、约束和当前事实源在后续写入中被静默覆盖，并保证任何高风险写入都能追溯到相关 Markdown 原文和验证证据。

全文检索、向量检索、知识图谱和自动研究只可能是后续召回手段，不是本项目的目标。

## 1.2 基本不变量

1. 中文 Markdown 是唯一事实源。
2. Index、lint report 和 preflight report 都是可删除、可重建的派生物。
3. 自动化不得绕过 [[AGENTS]]。
4. 写入门禁必须发生在首次修改之前，写后 lint 不能替代写前门禁。
5. Traceability Index 只召回候选，事实判断必须读取命中的 Markdown 原文。
6. 自动化不得直接修改 verified、guarded、critical 或包含 active constraints 的 current 文档。
7. 外部信息不得自动提升到 `01_Knowledge`，会话结晶化候选默认进入 `03_Inbox/Candidates/`。

# 2 分层治理与落点

Markdown 是唯一事实源。当前 lint、metadata extractor、Traceability Index 和 preflight gate 都只服务于 knowledge-base skill，因此采用 **Skill-owned tools**：工作流、规则和实现由同一个 skill 版本绑定发布，但在 skill 内部分文件保存；仓库侧只保留政策、运行报告和可重建缓存。

| 关注面 | 推荐落点 | 责任 | 不负责 |
|---|---|---|---|
| Hard Policy | `AGENTS.md` | 定义不可绕过的目录授权、写入分层、提升条件、自动化禁区和门禁原则 | 工作流步骤、severity 表、schema enum、CLI 和报告格式 |
| Skill-owned Bundle | knowledge-base skill | `SKILL.md/references` 负责流程，`rules/` 负责 schema enum、路径默认、lint severity 和 gate decision，`scripts/` 负责 extractor、lint、trace index、gate 和 hash check | 重新定义仓库政策、把机器规则塞入 `SKILL.md` 正文、把规则散落在实现代码中 |
| Runtime Reports | `reports/kb/` | 保存 lint/preflight 的单次运行输入摘要、命中、读取证据、skill/rules 版本和决策 | 充当事实源、长期 current、自动提升证据等级 |
| Rebuildable Cache | `.kb_cache/` | 保存 metadata projection、Traceability Index 和其他可从 Markdown 重建的缓存 | 保存唯一证据、承载人工维护内容、影响无缓存时的保守门禁语义 |

推荐目录形态：

```text
AGENTS.md

$SKILL_ROOT/
├── SKILL.md
├── references/
├── rules/
│   ├── schema-enums.yaml
│   ├── path-defaults.yaml
│   ├── lint-severity.yaml
│   └── gate-decision-table.yaml
└── scripts/
    ├── metadata-extractor
    ├── lint
    ├── trace-index
    ├── gate
    └── hash-check

reports/kb/
├── lint/
└── preflight/

.kb_cache/
├── metadata/
└── trace-index/
```

以上是目标布局，不表示当前阶段立即创建空目录或实现文件。具体文件格式应在阶段 0/1 固化后再创建。

Pre-write Gate 是 skill-owned bundle 内的绑定能力：`SKILL.md/references` 发起流程，同版本 `rules/` 提供确定性规则，同版本 `scripts/` 执行召回、原文核验与决策，仓库内 `reports/kb/preflight/` 保存运行证据，`.kb_cache/` 只保存可重建索引。

权威优先级为：

1. `AGENTS.md`。
2. 项目或模块 `overview_current` 及其列出的当前事实源。
3. knowledge-base skill 同一版本内的 workflow 与 rules。
4. skill scripts 中的非政策实现默认行为。

依赖方向必须单向：`AGENTS.md → skill-owned workflow/rules/scripts → reports/.kb_cache`。skill 内部 rules 必须引用稳定 rule ID，workflow 只能调用同版本 rules/scripts；若 rules 与 `AGENTS.md` 冲突、skill/rules 版本不匹配、规则未知或无法解析，gate 必须保守返回 `blocked`，不能由实现自行选择较宽松解释。

运行报告必须至少记录 `skill_version` 或 `skill_content_hash`、`tool_version`、`ruleset_hash`、`repository_revision`、输入/目标 hash 和生成时间。报告默认是可重建派生物；若某次报告需要成为项目验证依据，必须通过显式维护流程由 validation/fix/decision 记录引用其路径与 hash，不能自动把整个 `reports/` 目录提升为事实区。`.kb_cache/` 必须可安全删除并从 Markdown 重建，默认不纳入事实读取顺序。

只有出现以下独立消费者之一，才重新评估把 tools/rules 迁移为 repo-level `tools/kb/`：

- CI 需要不经过 knowledge-base skill 直接调用 lint/gate。
- 两个及以上 skill 需要共享同一规则与实现。
- 人工 CLI 或其他 Agent 形成稳定、独立的调用契约。
- 工具需要独立发布、版本兼容或安全审计边界。

在满足迁移条件前，不同时维护 skill-owned 与 repo-level 两套规则或实现。

# 3 生命周期 Schema v2

## 3.1 显式字段

```yaml
status: draft | active | verified | stale | superseded | archived
evidence_level: unsourced | single_source | corroborated | runtime_verified
evidence_refs: []
review_after:
supersedes: []
superseded_by: []
protection_level: normal | guarded | critical
change_policy: free_update | append_only | explicit_supersession_required
```

- `status` 表达知识生命周期。
- `evidence_level` 表达证据成熟度，不表达概率。
- `evidence_refs` 记录支撑当前文档状态或结论的来源卡、内部依据、fix、decision、validation 或运行证据引用；Schema v2 统一使用该字段。
- `protection_level` 表达修改风险。
- `change_policy` 表达允许采用的变更方式，不能由 `protection_level` 替代。
- 本阶段不引入 claim-level 浮点 confidence。

以上是 Schema v2 的最小 declared frontmatter。只有能改变写入门禁、追溯证据或 supersession 判断的字段才进入该集合。`project/module`、信号等级、权威状态、哈希、约束扫描结果及索引属性均不得要求作者重复填写。

本节定义的是未来门禁使用的最小 Schema v2，不立即废止当前 `AGENTS.md` 已要求的 summary/source/scope/risks 等内容元数据；这些既有字段在迁移前继续服务可读性和正式知识准入，但不得被写入门禁实现为新的隐式许可条件。

`change_policy` 语义：

| 策略 | 语义 |
|---|---|
| `free_update` | 在授权范围内允许普通更新；若文档同时为 guarded/critical/current，仍必须通过对应 preflight gate |
| `append_only` | 只允许追加，不允许改写或删除已经记录的历史事实；更正必须追加说明或建立新的替代记录 |
| `explicit_supersession_required` | 替代旧结论时必须声明 `supersedes/superseded_by`、替代原因和验证证据，不能静默覆盖 |

兼容规则：历史文档中的 `source` 或 `sources` 继续有效。Metadata Extractor 将其映射为 effective `evidence_refs`，但不得静默改写原文；新建或显式迁移到 Schema v2 的文档统一写 `evidence_refs`。

## 3.2 历史文档缺省解释

工具必须区分 `declared`、`effective` 和 `value_origin`，不得把推导值回写成已声明事实。

| 缺失字段 | effective 默认值 |
|---|---|
| `status` | `legacy_unknown` |
| `evidence_level` | `unsourced` |
| `review_after` | `unknown`，不得据此直接判定 stale |
| `evidence_refs` | `[]`，只表示未声明；不得据此断言没有证据 |
| `supersedes` / `superseded_by` | `[]`，只表示未声明 |
| `constraint_state`（派生） | `unknown`；current 写入进入人工审查，不要求人工填写 `active_constraints: []` |

路径保护与变更策略缺省：

| 路径或类型 | effective protection | effective change policy |
|---|---|---|
| `*_current.md` | `guarded` | `free_update`；不豁免 current preflight，替代 active constraint 时仍需显式 supersession |
| `01_Knowledge/` | `guarded` | `explicit_supersession_required` |
| fixes / decisions / validation records | `guarded` | `explicit_supersession_required` |
| `04_Sources/` 原始证据 | `guarded` | `append_only` |
| maintenance records | `normal`，且只作为弱信号 | `append_only` |
| `03_Inbox/` | `normal` | `free_update` |
| `90_Archive/` | `guarded` | `append_only`，禁止自动删除或改写已有内容 |

示例派生结果：

```yaml
declared:
  status: null
  protection_level: null
  change_policy: null
  evidence_refs: null
effective:
  status: legacy_unknown
  evidence_level: unsourced
  protection_level: guarded
  change_policy: explicit_supersession_required
  evidence_refs: []
  constraint_state: unknown
value_origin:
  status: default
  evidence_level: default
  protection_level: path_policy
  change_policy: path_policy
  evidence_refs: default
  constraint_state: default
```

`verified_at` 后置为可选审计属性，不进入第一版最小 declared schema。若未来确需记录，应由验证事件或审计记录产生，不得成为与 `status/evidence_level` 并行的第三套写入许可判断。

# 4 Traceability 与写前门禁

## 4.1 信号等级

| 等级 | 记录类型 | 门禁作用 |
|---|---|---|
| strong | current、verified knowledge、fixes、decisions、最终 incident 结论、validation records、active constraints | 可触发 `manual_review` 或 `blocked` |
| medium | source cards、已审核设计、active 但未 verified 的项目记录、supersession 关系 | 读取原文后参与影响判断 |
| weak | maintenance records、session summaries、run logs、临时调查、superseded 实验路径 | 只提高召回或提供追踪线索，不能独立形成约束或阻断写入 |

strong/medium/weak 是 Traceability Index 的派生分类，不允许作者在 Markdown 中人工填写。maintenance records 若命中，只能作为弱信号；若其链接到 fix、decision 或 validation，必须继续读取对应强信号原文。

Traceability Index 的派生记录可以包含以下属性，但这些不是 Schema v2 declared frontmatter：

```yaml
record_type: <derived from path/content>
project: <derived from path/overview>
module: <derived from path/overview>
affected_paths: <derived from links/content>
symptoms: <derived from content>
constraints: <derived from content scan and source reads>
signal_strength: strong | medium | weak
authority_status: authoritative | supporting | historical | superseded
source_document: <derived path>
recorded_at: <derived from metadata/git/filesystem according to tool policy>
```

其中 `signal_strength`、`authority_status`、`source_document`、`project`、`module`、`recorded_at` 和 `constraint_state` 都必须带 `value_origin`，不得伪装为作者声明。

## 4.2 Preflight 流程

1. 根据拟修改路径、项目、模块、标题和 aliases 确定检索范围。
2. 用最小 Metadata 和 Traceability Index 召回候选。
3. 读取命中的 Markdown 原文，而不是使用索引摘要作为事实依据。
4. 读取相应 current 入口和 active constraints。
5. 形成可能被覆盖的修复、受影响文件、必须保持的约束和必需验证。
6. 校验目标文档的 `change_policy`：append-only 变更不得改写已有内容；显式替代必须具备双向 supersession、原因和 `evidence_refs`。
7. 在首次文件修改前输出门禁决策。
8. 写入前重新核验关键原文和目标文件哈希；发生变化则 preflight 失效。

## 4.3 原文读取证据

```yaml
source_documents_read:
  - path: 02_Projects/DMS/04_Tracking/tracking_spec_current.md
    reason: 命中 affected_paths 和 active constraint
    matched_terms:
      - driver-bound
      - body evidence
    sections_read:
      - heading: "Body evidence constraints"
        line_start: 82
        line_end: 116
        section_hash: sha256:...
    document_hash: sha256:...
    status: verified
    protection_level: guarded
    read_at: 2026-06-22T14:30:00+08:00
```

`document_hash`、`section_hash` 和写前 `target_hash_before_write` 属于单次 preflight 的运行时证据，不写入目标 Markdown frontmatter。

完整 preflight report 至少包含：

```yaml
preflight_snapshot:
  generated_at:
  skill_version:
  skill_content_hash:
  tool_version:
  ruleset_hash:
  repository_revision:
  target_files: []
  target_hashes_before_write: []
  source_hashes_valid: true
proposed_targets: []
matched_records: []
source_documents_read: []
derived_constraints: []
potentially_overwritten_fixes: []
required_validations: []
authorization_gaps: []
change_policy_checks:
  append_only_violations: []
  supersession_requirements: []
gate_decision: allow | manual_review | blocked
```

`derived_constraints` 必须引用其来源文档和读取 section，不允许人工填写一个无来源的 `active_constraints: []` 来影响门禁。

## 4.4 确定性门禁规则

门禁输入固定为：

```yaml
target_path:
target_declared_metadata:
target_effective_metadata:
matched_trace_records: []
source_documents_read: []
change_intent:
```

规则固定为：

1. 如果目标位于 `AGENTS.md` 禁区：`blocked`。
2. 如果目标原文不可读或授权不足：`blocked`。
3. 如果 target `status = verified`：`manual_review`。
4. 如果 target `protection_level = critical`：`manual_review`，并设置 `validation_plan_required: true`。
5. 如果 target `protection_level = guarded`：`manual_review`。
6. 如果 target `change_policy = append_only` 且变更会改写或删除已有内容：`blocked`。
7. 如果 target `change_policy = explicit_supersession_required`，且变更替代旧结论但没有完整 supersession、原因或 `evidence_refs`：`blocked`。
8. 如果命中 strong record 且未读取对应 Markdown 原文：`blocked`。
9. 如果命中 effective protection 为 guarded/critical 的来源文档且未读取原文：`blocked`。
10. 如果 supersession 冲突未解决：`blocked`。
11. 如果只有 weak record 命中：不阻断，但必须写入 preflight 报告。
12. 其他情况：`allow`。

所有规则都必须评估，不能在遇到第一个 `manual_review` 后提前返回。最终结果按 `blocked > manual_review > allow` 合并；`validation_plan_required` 是附加要求，不是第四种决策状态。规则只使用 declared/effective metadata 和可验证的读取证据，不能使用索引摘要直接判定事实。

## 4.5 Current 写入规则

| Current 情况 | 允许行为 |
|---|---|
| draft/active + normal + 内容扫描未发现 active constraints | preflight 为 `allow` 后可以写入 |
| verified | 只能自动生成 proposal、patch draft 或 candidate summary |
| guarded | 只能自动生成 proposal 或 patch draft，人工确认后写入 |
| critical | 必须额外生成影响分析和验证计划 |
| 内容扫描或原文读取发现 active constraints | 禁止自动直写 |
| 字段缺失或约束状态不明 | 按 guarded 处理 |

所有 current 写入都必须经过 preflight。`allow` 只授权本次具体变更，不形成后续豁免。

`change_policy` 与 current gate 同时生效：`free_update` 不表示允许绕过 preflight；若变更将替代 active constraint 或已验证结论，即使 current 声明为 `free_update`，也必须升级为 `explicit_supersession_required` 处理。

# 5 自动化边界

## 5.1 允许

- 生成候选，默认写入 `03_Inbox/Candidates/`。
- 生成 current update proposal、patch draft、candidate summary 和 required validation plan。
- 更新可重建索引。
- 生成只读 lint 和 preflight 报告。
- 标记疑似 stale、broken、orphan 或 supersession conflict。

## 5.2 禁止

- 自动提升正式知识。
- 自动修改 verified、guarded、critical 或含 active constraints 的文档。
- 自动关闭 supersession 冲突。
- 自动删除或改写历史记录。
- 自动提高 evidence level。
- 自动把缺失的 `evidence_refs` 解释为“无证据”，或把 legacy `source/sources` 静默改写为 Schema v2。
- 自动声明 `single_pass_recoverable: true`。

# 6 分阶段实施计划

## 6.1 阶段 0：目标与权威边界收敛

交付职责矩阵、目标/非目标、Skill-owned tools ownership 决策、目标目录契约、稳定 rule ID、自动化边界和 preflight 触发条件。退出条件是每条强制政策只有一个权威定义位置，同一 skill 版本绑定 workflow/rules/scripts，`AGENTS.md` 不继续吸收工作流、机器规则、工具实现或报告格式。

## 6.2 阶段 1：生命周期 Schema v2

交付最小 declared 字段、`change_policy`、页级 `evidence_refs`、legacy effective-default policy、确定性门禁规则、校验规则及兼容示例。不批量猜测或迁移历史字段。

## 6.3 阶段 2：只读 Wiki lint

在 knowledge-base skill 的 `rules/` 固化 lint severity，在同一 skill 的 `scripts/` 实现只读 lint，并将单次结果写入仓库 `reports/kb/lint/`。检查标准分区、入口、元数据、断链、孤儿页、current 完整性、supersession 环路/悬空、来源越权、复核到期、保护异常和 current 历史流水。默认只报告，不修复。

## 6.4 阶段 2.5：记录类型与目标目录

先定义新记录的稳定落点，不立即大规模迁移：

| 类型 | 默认落点 |
|---|---|
| 当前事实 | `*_current.md` |
| 修复闭环 | `fixes/` |
| 设计决策 | `decisions/` |
| 验证证据 | `validation_records/` |
| 普通维护过程 | `Current Maintenance Records/` |
| 事故调查 | `incidents/` |
| 外部候选 | `03_Inbox/Candidates/` |
| 外部证据 | `04_Sources/` |

## 6.5 阶段 3A：最小 Metadata Extractor

在 knowledge-base skill 的 `rules/` 固化 schema enum 与路径默认策略，在同一 skill 的 `scripts/` 实现 extractor；可重建结果写入仓库 `.kb_cache/metadata/`。只读取最小 declared frontmatter，并派生 path、record type、project/module、约束候选、信号等级、权威状态和运行时哈希等 Traceability 属性。所有结果输出 `declared/effective/value_origin`；读取 legacy `source/sources` 时只做 effective 映射，不修改原文。

## 6.6 阶段 3B：Traceability Index 与 Pre-write Gate

在 knowledge-base skill 的 `rules/` 固化 gate decision table，在同一 skill 的 `scripts/` 实现 Traceability Index、gate 与 hash check；Traceability 缓存写入 `.kb_cache/trace-index/`，运行结果写入 `reports/kb/preflight/`。实现强/中/弱信号、候选召回、原文 section/hash 读取证据、影响分析和门禁决策。索引不可用、原文不可读、授权不足、skill/rules 版本异常或 supersession 冲突未解决时，高风险写入不得降级放行。

## 6.7 阶段 4：Current 去历史化与记录迁移

current 只保留当前事实；fixes/decisions/validation/incidents 保存可追溯历史；maintenance records 保存过程流水；结构审计 current 去除逐次项目流水。迁移前后保持链接和 supersession 可追溯，不默认整组重写 current。

## 6.8 阶段 5：可选 Metadata Projection

该阶段不再以“完整 metadata index”为目标。在最小 extractor 无法满足导航或检索评测时，才按需派生 headings、summaries、tags/domain、entry relationships 或 review queues；这些字段默认不写入 Markdown，也不得成为 pre-write gate 的隐藏输入。任何扩展都必须说明具体消费者、重建方式和删除后的降级行为。

## 6.9 阶段 6：中文全文检索基准

用固定中文查询集比较 `rg`、FTS5 `unicode61`、FTS5 `trigram`、外部分词及 metadata + traceability 组合。评测 Recall@5、Recall@10、首个相关结果排名、噪声比例和索引成本。未达标方案不得进入正式写入链。

## 6.10 阶段 7：事件驱动维护

允许新来源候选化、会话结晶化候选、索引更新、局部 lint 和定期 stale 检查；所有正式提升、受保护写入、冲突关闭和历史删除继续受人工门禁控制。

## 6.11 阶段 8：高级能力

只有评测证明必要时才考虑 embedding + BM25 RRF、typed relationships、claim-level lifecycle/decay 和多 Agent 合并。

# 8 验收标准

1. 每次 guarded/critical 命中都读取 Markdown 原文，并记录 section、行号和可验证 hash。
2. preflight 后关键原文或目标文件变化会使门禁失效。
3. 所有 current 写入都在首次修改前完成 preflight。
4. 历史修复回放的 Traceability Recall@5 达到 100%。
5. maintenance records 不会单独产生 active constraint 或阻断写入。
6. 自动化直接修改 verified/guarded/critical/active-constraint 文档的次数为 0。
7. active 入口断链为 0，supersession 无环且无悬空目标。
8. current 不再承载逐次维护流水。
9. 删除派生索引后能够从 Markdown 完整重建。
10. 工具不会把 effective 默认值回写成 declared 事实。
11. 中文全文方案必须经过基准后才能进入正式维护链。
12. append-only 文档的已有内容不会被自动改写或删除。
13. 对 fix、decision、validation record 或正式知识的结论替代，必须具备双向 supersession、替代原因和可读取的 `evidence_refs`。
14. 人工 declared frontmatter 不包含 `signal_strength`、`authority_status`、`source_document`、`project/module`、运行时 hash 或无来源的 `active_constraints`。
15. 门禁对全部规则完成评估，并严格按 `blocked > manual_review > allow` 合并结果。
16. `AGENTS.md` 只保存政策；knowledge-base skill 同一版本绑定 workflow/rules/scripts；`reports/kb/` 和 `.kb_cache/` 只保存运行产物，不存在跨 ownership 的重复规则实现。
17. 每份 lint/preflight 报告都能追溯到 skill version/content hash、`tool_version`、`ruleset_hash`、repository revision 和输入 hash；报告本身不被视为事实源。
18. 未出现 CI、多 skill、独立 CLI 或其他 Agent 等独立消费者前，不创建 repo-level `tools/kb/` 第二实现。
