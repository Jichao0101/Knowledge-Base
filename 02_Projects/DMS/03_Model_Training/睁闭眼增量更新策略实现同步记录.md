## 1.2 当前规则

### 1.2.1 Stage A

- 引入 `stage_a_scan_state.json`
- 已扫描且目录指纹未变化的子目录不再访问
- 若目录复用，则从历史 `stage_a_source_manifest.json` 回填该目录的旧 items
- 若目录被复用但历史 `stage_a_source_manifest.json` 中已缺失该目录旧 items，则自动回退为该目录重扫
- Stage A 每次执行后输出的是“当前全量视图”，而不是“本轮增量子集”

### 1.2.2 Stage B

- 引入 `stage_b_copy_registry.json`
- 已复制完成且源目录指纹未变化的目录不再重复拷贝
- 输出记录统一为：
  - `stage_b_missing_images.txt`
  - `stage_b_copy_report.json`
  - `stage_b_copied_jsons.txt`

  - `stage_b_copy_registry.json` 表示当前全量复制状态
  - `stage_b_copy_report.json`、`stage_b_copied_jsons.txt`、`stage_b_copied_images.txt`、`stage_b_missing_images.txt` 表示本轮执行记录

### 1.2.3 Stage C

- 历史 group 继承原 split
- 默认模式为“更新 benchmark”
- 在“更新 benchmark”模式下：
  - `total_samples < N_min` 的新增 group 只能进入 `train`
  - `total_samples >= N_min` 的新增 group 参与本轮 `train / val / test` 增量更新
- 在“冻结 benchmark”模式下：
  - 所有新增数据直接进入 `train`
  - 历史 `val/test` 保持不变
- 输出记录统一为：

- 上述 Stage C 输出统一表示增量更新后的当前全量结果；若 checklist 记录本轮统计，必须显式区分

### 1.2.4 Stage D

- 只保留 `SquareCrop + OOB Const Padding`
- `k` 为唯一上下文比例变量

- 输出记录统一为：
  - `stage_d_roi_manifest.json`
  - `stage_d_roi_checklist.txt`

## 1.3 Bug 根因

问题根因不在 Stage C split 规则，而在 Stage A 增量扫描实现。

旧实现的问题是：

1. 当目录指纹未变化时，Stage A 只复用 `scan_state` 里的目录级状态并直接跳过子树扫描。
2. `scan_state` 不保存该目录对应的历史 json items。
3. 因此本轮重新写出的 `source_manifest.json` 只包含“变化目录”的 items。
4. Stage B/C/D 后续都基于这个被缩小的 manifest 继续执行，导致历史记录在下游被隐式覆盖。

结论：

- 只做“目录级跳过”而不做“历史 item 回填”，不满足增量更新语义。
- 至少要保证一个传递给下游的文件保持“全量当前视图”；本轮选择在 Stage A 修复这一点。

## 1.4 2026-04-21 补充问题：Stage D 残留 ROI 污染当前数据视图

本轮补充排查发现，Stage A/B/C 的增量语义已经基本对齐，但 Stage D 仍有一个会破坏“当前视图”的缺口：

1. `stage_d_export_rois.py` 在 `--incremental` 模式下会复用已有 ROI，并重写 `stage_d_roi_manifest.json`
2. 但旧实现不会删除磁盘上已经失效的历史 ROI 文件
3. `train_rois.py` 的数据读取口径是直接扫描 `train/val/test` 目录，而不是只按 `stage_d_roi_manifest.json` 过滤
4. 因此只要某个样本在新一轮 `stage_c_final_manifest.json` 中被删除、迁移 split，或因数据清洗不再保留，其旧 ROI 仍可能继续进入训练/验证

结论：

- 这不符合 `02_Projects/DMS/03_Model_Training/睁闭眼模型训练方案.md` 中“benchmark 变化不能隐式覆盖”“增量更新后仍需保持可追溯当前视图”的要求。
- Stage D 不仅要维护 manifest，还必须对齐目录内容。

## 1.5 修复方案

### 1.5.1 Stage A 修复

在 `stage_a_scan_blink.py` 中新增以下机制：

1. 读取历史 `stage_a_source_manifest.json`
2. 以目录为粒度建立 `prev_items_by_dir`
3. 对于本轮复用目录，把旧 items 回填到 `merged_items`
4. 用 `merged_items` 重建新的 `stage_a_source_manifest.json`
5. 在 build 信息里记录：
   - `reused_source_dirs`
   - `recovered_source_dirs`
   - `recovered_jsons`
   - `reused_items`
   - `merged_items`
   - `previous_source_manifest`

这样即使第二次只新增一个目录，输出 manifest 仍包含历史目录和新增目录的全部记录。

### 1.5.2 1.4.1A 2026-04-22 Stage A 自愈补丁

补充排查发现，仅依赖“从上一版 manifest 回填 reused dir 的旧 items”仍有一个恢复缺口：

1. 若某次错误执行已经把 `stage_a_source_manifest.json` 覆盖成“只含当前批次”
2. 下一次运行即使代码已支持 reused-dir 回填，也只能从这个错误 manifest 中继续回填空结果
3. 结果就是旧目录会被 `scan_state` 持续跳过，而历史 items 永远回不来

因此本轮增加自愈逻辑：

1. 对于被 `scan_state` 判定为“可复用”的目录，若其 `contains_blink_json=true`
2. 但上一版 `stage_a_source_manifest.json` 中不存在该目录的历史 items
3. 则不继续静默复用，而是对该目录执行一次补偿重扫
4. 用补偿重扫得到的 items 重新构建当前全量 manifest

这样即使现场已经被错误产物污染，只要原始 `rawData` 还在，Stage A 也能恢复为设计文档要求的当前全量视图。

### 1.5.3 2026-04-21 Stage D 修复

在 `src/stage_d_export_rois.py` 中新增以下机制：

1. 先根据当前 `stage_c_final_manifest.json` 计算本轮应存在的 `desired_roi_paths`
2. 正常执行 ROI 复用或重新导出
3. 在 `max_items=0` 的正式运行中，扫描 `train/val/test` 下现存 ROI 文件
4. 删除不在 `desired_roi_paths` 内的残留文件
5. 尝试清理因删除而变空的 label/split 目录
6. 在 `stats` 中记录 `stale_files_removed`

这样 Stage D 的目录内容与 `stage_d_roi_manifest.json` 会重新收敛为同一份当前视图，训练入口不会再被历史残留 ROI 污染。
