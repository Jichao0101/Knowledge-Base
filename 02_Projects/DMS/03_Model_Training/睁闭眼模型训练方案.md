
## 0.1 目标与约束

本文档用于统一当前睁闭眼分类任务的数据构建、输入生成、训练配置、评测协议与误分类分析机制，确保后续实验具备以下性质：

- 训练输入与部署输入尽可能一致
- 数据版本、split 版本、输入版本、训练版本、评测版本严格绑定
- 增量数据加入后，历史 benchmark 不漂移
- 输入实验、loss 实验与 backbone 实验可归因
- 误分类可回溯至原始数据与输入生成链路
- 正式 baseline 以量化表现优先，而非仅以 FP32 最优为准

本文档同时明确当前阶段的边界条件：

- split 主键仅使用 `group_id = f(person_id)`
- 其他信息仅保留为 `meta`，不参与 split
- 仅使用 `total_samples >= N_min` 作为评测 group 候选门槛
- 暂不引入时序约束、覆盖度约束、受约束分配
- 暂不处理连续抽帧导致的有效样本数虚高问题
- 评测仅使用 **GT 口径**
- 不再保留 `Deploy Eval` 作为正式输出口径

---

## 0.2 当前真正需要解决的问题

当前正式方案聚焦解决以下问题：

1. 训练输入与部署输入不一致  
2. 训练不能再以 `reflect / replicate padding` 为正式主线  
3. ROI 过扁导致 padding 占比过高，模型可能学习 padding shortcut  
4. 输入实验变量混杂，需要拆开“减 padding”和“加上下文”两个效应  
5. split 不支持增量公平比较，必须冻结 `val/test`  
6. 稀疏 group 不适合作为正式评测单元，需要最小样本门槛  
7. MobileNetV2 基线尚未正式重建，必须先稳定 backbone  
8. baseline 选择必须纳入量化表现，而不能只看 FP32  
9. `eye_narrow` 与 `eye_occluded` 的瓶颈机制不同，不能混合优化  
10. 误分类分析必须进入正式闭环，而不能只是附属功能  
11. 训练、量化、部署前处理协议必须写死，避免“表面对齐、细节失配”  
12. 每个正式实验必须绑定完整版本信息

## 0.3 原始数据集

### 0.3.1 理论数据量

睁闭眼数据集来自 56 个场景，每个场景为光线、位置、遮挡的组合，包含：

- 常规场景 12 个，每个场景 24 个 id，每个 id 执行 14 个动作，单 id 抽帧 `14 * 20 = 280` 帧
- 复杂场景 44 个，每个场景 2 个 id，每个 id 执行 14 个动作，单 id 抽帧 `14 * 20 = 280` 帧

总数据量：

``````text
(12 * 24 + 44 * 2) * 280 = 105280
``````

说明：

- 该值为理论样本量，不代表最终可用样本量
- 最终可用样本量受以下因素影响：
  - 图片是否存在
  - JSON 是否可解析
  - bbox 是否有效
  - bbox 是否越界
  - 标签是否合法
  - split 过滤规则
  - ROI 导出是否成功

## 0.4 数据集构建总原则

### 0.4.1 基本原则

- 样本粒度：**单眼**
- split 粒度：**group**
- `group_id = f(person_id)`
- split 比例：**8:1:1**
- seed 固定
- 评估必须可复现：同一版本数据集 + 同一 seed + 同一 split 策略 + 同一输入生成策略 ⇒ 导出结果一致

### 0.4.2 当前 split 约束

正式实验当前只采用以下 split 规则：

- 仅从文件名、路径、JSON 中抽取 `person_id`
- 统一映射为 `group_id = f(person_id)`
- 按 `group_id` 分配 `train / val / test`
- 同一 `group_id` 下所有图片与单眼样本广播到同一 split
- 其他信息如 `session_id`、`action_id`、`scene`、`camera`、`illumination` 仅保留在 `meta` 中，不参与 split

### 0.4.3 当前不纳入的机制

以下机制在当前阶段明确不启用：

- 不使用时序约束
- 不使用覆盖度约束
- 不使用受约束分配
- 不单独修正连续抽帧导致的有效样本数虚高

理由：

- 当前首要目标是先建立一套可复现、可归因、便于执行的正式闭环
- 若同时引入过多 split 约束，会显著增加构建复杂度与执行成本
- 当前阶段优先解决输入一致性、baseline 重建、量化主导与误分类闭环问题

## 0.5 采样与 split 策略

### 0.5.1 group split

正式实验默认使用 **group split**：

- 从文件名、路径、JSON 中提取 `person_id`
- 生成 `group_id = f(person_id)`
- 按 `group_id` 分配 split（8:1:1）
- 广播到该 group 下全部图片与单眼样本
- 输出：
  - `split_report.json`
  - `leakage_audit.txt`

要求：

- `group_id` 跨 split 次数必须为 0

### 0.5.2 评测 group 候选门槛

为避免极小 group 进入 `val/test` 造成评测波动，当前采用最简门槛规则：

- 若某 `group_id` 的 `total_samples < N_min`，则该 group 默认只进入 `train`
- 只有 `total_samples >= N_min` 的 group 才允许作为 `val/test` 候选

说明：

- 当前仅使用 `total_samples` 作为门槛
- 暂不引入时序去相关后的有效样本数约束
- 暂不引入场景覆盖度约束

建议输出：

``````text
group_registry.json
``````

字段至少包括：

- `group_id`
- `person_id_raw`
- `total_samples`
- `is_eval_candidate`
- `split`
- `first_seen_source_version`
- `is_frozen`

### 0.5.3 冻结评测集与增量更新原则

为保证版本间实验可比，正式实验采用 **冻结评测集** 策略：

- 历史 `val/test` 中的 `group_id` 一旦确定，不允许在后续增量版本中流入 `train`
- 新数据到来时，历史 `group_id` 继承原 split，不重新随机切分
- 新增且 `total_samples < N_min` 的 `group_id` 默认只进入 `train`
- 仅在显式创建新的 benchmark 版本时，才允许重建 `val/test`

说明：

- `split_version` 必须可追溯
- benchmark 变化必须通过新版本体现，而不能隐式覆盖旧版本

## 0.6 数据集构建流程

### 0.6.1 Stage A：扫描源目录，生成 source manifest

#### 0.6.1.1 目标

低 I/O 找全 JSON，并行完成 JSON 与 bbox 语义校验，同时为后续 group split 提供 `person_id` 候选信息。

#### 0.6.1.2 输入

- `annotation_root`（只读）

#### 0.6.1.3 扫描规则

- 单线程 `os.walk`
- 只在命中 `BlinkDetection` 子树时收集 `*.json`

#### 0.6.1.4 增量扫描规则

Stage A 必须支持目录级增量更新，目标是避免重复访问已经遍历过的子文件夹，包括历史上没有命中目标数据的子文件夹。

建议新增状态文件：

``````text
scan_state.json
``````

每个目录条目至少记录：

- `subdir_rel`
- `scan_status`
- `contains_blink_json`
- `dir_fingerprint`
- `last_scanned_at`
- `source_version`

执行规则：

- 若 `subdir_rel` 已存在于 `scan_state.json`，且 `dir_fingerprint` 未变化，则本轮跳过该子目录
- 即使历史扫描结果为“不包含目标数据”，只要目录指纹未变化，本轮也不得再次进入
- 只有目录新增、目录内容变化或显式要求全量重扫时，才重新进入该子目录
- `scan_state.json` 更新必须是幂等的，允许中断后续跑

#### 0.6.1.5 并行检查

- JSON 能否解析
- 是否有 `filePath`
- 是否有 `info.width/height`
- `dataList` 是否为 list
- 每个 `dataList[i]`：
  - `properties.eye_status` 是否合法
  - `coordinates` 是否为 `[[x1,y1],[x2,y2]]`
  - 坐标是否可转 float
  - 坐标是否非 `NaN/Inf`
  - `x2 > x1, y2 > y1`
  - 宽高是否大于 `min_size`
  - 若有 `width/height`，检查越界情况
- 提取 `person_id_guess`
- 记录命中规则版本 `person_parse_rule_version`

#### 0.6.1.6 产出

1. `blink_roots.txt`
2. `source_manifest.json`
3. `data_checklist.txt`
4. `group_key_stats.json`
5. `scan_state.json`

其中 `source_manifest.json` 每条记录至少包含：

- `json_rel`
- `img_rel_guess`
- `filePath`
- `samples`
- `validation_stats`
- `person_id_guess`
- `person_parse_rule_version`

说明：

- Stage A 不读图片
- 只做低成本结构检查
- 缺图只能在后续阶段确认
- `scan_state.json` 属于 Stage A 的增量状态，不得在未变更目录上重复回退
- `source_manifest.json`、`group_key_stats.json`、`blink_roots.txt`、`scan_state.json` 必须表示“增量合并后的当前全量视图”
- `data_checklist.txt` 可以同时包含“本轮执行统计”和“当前全量统计”，但必须显式区分
- 若目录被增量复用，但上一版 `source_manifest.json` 已缺失该目录的历史 items，Stage A 不得继续静默复用空结果，必须回退为该目录重扫以恢复当前全量视图

### 0.6.2 Stage B：复制数据到私人目录

#### 0.6.2.1 输入

- `source_manifest.json`

#### 0.6.2.2 动作

- 复制 JSON 到 `DEST/<json_rel>`
- 推导图片路径：`img_abs = json_abs.parent / filePath`
- 若图片存在，则复制到 `DEST/<img_rel_guess>`
- 若不存在，则记录到 `missing_images.txt`

#### 0.6.2.3 增量复制规则

Stage B 必须支持“已复制过的文件夹不再拷贝”。

建议新增状态文件：

``````text
copy_registry.json
``````

每个复制单元至少记录：

- `source_subdir_rel`
- `dest_subdir_rel`
- `copy_status`
- `source_fingerprint`
- `copied_json_count`
- `copied_image_count`
- `last_copied_at`

执行规则：

- 复制粒度默认按源子目录或批次单元管理，而不是仅按单文件判断
- 若 `source_subdir_rel` 已完成复制且 `source_fingerprint` 未变化，则整个目录跳过，不再重复拷贝
- 若目录内容变化，仅复制新增或变化文件，不回刷未变更文件
- 中途中断后允许按 `copy_registry.json` 恢复，已成功复制部分不得重复写入

#### 0.6.2.4 产出

- `missing_images.txt`
- `copy_report.json`
- `copied_jsons.txt`
- `copied_images.txt`
- `copy_registry.json`

语义要求：

- `copy_registry.json` 必须表示“当前全量 source_manifest 对应的目录复制状态”
- `copy_report.json`、`copied_jsons.txt`、`copied_images.txt`、`missing_images.txt` 默认表示“本轮执行记录”
- README 或同级说明文档必须明确区分“本轮执行记录”和“增量更新后的全部状态”

### 0.6.3 Stage C：容器内升级 final manifest

#### 0.6.3.1 样本粒度与 split 粒度

- 样本粒度：单眼
- split 粒度：group
- `group_id = f(person_id)`
- split 比例：8:1:1
- seed 固定

#### 0.6.3.2 数据检查

- 再次解析 JSON，防复制过程损坏
- 读图获取真实 `W/H`
- bbox 越界按真实 `W/H` 判定
- `img_path/json_path` 统一写为 `dest` 相对路径
- `image_id = sha1(img_rel)`，绑定同图双眼
- `group_id = f(person_id)`
- 基于 `group_id` 生成 split，并广播到组内全部样本

#### 0.6.3.3 增量 split 继承规则

Stage C 必须以历史 `group_registry.json` 和 `final_manifest.json` 为输入进行增量升级，不允许默认全量重分配。

执行规则：

- 先加载上一版 `group_registry.json`
- 若某 `group_id` 在历史版本中已存在，则无条件继承原 `split`
- 历史 `val/test` 中的 `group_id` 不允许流入 `train`
- 历史 `train` 中的 `group_id` 若新增样本，只允许继续追加到 `train`
- 对本轮首次出现的 `group_id`，先统计 `total_samples`
- 若当前任务为“更新 benchmark”：
  - `total_samples < N_min` 的新增 `group_id` 只允许进入 `train`
  - `total_samples >= N_min` 的新增 `group_id` 参与本轮 `train / val / test` 的默认增量更新
- 若当前任务为“冻结 benchmark”：
  - 所有新增数据都直接进入 `train`
  - 历史 `val/test` 保持不变

说明：

- Stage C 的默认行为是“继承 + 追加”，不是“重算 + 重分配”
- 更新 benchmark 时，低于阈值的新 group 只能进入 `train`，但不意味着“只有低于阈值的 group 才能进入 `train`”
- 不允许因为增量数据加入，导致历史测试集样本进入训练集
- `final_manifest.json` 必须支持 append / merge，不得通过全量重建隐式打乱旧 split

#### 0.6.3.4 输出

- `final_checklist.txt`
- `split_report.json`
- `leakage_audit.txt`
- `group_registry.json`
- `final_manifest.json`
- `benchmark_state.json`

其中 `final_checklist.txt` 至少统计：

- 真实缺图率
- 读图失败率
- bbox 越界率
- label 分布
- split 分布
- `val/test` group 最小样本数
- 因 `total_samples < N_min` 被降入 `train` 的 group 数量

说明：

- `final_manifest.json`、`group_registry.json`、`split_report.json`、`leakage_audit.txt`、`benchmark_state.json`、`final_checklist.txt` 均表示“增量更新后的当前全量结果”
- 若 checklist 中需要保留本轮执行统计，必须与当前全量统计分栏或分节展示，避免把本轮增量误读为全部结果

### 0.6.4 0.6.3A Stage D：导出 ROI 数据集

#### 0.6.4.1 0.6.3A.1 目标

将 Stage C 的 `final_manifest.json` 增量导出为训练可直接消费的 ROI 数据集，并保证输入构造、split 继承和版本绑定不漂移。

#### 0.6.4.2 0.6.3A.2 唯一正式输入方案

Stage D 只允许使用：

- `SquareCrop + OOB Const Padding`

不再作为当前正式主线保留：

- `RectROI + Const Padding`
- `reflect / replicate padding`

其中：

- `crop_size = k * max(w_bbox, h_bbox)`
- `k` 为当前唯一实验变量，正式比较范围固定为 `1.0 / 1.4 / 1.8 / 2.2`
- 越界区域仅允许使用 `const padding`
- `pad_value_raw` 必须写入 `preprocess_spec.yaml`

#### 0.6.4.3 0.6.3A.3 增量导出规则

- 若某 ROI 已按相同 `input_version + square_k + pad_value_raw` 导出，则本轮直接复用，不重复生成
- 若 Stage C 仅追加了新样本，则 Stage D 只追加新 ROI，不重写旧 ROI
- 历史 `val/test` ROI 不允许因增量数据加入而进入 `train`
- 不允许通过重新导出全量数据集的方式隐式重排 split

#### 0.6.4.4 0.6.3A.4 输出

- `train/ val/ test` 目录树
- `roi_manifest.json`
- `roi_checklist.txt`

其中 `roi_manifest.json` 必须记录：

- `square_k`
- `pad_value_raw`
- `crop_mode = square_crop_oob_const_pad`
- `bbox_gt`
- `bbox_used`
- `pad_area_ratio`
- `oob_pad_ratio`
- `context_ratio`
- `split`
- `label`
- `input_version`
- `source_final_manifest_version`

说明：

- `train/ val/ test` 目录树、`roi_manifest.json`、`roi_checklist.txt` 必须共同表示“增量更新后的当前全量视图”
- `roi_checklist.txt` 可以记录本轮导出动作统计，但不得让本轮新增量覆盖对当前全量结果的描述

- 默认模式下，benchmark 允许同步增量更新，新增且满足阈值的 group 参与新的 `train / val / test` 分配
- 在冻结 benchmark 上，所有新增数据直接进入 `train`
- 若需要冻结或重建 benchmark，必须显式创建新的 `benchmark_version`

## 0.7 预处理协议固化

这是正式方案新增的关键部分。为避免训练、量化、部署在实现细节上失配，预处理协议必须版本化并写死。

建议新增文件：


### 0.7.1 必须固化的字段

- `color_order`：`RGB` / `BGR`
- `decode_backend`
- `crop_coord_rounding`：`floor / round / ceil`
- `resize_backend`
- `resize_interpolation`
- `keep_ratio`
- `pad_mode = const`
- `pad_value_raw`
- `pad_apply_stage = before_normalize`
- `normalize_mean`
- `normalize_std`
- `input_size`
- `dtype_cast_order`
- `quant_input_dtype`
- `quant_calib_sampling_rule`

### 0.7.2 当前正式要求

训练、量化、部署前处理协议必须满足：

- padding 模式统一为 `const`
- pad value 写入正式版本，不允许口头约定
- 若保留历史 `RectROI` 参考实验，其坐标取整规则必须与当前 `SquareCrop` 保持一致
- 量化 calibration 的输入协议与训练/评测保持一致
- 所有正式实验必须记录 `preprocess_spec_version`
- 所有正式量化实验必须记录 `quant_calib_version`

### 0.7.3 作用机制说明

这一步的目的不是增加配置数量，而是消除以下隐性漂移：

- 相同 bbox 在不同链路中的取整差异
- 相同图片在不同 resize 实现中的插值差异
- 相同 const padding 在不同阶段施加导致分布变化
- 训练期 normalize 与量化期 calibration 分布不一致

若这部分不固化，则即使表面上都叫“ConstPad + 128×128”，仍然可能不是同一输入协议。

## 0.8 输入生成策略

### 0.8.1 正式输入主线

由于部署侧仅支持 **const padding**，当前正式实验输入主线只保留：

#### 0.8.1.1 SquareCrop + OOB Const Padding

基于标注框中心 `(cx, cy)`，从原图直接裁取正方形区域：

``````text
crop_size = k * max(w_bbox, h_bbox)
``````

若裁剪越界，仅对越界区域做 constant padding。

用途：

- 减少人工 padding 占比
- 降低 aspect ratio shortcut
- 引入真实眼周上下文
- 更贴近“中心点 + 固定方窗”的部署前处理

说明：

- `RectROI + Const Padding` 仅保留为历史参考，不再进入当前正式主线
- Stage D export ROI 必须显式输出 `square_k` 与 `pad_value_raw`

### 0.8.2 输入实验顺序

当前输入实验只在 `SquareCrop + OOB Const Padding` 主线上比较不同 `k`。

#### 0.8.2.1 第一步：固定最小方窗基线

- `SquareCrop(k=1.0) + OOB ConstPad`

#### 0.8.2.2 第二步：验证加上下文效应

- `SquareCrop(k=1.4)`
- `SquareCrop(k=1.8)`
- `SquareCrop(k=2.2)`

解释：

- `k=1.0` 作为当前正式输入基线
- `k>1.0` 用于评估额外上下文是否有助于 `eye_occluded`

### 0.8.3 ROI shortcut 观测字段

由于已经识别到模型可能利用 padding 占比、边框面积、边框位置等伪特征，因此 ROI 导出阶段必须显式记录这些观测变量。

建议在 `roi_manifest.json` 中新增：

- `crop_mode`
- `crop_w`
- `crop_h`
- `square_size`
- `bbox_w`
- `bbox_h`
- `bbox_area`
- `crop_area`
- `bbox_aspect_ratio`
- `bbox_area_ratio`
- `content_area_ratio`
- `pad_area_ratio`
- `pad_left`
- `pad_right`
- `pad_top`
- `pad_bottom`
- `oob_pad_ratio`
- `context_ratio`

#### 0.8.3.1 这些字段的作用

`pad_area_ratio` 用于衡量该样本中有多少像素来自 padding。若误分类随着该值增加而显著上升，则说明模型确实受 padding shortcut 影响。

`bbox_aspect_ratio` 用于衡量原始眼框是否过扁。若极端长宽比样本更易误分，则说明 RectROI 路线可能放大了形状偏差。

`context_ratio` 用于衡量裁剪区域相对 bbox 的上下文比例。它是分析 `occluded` 是否受益于更大真实上下文的关键变量。

### 0.8.4 Bounding Box 离线增强策略

#### 0.8.4.1 核心原则

- bbox 增强发生在裁剪 ROI 之前
- 用于模拟部署时“关键点 / 检测框 → 外接框”的偏差
- 训练集随机扰动
- 验证 / 测试集固定规则，保证可复现
- 当前正式评测仍只使用 **GT 口径**

#### 0.8.4.2 训练集 jitter（随机）

对 `B_gt` 随机扰动得到 `B_aug`，再裁剪：

- 外扩/内缩：`pad_ratio ∈ [-0.10, 0.15]`
- 平移：`dx, dy ∈ [-0.03, 0.03] × bbox_size`

约束：

- 最小宽高 `min_size`
- clamp 到图像边界
- 不重采样，失败则丢弃并统计

命名建议：

``````text
{image_id}__{eye_id}__aug{0..K-1}__{label}.jpg
``````

随机数使用样本级确定性随机：

``````text
rng_seed = sha1(seed, image_id, eye_id, aug_id)
``````

#### 0.8.4.3 验证 / 测试

当前正式评测只保留 **GT 口径**：

- `pad_ratio = 0.0`
- 或直接使用 `bbox_gt`
- 用于观察理想输入下的模型能力
- 不单独输出 `Deploy Eval`

## 0.11 模型输入与数据增强

### 0.11.1 总体原则

训练侧保持“输入生成策略”和“在线增强策略”分层：

1. Stage D 生成基础输入（仅 `SquareCrop + OOB Const Padding`）
2. 训练代码中执行轻量在线增强

目的：

- 固定输入构造版本，便于对照实验归因
- 将输入生成策略与在线增广解耦
- 保证部署前处理与训练输入更容易对齐

### 0.11.2 Stage T1：V2 基线重建时的训练增强

在 **V2 基线重建阶段**，训练配置应尽量简化，先建立最小可解释基线。

#### 0.11.2.1 推荐保留

1. `Resize` 或 `ResizeKeepRatio`
2. `SquareCrop + OOB Const Padding`
3. `RandomHorizontalFlip`
4. 轻量 `ColorJitter`
5. `ToTensor`
6. `Normalize`

#### 0.11.2.2 暂不启用

- `RandomErasing`
- 强 bbox jitter
- Weighted CE
- Focal Loss
- Label Smoothing
- 多输入策略混跑

原因：

- 先把 backbone 的训练动力学与量化表现调稳
- 避免增强、loss、输入策略同时变化，导致结论不可归因

### 0.11.3 Stage T2/T3/T4：对照实验阶段

在 T1 完成后，若基线已稳定，可在正式对照实验中继续沿用轻量在线增强。

推荐默认增强链路：

1. `SquareCrop(k) + OOB Const Padding`
2. `ResizeKeepRatio(long=128)` 或 `Resize(128, 128)`
3. `RandomHorizontalFlip`
4. 轻量 `ColorJitter`
5. `ToTensor`
6. `Normalize`

说明：

- `RandomErasing` 默认仍关闭
- 仅当后续单独验证其收益时再启用

### 0.11.4 0.11.3A 最终收敛阶段的增强约束

在联合验证的最后阶段，若目标是收敛正式候选 baseline，应进一步关闭强数据增强，只保留：

- `RandomHorizontalFlip`
- 轻量 `ColorJitter`

默认关闭：

- `RandomErasing`
- 强 bbox jitter
- 大幅颜色扰动
- 其他会显著改变局部纹理或上下文比例的增强

目的：

- 避免强增强掩盖输入构造策略本身的收益
- 让最终量化与部署对齐评估更稳定

### 0.11.5 验证 / 测试

要求：

1. 与训练保持相同输入构造逻辑
2. 不使用随机增强
3. 同版本、同 seed、同配置下结果可复现
4. 统一使用 **GT 口径**

当前正式评测定义如下：

- 使用 `bbox_gt`
- 或使用 `pad_ratio = 0.0` 的等价 GT 裁剪逻辑
- 不单独输出 `Deploy Eval`
- 所有正式指标均基于 GT 口径统计

## 0.12 训练配置

### 0.12.1 训练基线重建目标

由于 backbone 已从 `MobileNetV3` 切换到 `MobileNetV2`，原先基于 V3 的训练超参数不再直接适用。

因此正式训练流程更新为：

1. 先完成 **T1：MobileNetV2 基线重建**
2. 再开展 loss 对照实验
3. 再开展输入构造对照实验
4. 最后进行联合优化验证

### 0.12.2 Stage T1：MobileNetV2 基线重建配置

#### 0.12.2.1 固定项

- Backbone：`MobileNetV2`
- Loss：`CrossEntropyLoss`
- 单一部署对齐输入基线：`SquareCrop(k=1.0) + OOB Const Padding`
- 输入尺寸：`128 × 128`
- Batch size：`1024`
- Workers：`128`
- Optimizer：`AdamW`
- Scheduler：`CosineAnnealingLR`
- Epoch：`100`
- AMP：开启
- DDP：关闭

#### 0.12.2.2 搜索项

Learning Rate：

- `1e-3`
- `2e-3`
- `3e-3`

Weight Decay：

- `0`（仅 `lr=1e-3` 补充）
- `1e-5`
- `1e-4`
- `5e-4`

EMA：

- `on`
- `off`

#### 0.12.2.3 选择标准

统一记录：

- `FP32 Macro-F1`
- `Quant Macro-F1`
- `Drop = FP32 - Quant`

优先级：

1. 若量化结果已接通，以 `Quant Macro-F1` 更高优先
2. 若量化结果尚未接通，以 `test_fp32/Test Macro-F1` 更高优先
3. `Drop` 更小
4. 训练过程更稳定
5. FP32 与量化结果一致性更好

### 0.12.3 Stage Gate 机制

目的是避免在不稳定基线上继续扩展 loss 或输入实验。

#### 0.12.3.1 T1 -> T2/T3 进入条件

只有满足以下条件，才进入 loss 或输入构造对照阶段：

- 已确定单一 `MobileNetV2` baseline
- 若量化链路已接通，`Quant Macro-F1` 已稳定且 `Drop` 可接受
- 若量化链路尚未接通，`test_fp32` 已完成并可确定单一 CE baseline
- 同配置重复实验结果无明显漂移
- GT 口径下 confusion matrix 主迁移方向稳定

#### 0.12.3.2 T2（loss）结束条件

只有在以下条件成立时，某 loss 方案才视为优于 baseline：

- `Quant Macro-F1` 持续高于 CE baseline
- `eye_open` 的 Precision 未明显恶化
- confusion matrix 主迁移方向未显著恶化

#### 0.12.3.3 T3（input）结束条件

输入方案优化必须回答两个问题：

1. `SquareCrop(k=1.0)` 是否验证“减 padding”有效
2. `k>1.0` 是否对 `eye_occluded` 带来稳定增益

若不能稳定回答上述问题，则不继续放大上下文尺度。

### 0.12.4 Stage T2/T3/T4 配置约束

在完成 T1 后，后续训练统一遵循以下约束：

- 除被比较变量外，其余配置保持不变
- T2 仅改 loss
- T3 仅改输入构造
- T4 才允许组合最优项进行联合验证
- 所有正式实验均绑定：
  - `source_version`
  - `split_version`
  - `input_version`
  - `train_cfg_version`
  - `eval_protocol_version`
  - `preprocess_spec_version`
  - `quant_calib_version`

### 0.12.5 指标

统一关注：

- `Macro-F1`
- `Accuracy@1`
- `Macro-Precision`
- `Macro-Recall`
- 各类别 `Precision / Recall / F1`
- `FP32 / Quant / Drop`

重点关注：

- `eye_narrow` 的 Recall / F1
- `eye_occluded` 的 Recall / F1
- `eye_open` 的 Precision 是否显著下降
- 量化前后 confusion matrix 的迁移方向是否一致

## 0.13 Loss 策略约束

### 0.13.1 Weighted CE

历史经验表明：

- 权重过强会导致大类决策边界受损
- 典型现象是 `open -> narrow` 明显增加

因此当前策略为：

- 若重验，加权从温和版本开始
- 采用 `1 / sqrt(freq)` 类形式
- 对权重做 clip 限制范围

说明：

- Weighted CE 只能在 T1 稳定基线上验证
- 不允许在 backbone 未稳定时直接作为主线

### 0.13.2 Focal Loss

历史现象表明：

- `narrow -> closed`
- `open -> narrow`

在 Focal 下恶化明显。

当前判断：

- 当前任务的主要矛盾不太像“hard sample 学得不够”
- 更可能是 `narrow` 本身属于连续边界类，且含有噪声样本或模糊样本
- Focal 强调 hard sample，可能会把边界推得更紧

因此：

- Focal 不作为优先主线
- 若重验，只从小 `gamma` 开始
- 且必须在 V2 稳定基线上验证

### 0.13.3 Label Smoothing

历史经验显示 Label Smoothing 进一步模糊：

- `open`
- `narrow`
- `occluded`

之间的边界。

因此：

- 不作为默认项
- 仅保留为辅助验证项
- 不进入当前正式主线

## 0.16 narrow 与 occluded 的分治分析

这是当前正式方案新增的重点。因为 `eye_narrow` 与 `eye_occluded` 的问题机制不同，不能继续放在同一优化假设下。

### 0.16.1 eye_occluded：上下文专题分析

当前判断：

- `eye_occluded` 更像输入信息不足问题
- 更依赖：
  - 镜框
  - 发丝
  - 手部
  - 阴影
  - 上下眼周上下文

因此重点观察：

- `SquareCrop(k=1.0)` 是否提升 `occluded Recall/F1`
- `k>1.0` 是否继续提升 `occluded Recall/F1`
- `occluded -> open` 是否下降
- 提升是否集中于特定 `accessory / illumination / scene`

建议输出专题报告：

``````text
occluded_context_report.json
``````

建议统计字段：

- `Recall/F1 by input_version`
- `Recall/F1 by context_ratio bucket`
- `occluded -> open` by accessory
- `occluded -> open` by illumination
- `occluded -> open` by pad_area_ratio

### 0.16.2 eye_narrow：边界类专题分析

当前判断：

- `eye_narrow` 不只是普通小类召回不足
- 更可能来自：
  - 类别定义连续
  - 标注边界模糊
  - 中间态天然不稳定

因此重点观察：

- `open -> narrow`
- `narrow -> closed`
- `closed -> narrow`
- 高置信误分类是否集中于 narrow
- 是否集中在特定动作段、模糊帧、边界帧

建议输出专题报告：

``````text
narrow_boundary_report.json
``````

建议统计字段：

- 相邻类别混淆对统计
- 高置信误分类占比
- confidence / margin 分布
- 误分类样本抽检结论
- 是否存在标注标准不一致

## 0.17 最终实验主线

正式实验主线按以下顺序推进：

### 0.17.1 Stage T1：MobileNetV2 基线重建

- 固定单一输入基线：`SquareCrop(k=1.0) + OOB Const Padding`
- 固定 CE
- 扫 `lr / wd / EMA / 轻量增广`
- 以 Quant 表现优先选 baseline

### 0.17.2 Stage T2：Loss 对照实验

- 只改 loss
- 其余保持不变
- 重点验证：
  - 温和 Weighted CE
  - 小 gamma Focal
  - Label Smoothing 辅助验证

### 0.17.3 Stage T3：输入构造对照实验

- 固定 `SquareCrop + OOB Const Padding`
- 只比较 `k=1.0 / 1.4 / 1.8 / 2.2`
- 不再将 `RectROI + ConstPad` 作为当前正式主线输入

### 0.17.4 Stage T4：联合验证

- 仅组合 T2/T3 中最优项
- 评估联合收益是否真实存在
- 若联合后量化掉点扩大，则不进入正式 baseline
- 最终收敛阶段关闭强数据增强

## 0.18 当前正式结论

在当前约束下，正式方案更新为：

1. split 主键仅使用 `group_id = f(person_id)`  
2. 仅使用 `total_samples >= N_min` 作为 `val/test` 候选门槛  
3. 暂不引入时序约束、覆盖度约束与受约束分配  
4. 正式训练输入主线统一切换到 `const padding`  
5. `SquareCrop(k=1.0) + OOB Const Padding` 作为当前正式部署对齐基线  
6. `SquareCrop` 通过比较不同 `k` 拆解上下文比例效应  
7. MobileNetV2 必须先完成正式 baseline 重建  
8. baseline 选择以 `Quant Macro-F1` 为主导指标  
9. 训练/量化/部署预处理协议必须版本化并写死  
10. ROI 导出必须记录 shortcut 观测字段  
11. 测试阶段必须输出全量 trace 文件  
12. `eye_narrow` 与 `eye_occluded` 必须分别进行专题分析  
13. 所有正式实验必须绑定完整版本信息  
14. 正式评测仅使用 GT 口径  
15. 只有通过阶段 gate 的方案才允许进入下一阶段  
16. Stage A/B/C/D 必须支持增量更新与幂等恢复  
17. 冻结 benchmark 上不得因增量数据导致历史测试集样本回流训练集
