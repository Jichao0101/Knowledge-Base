## 2. 已同步的实现差异

### 2.1 输入模式与数据路径

- 采集模式不再从飞书表格读取或要求数据路径，只读取 Jira ID、责任人、概要、描述、车型、版本、区域和分析标记等入口上下文。
- Jira Parser 采集全部评论后，`resolve_jira_data_path.py prepare` 提取路径片段、评论原文和检索词；Agent/LLM 在固定共享根 `\\192.168.1.111\Global_VIP\J6B_DMSRain` 对应的授权访问根下容错召回候选。
- LLM 只负责候选召回和排序。`validate` 负责唯一性、存在性、目录类型、可读性和根目录边界校验，并保留 `canonical_path`、`access_path`、comment ID 和候选数。
- 无提示、零候选、多候选、根目录不可访问、路径不存在、不可读或越界时输出 `blocked_user_confirmation` 并停止；用户确认仍不能绕过硬校验。
- 直接日志模式跳过飞书、Jira、Evidence Package 和自动 Jira 写回，只处理用户明确授权路径。

### 2.2 Evidence Package v2

- Builder 从三输入升级为四输入，新增强制 `path_resolution.json`。
- Builder 校验 Lark/Jira/path resolution 的 Jira ID 一致、解析状态为 `resolved`、`continue_allowed=true`，以及解析 `access_path` 与 Data Loader 清单源路径一致。
- Package 同时记录实际 `data_path`、规范 `canonical_data_path`、四个输入 hash 和 `data/path_resolution.json`；待用户确认路径不能进入 partial package。

### 2.3 R 核规则与反向分析

- R 核 strategy 已同步项目来源 SHA-256 `70745baf9fe48903b9fdc57dc0da196fa5500e306ed8a54f81935a053466486f`，schema/revision 为 4，细分状态为 `reference_ready/analyser_not_implemented`。
- 已同步六类行为的间歇 `false` 容忍窗口、抽烟完整规则、危险报警规范信号、遮挡/无人脸高优先级及仍未定义的规则边界。
- 分析顺序改为从正式 `WrngIndReq` 反向读取 R 核内部状态、计时和门禁，再读取 R 核收到的感知输入。
- 每个事件分开记录正标签段、每次间歇、间歇次数/合计、墙钟跨度、正标签合计和 R 核内部计时峰值，不互相替代。
- R 核逻辑输出固定为 `conforming`、`nonconforming` 或 `unknown`，并分别保留依据、矛盾和缺失证据。
- 确定性 R 核 analyser、输入适配、证据 ID、结果 schema 和原子输出仍未实现；自动流水线继续为 `skipped/r_core_analyser_not_available`，不得生成 `r_core_result.json`。

### 2.4 R/A 对齐与运行时边界

- 无论 R 核三态结果为何，都必须继续分析 A 核。
- `r-a-core-alignment.md` 已定义 A 核 fuse/atomic/model 输出、映射前枚举与 R 核接收值的反向对齐，并检查延迟、丢失、重复、乱序和陈旧数据。
- J6B 视线分心 A→R 映射和常见日志别名以内置版本化规则提供；普通 case 运行时不访问源码或协议，不根据单 case 相关性猜测或修改枚举语义。
- 同一物理日志同时包含 A/R marker 时保留统一源路径和物理行号，按 marker 逻辑分流；禁止用未来 A 核样本解释此前 R 核已消费输入。
- 运行 profile 与内置映射兼容性无法确认时必须标记 `mapping_version_unverified` 并降低结论强度。
