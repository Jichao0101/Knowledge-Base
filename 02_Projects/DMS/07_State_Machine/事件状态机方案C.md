# 1 目标

在 hamper 滤波、泄露积分、二值滞回之后，输入已经是相对稳定的帧级二值结果 `b_t`。
但该结果仍然只表示“当前帧是否为正”，无法直接表达以下事件级语义：

- 一个行为事件是否真正开始
- 当前事件是否已被确认
- 当前事件是否因短时掉点而被误切断
- 当前是否应立即触发单次事件报警
- 最近窗口内累计事件时长是否超过阈值
- 用户主动取消报警后，短时间内是否应抑制重复报警
- 当前工况不满足条件时，事件是否应继续计时与累计

因此，需要在帧级二值判定之后增加**事件状态机层**，并在其外侧进一步增加**工况门控层**与**报警仲裁层**，将逐帧结果转换成可用于量产系统的事件级输出。

该方案的目标输出包括：

1. 当前进行中的事件
2. 已结束的历史事件队列
3. 单事件报警量
4. 窗口累计报警量
5. 用户取消报警后的抑制结果
6. 工况无效时的计时冻结/终止控制结果

## 1.1 模块边界说明  
  
本模块负责基于帧级二值结果进行事件级建模，输出单事件触发量、窗口累计触发量及相关事件状态。  
  
本模块不负责以下策略：  
- 基于车速阈值的报警提示使能  
- 低速到高速切换时的补报/延时报策略  
- 多类型报警之间的优先级仲裁  
- 最终视觉/听觉报警提示输出  

---


# 2 总体架构

优化后的方案分为三层：

## 2.1 行为观测层

输入：
- 当前帧原始行为检测结果

输出：
- 帧级二值结果 `b_t`

该层只负责回答当前帧是否检测到目标行为，不负责事件定义、报警定义或交互控制。

## 2.2 事件状态机层

输入：
- 帧级二值结果 `b_t`
- 计时使能信号 `count_enable`

输出：
- 当前事件状态
- 当前事件持续时长
- 历史事件队列
- 窗口累计时长
- 原始报警量

该层负责：

- 短段剔除
- 小间隙桥接
- candidate / active 状态演化
- 当前事件持续时长计算
- 历史事件写入与裁剪
- 单事件报警判定
- 窗口累计报警判定

## 2.3 报警仲裁层

输入：
- 原始单事件报警量
- 原始窗口累计报警量
- 用户取消报警信号
- 报警抑制状态

输出：
- 最终对外输出报警量

该层负责：

- 用户取消报警后的静音控制
- 短时间内禁止重复播报
- 风险未解除前禁止重复触发
- 将“事件是否成立”与“报警是否输出”解耦

---


# 3 输入输出定义

## 3.1 输入

对单一行为类型（例如闭眼）而言，每帧输入包括：

- `t`：当前帧号
- `b_t ∈ {0,1}`：该行为的帧级二值结果
- `count_enable ∈ {0,1}`：当前帧是否允许事件状态机继续计时
- `cancel_alarm ∈ {0,1}`：当前帧是否收到用户取消报警信号

其中：

- `b_t = 1`：当前帧检测为正
- `b_t = 0`：当前帧检测为负
- `count_enable = 1`：当前工况满足行为计时条件
- `count_enable = 0`：当前工况不满足计时条件，不应继续积累行为时长
- `cancel_alarm = 1`：用户在当前帧触发取消报警动作

---


## 3.2 输出

每帧输出以下中间结果或最终结果：

- `state`：当前状态机状态
- `active_duration`：当前进行中事件持续时长
- `window_duration`：统计窗口内累计事件时长
- `alarm_single_raw`：单事件原始报警标志
- `alarm_total_raw`：窗口累计原始报警标志
- `alarm_single_out`：单事件最终输出报警标志
- `alarm_total_out`：窗口累计最终输出报警标志

其中：

- `alarm_single_raw`、`alarm_total_raw` 由事件状态机直接产生
- `alarm_single_out`、`alarm_total_out` 由报警仲裁层在考虑静音期后给出

---


# 4 参数定义

对每个行为类型分别配置参数。



| 参数 | 含义 | 建议说明 |
| --- | --- | --- |
| `L_min` | 最小事件长度 | 小于该阈值的候选段视为短段误检 |
| `G_max` | 最大桥接间隙 | 小于等于该阈值的负段仍视为同一事件内部掉点 |
| `D_single` | 单事件报警阈值 | 当前单个事件持续时长超过该阈值时立即报警 |
| `W` | 窗口长度 | 窗口累计统计长度 |
| `D_total` | 窗口累计报警阈值 | 窗口内总事件时长超过该阈值时报警 |
| `T_sup` | 报警抑制时长 | 用户取消报警后，静音持续时间 |
| `v_on` | 车速使能上阈值 | 车速升高到该值以上时使能计时 |
| `v_off` | 车速使能下阈值 | 车速降低到该值以下时关闭计时 |



## 4.1 约束关系

#### 4.1.1.1 事件内约束


$$
G_{max} < L_{min}
$$


原因：

- 若 `G_max` 过大，容易将本应独立的两个事件误合并
- 若 `G_max >= L_min`，状态机会过度偏向“不断事件”，削弱短段剔除能力

#### 4.1.1.2 工况门控约束


$$
v_{off} < v_{on}
$$


原因：

- 若车速启停共用同一阈值，车速在边界附近抖动时会频繁启停
- 启停抖动会导致事件碎裂、历史队列频繁写入、报警逻辑不稳定

---


# 5 数据结构设计

## 5.1 当前事件结构

当前未结束事件单独维护，不放入历史队列。

```cpp
struct CurrentEvent {
    bool exists = false;       // 当前是否存在事件
    bool confirmed = false;    // 是否已从candidate升级为active
    int start = -1;            // 事件起始帧
    int last_pos = -1;         // 最近一次正帧位置
    int gap = 0;               // 当前连续负帧数
};
```


字段解释：

- `exists`
  - 表示当前是否存在一个候选或活动事件

- `confirmed`
  - `false` 表示 candidate
  - `true` 表示 active

- `start`
  - 当前事件起点

- `last_pos`
  - 最近一次 `b_t = 1` 的帧号
  - 用于在 `gap` 超阈值时确定真实结束位置

- `gap`
  - 当前连续负帧数
  - 用于小间隙桥接判断

---


## 5.2 历史事件结构

```cpp
struct Event {
    int start;
    int end;
    int duration;
};
```


历史事件队列：

```cpp
std::deque<Event> history_events;
```


约束：

`history_events` 中只保存：

- 已结束
- 且已确认成立

的事件。

---


## 5.3 报警控制结构

为支持用户取消报警、静音期与重新武装逻辑，需要增加报警控制状态。

```cpp
struct AlarmControl {
    bool suppress_active = false;   // 当前是否处于报警抑制期
    int suppress_end = -1;          // 抑制结束帧
};
```


字段解释：

- `suppress_active`
  - 表示当前是否处于取消报警后的静音期

- `suppress_end`
  - 抑制期结束帧号

---


## 5.4 运行时上下文结构

为了统一维护事件状态、历史队列和报警控制状态，可定义统一上下文。

```cpp
struct RuntimeContext {
    CurrentEvent cur;
    std::deque<Event> history_events;
    AlarmControl alarm_ctrl;
};
```


该结构用于保存：

- 当前事件状态
- 历史事件队列
- 报警抑制状态

---


# 6 状态定义

事件状态机逻辑上分为四个状态：

- `inactive`
- `candidate`
- `active`
- `ended`

实际代码里可以不单独存 `ended`，而是在“结束条件满足时执行一次结束动作后直接回到 inactive”。

---


## 6.1 inactive

当前没有任何事件在进行。
系统等待新的正状态进入。

判断方式：

- `!cur.exists`

---


## 6.2 candidate

已经检测到正状态起点，但尚未满足最小事件长度 `L_min`。
此时事件仍可能只是短脉冲误检。

判断方式：

- `cur.exists && !cur.confirmed`

---


## 6.3 active

当前事件已经达到最小长度阈值，被确认为真实事件。
但事件尚未结束。

判断方式：

- `cur.exists && cur.confirmed`

---


## 6.4 ended

不是长期驻留状态，而是一次转移动作：

- 计算结束位置
- 若 `confirmed` 为真则写入队列
- 清空当前事件
- 回到 `inactive`

---


# 7 原始事件状态转移逻辑

下面给出在 `count_enable = 1` 时，单行为通用状态转移表。

## 7.1 记号说明

- `dur_now = t - cur.start + 1`
- `end = cur.last_pos`

---


## 7.2 状态转移表



| 当前状态 | 条件 | 动作 | 下一状态 |
| --- | --- | --- | --- |
| inactive | `b_t == 0` | 无操作 | inactive |
| inactive | `b_t == 1` | 初始化 `cur`：`exists=true, confirmed=false, start=t, last_pos=t, gap=0` | candidate |
| candidate | `b_t == 1` | `last_pos=t, gap=0`；计算 `dur_now`；若 `dur_now >= L_min` 则 `confirmed=true` | candidate 或 active |
| candidate | `b_t == 0 && gap+1 <= G_max` | `gap++`，不结束，继续等待 | candidate |
| candidate | `b_t == 0 && gap+1 > G_max` | 候选事件结束；因未确认，不写队列；清空 `cur` | inactive |
| active | `b_t == 1` | `last_pos=t, gap=0` | active |
| active | `b_t == 0 && gap+1 <= G_max` | `gap++`，保持 active | active |
| active | `b_t == 0 && gap+1 > G_max` | 事件结束；`end=last_pos`；写入 `history_events`；清空 `cur` | inactive |



---


# 8 工况门控机制设计

## 8.1 设计动机

原始事件状态机默认每一帧都参与计时与统计，但在实际车载系统中，并非所有时刻都应纳入疲劳/分心行为评估。
例如在以下工况下，系统通常不应继续积累事件时长：

- 车速不满足条件
- 档位不满足条件
- 主驾不在位
- DMS/OMS 系统未激活
- 图像质量不满足要求
- 整车策略要求暂时关闭该行为监测

如果不对这些工况做门控，则会出现以下问题：

- 在无效工况下仍累计闭眼/分心时长
- 低速停车阶段异常积累窗口时长
- 驾驶开始前已经形成历史风险状态
- 状态机跨无效工况错误拼接两个本应独立的事件

因此，需要在事件状态机外增加**计时使能控制层**。

---


## 8.2 计时使能信号定义

定义：

- `count_enable = 1`：当前帧允许事件状态机演化
- `count_enable = 0`：当前帧不允许事件状态机继续计时

---


## 8.3 车速门控滞回

设：

- `v_on`：车速使能上阈值
- `v_off`：车速失能下阈值

机制如下：

- 当车速从低到高超过 `v_on` 时，进入计时使能状态
- 当车速从高到低低于 `v_off` 时，退出计时使能状态
- 在 `v_off < v < v_on` 区间内保持原状态不变

这样可以显著降低事件碎裂风险。

---


## 8.4 工况失效时的处理策略

对于 `count_enable = 0` 时如何处理当前事件，有
### 8.4.1 策略 ：工况失效时终止当前事件

即当 `count_enable` 从 1 变为 0 时：

- 若当前为 candidate，则直接丢弃
- 若当前为 active，则以 `last_pos` 为结束位置进行收尾
- 收尾后清空当前事件
- 禁用期间不再继续推进状态机

该策略的优点是：

- 不跨无效工况拼接事件
- 工况语义清晰
- 事件持续时间只覆盖有效驾驶区间
- 更符合量产逻辑

该策略是推荐方案。

---


### 8.4.2 策略 ：工况失效时整体清零

即只要 `count_enable = 0`：

- 清空当前事件
- 清空历史队列
- 所有统计归零

该策略最简单、最干净，但会丢失已有有效工况信息。
对于窗口累计报警不够友好，只有在业务明确要求“离开有效工况后重新开始计算”时才适合使用。
---


# 9 关键机制解释

## 9.1 为什么 candidate 和 active 要分开

主导约束是：

短段剔除需要等待长度确认，不能一出现正帧就算真实事件。

如果没有 candidate：

- 一帧误检就会启动真实事件
- 后续会直接污染单事件报警和窗口累计报警

所以：

- `candidate` 负责观察
- `active` 负责确认后的正式计入

---


## 9.2 为什么 gap 内 active 不立即结束

主导约束是：

真实行为事件内部经常会出现 1~2 帧甚至更长一点的掉点。

来源包括：

- 分类抖动
- ROI 轻微漂移
- 遮挡
- 特征短时失稳

如果 `b_t = 0` 就立即结束，会把一个完整事件切成多个碎段。
因此需要 `gap` 计数器：

- `gap <= G_max`：仍视为同一事件
- `gap > G_max`：才认为真正结束

---


## 9.3 为什么结束帧取 `last_pos` 而不是当前 `t`

当 `gap > G_max` 时，说明：

- 最近的若干帧已经是负帧
- 真实事件早在最后一个正帧就结束了

因此结束位置必须用：


$$
end = last\_pos
$$


否则会把桥接失败后的负帧错误计入事件时长。

---


# 10 时长计算规则

## 10.1 active 事件当前持续时长

当当前事件存在且 `count_enable = 1` 时，定义：


$$
active\_duration = t - start + 1
$$


这里使用连续时间轴口径。
也就是说，只要 `gap <= G_max`，即使当前帧为 0，事件仍视为连续。

原因在于：

桥接逻辑已经定义“小 gap 不应打断事件”，
那么时长也必须保持连续，否则“事件连续性定义”和“时长定义”会互相矛盾。

---


## 10.2 已结束事件时长

事件结束并写入队列时：


$$
duration = end - start + 1
$$


其中：


$$
end = last\_pos
$$


---


# 11 窗口累计统计

## 11.1 窗口定义

当前帧 `t` 下，窗口定义为：


$$
[L, R] = [t - W + 1,\ t]
$$


---


## 11.2 历史事件对窗口的贡献

对队列中每个事件 `[start_i, end_i]`，其在窗口内的贡献为：


$$
contrib_i = \max(0,\ \min(end_i, R) - \max(start_i, L) + 1)
$$


---


## 11.3 active 事件对窗口的贡献

若当前存在 active 事件，则其临时区间视作：


$$
[start,\ t]
$$


其窗口贡献为：


$$
contrib_{active} = \max(0,\ t - \max(start, L) + 1)
$$


---


## 11.4 窗口累计总时长


$$
window\_duration = \sum_i contrib_i + contrib_{active}
$$


其中：

-
$$
\sum_i contrib_i
$$
：历史事件贡献
- `contrib_active`：当前进行中事件贡献

---


## 11.5 工况失效时的窗口行为

在推荐方案下，工况失效边沿会先终止当前事件，因此：

- 禁用期间不会再新增 active 贡献
- 已结束历史事件仍可根据当前窗口位置继续参与裁剪统计
- 随着真实时间推进，旧事件会自然滑出窗口

因此窗口统计仍基于真实时间轴，而非有效计时时间轴。
这种定义实现简单、语义自然，也便于与其他整车时间逻辑对齐。

---


# 12 队列裁剪规则

仅保留可能与当前窗口有交集的事件。

若：


$$
event.end < L
$$


则说明该事件已完全落在窗口左边界之外，可以删除。

因此：

- `history_events` 不需要无限增长
- 队列长度受 `W` 约束
- 在线系统内存占用可控

---


# 13 报警判定逻辑

## 13.1 原始单事件报警

当存在 active 事件且：


$$
active\_duration \ge D_{single}
$$


则：

- `alarm_single_raw = true`

作用：

用于识别：

- 长闭眼
- 长打哈欠
- 长时间低头/视线偏移
- 长时间打电话/抽烟动作持续

---


## 13.2 原始窗口累计报警

当：


$$
window\_duration \ge D_{total}
$$


则：

- `alarm_total_raw = true`

作用：

用于识别：

- 多次短闭眼
- 多次短分心
- 多个短事件在窗口内累计达到风险水平

---


# 14 报警抑制机制

## 14.1 设计动机

原始事件状态机能够判断“风险是否存在”，但在车载交互中，还需要处理以下问题：

- 用户已经看到报警并主动点击取消
- 用户取消后，短时间内不应重复播报
- 若风险持续存在，系统是否应在静音结束后立刻再次报警

这些问题不应通过修改事件本体来解决，因为：

- 事件是否存在，是行为层语义
- 是否对外报警，是交互层语义

二者属于不同层级，必须解耦。

---


## 14.2 报警抑制机制

当用户触发 `cancel_alarm` 后，系统进入报警抑制期。

抑制期定义为：


$$
[t_{cancel},\ t_{cancel} + T_{sup} - 1]
$$


在该时间段内：

- `alarm_single_out = false`
- `alarm_total_out = false`

但事件状态机本身仍可继续运行，
即：

- 当前事件可以继续存在
- `active_duration` 可以继续增长
- `window_duration` 可以继续累加
- `alarm_single_raw`、`alarm_total_raw` 可以继续计算

这意味着抑制只影响“输出”，不影响“风险建模”。

---


## 14.3 为什么抑制期不停止事件计时

如果用户取消报警后同时停止事件计时，则会带来两个问题：

- 风险仍在持续，但系统内部却认为事件中断
- 静音期结束后，系统无法准确判断是否仍存在连续风险

因此用户取消报警本质上应理解为：


> 暂时不要提示用户，而不是风险已经消失



所以取消报警应只作用于报警仲裁层，而不应改写事件状态机。

---


## 14.4 最终报警输出定义

最终报警量由共同决定：

1. 原始风险是否成立
2. 当前是否处于抑制期

因此：

- `alarm_single_out` 由 `alarm_single_raw`、抑制状态共同决定
- `alarm_total_out` 由 `alarm_total_raw`、抑制状态共同决定

其语义是：

- `raw` 表示风险存在
- `out` 表示允许真正对外提示
