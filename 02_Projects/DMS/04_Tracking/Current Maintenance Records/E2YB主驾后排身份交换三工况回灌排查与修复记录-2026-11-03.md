本次排查针对主驾与后排身份交换。复现输入来自 `/home/jichao/dms/dumps/{distraction,handoff,faceid}`，运行于 `root@192.168.1.10` 的 `/userdata/dms`。以下结论只覆盖这些样本，不代表其他车型、摄像头安装位置或全部驾驶姿态已完成标定。

Face ID 基线在输入时间戳 300000 μs 已复现交换：`face=0` 对应后排，框约为 `(808,675,148,193)`，却被发布为 DRIVER；`face=1` 对应实际驾驶员，框约为 `(1087,719,260,314)`，被发布为 BACK_PASSENGER。截图中的位置、检测日志和序列化 Face map 相互对应。

## 为什么会交换

E2YB 原始配置继承 DEFAULT 的 `driver_face_anchor=(960,620)` 和 `smallFaceAreaRatio=0.005`。Face ID 样本后排脸中心约在 `(880–963,748–822)`，实际驾驶员脸通常更靠右。两人同时通过候选过滤时，初始选择主要由到锚点的距离决定，旧锚点更接近后排脸；原始小脸阈值也不足以滤除该后排脸。

误选还会被后续状态更新放大：`DmsTrack::Update` 将未选中的原 DRIVER 降为 BACK_PASSENGER 并清零 `driverCount`；而 `selectDriverFace` 会拒绝稳定 BACK_PASSENGER 候选。这样，即使实际主驾仍被检测到，也可能因上一轮降级而暂时无法重新参与选择。该机制说明为什么一次不合适的初始选择会持续影响身份输出，而不是仅造成单帧抖动。

脱手工况还暴露了独立的 ROI 边界问题：3.8 秒附近，实际驾驶员前倾后脸中心约为 `(450,923)`，落在旧主驾 ROI 左边界 620 之外。到 4.6 秒重新进入主驾 ROI 后，稳定 BACK_PASSENGER 分类仍会继续影响恢复。图片与检测框均支持该判断。

## 修复范围

修复包含两处代码调整和 E2YB 配置标定。代码在 `selectDriverFace` 移除对历史稳定 BACK_PASSENGER 的硬拒绝，继续保留当前帧主驾 ROI、副驾 ROI 排除、小脸过滤、hit/miss 条件和原有评分。累计类型投票仍用于其他乘员的分类输出。仅标定配置的对照回灌仍有 83/392 帧无主驾：3.8–6.2 秒的主驾框已满足当前几何与面积条件，但所继承轨迹有 28 张历史后排票。这组证据支持解除历史类型硬门禁。

扩大主驾 ROI 还会与副驾 ROI 重叠。原 `computePersonType` 先判断主驾区域，使副驾可能先经过主驾小脸规则而被累计为 BACK_PASSENGER；第一版 SDK 的分心回灌中出现了该副作用。因此最终实现将副驾 ROI 的判断前置，与 `selectDriverFace` 本已排除副驾 ROI 的规则保持一致。该调整保留原副驾区域，不扩展到新的座位标定。

同时通过配置修正车型先验，保持 `DmsTrack` 的状态结构、匹配公式、public/private API 与四类输出 map 不变。仅在 `etc/track_params.json` 的 E2YB 节点覆盖以下参数：

| 配置 | 原值（继承 DEFAULT） | 修正值 |
|---|---|---|
| `threshold.face.smallFaceAreaRatio` | 0.005 | 0.01 |
| `presets.driver_face_anchor` | (960,620) | (1200,800) |
| `presets.driver_region` | (620,450,980,900) | (400,450,1200,900) |

扩展 ROI 左边界以覆盖前倾时的主驾脸中心，右边界保持 1600；保留其他阈值和其他车型配置。代码门禁修复对共享跟踪逻辑生效，其他车型未运行回灌，不能据此宣称其行为已验收。已保存的 Face ID 基线中，后排脸面积占比约 0.54%–0.78%，实际驾驶员约 1.13%–3.44%；Face ID 的 0.9% 初始候选位于该样本的两组观测区间之间；但脱手后排脸的面积占比最高达到约 0.94%，因此最终使用 1.0%。已发布的脱手实际主驾脸最小约 1.10%。该数值来自当前样本，不能直接作为其他安装位置的通用阈值。

没有新增 helper/type，public/private API 和 ABI 无变化；移除了被替代的硬拒绝及其日志分支，类型投票相关代码仍承担非主驾分类职责。

## 回灌与验收

按用户边界未运行测试套件。最终代码使用 `bash scripts/compile_j6b.sh` 全量编译成功，`git diff --check` 通过；部署文件逐字节回读校验。

板端没有 `bash`，实际使用兼容的 `cd /userdata/dms; sh run.sh`。每次切换输入前删除 `/ota` 上一组数据，再上传下一组；同一组保留原始 SDK/配置的基线，并与最终 SDK/配置回灌对照。首轮 Face ID 基线按本次运行的日志文件时间戳归档，其余回灌使用独立日志目录，避免与板端同时运行的业务进程日志混淆。输入末尾到达后，确认最后一张图片的序列化输出，再停止本次 SDK；SDK 主循环不会自行退出，输入耗尽报错不能当作新的跟踪故障。

多线程输入与计算速度不同，有效序列化输出数可能小于 manifest 行数。验收分别报告输入帧数、有效输出数、无主驾输出及前后共同时间戳；不把输入读完等同于全部输入帧均经过跟踪验证。序列化 map 为空的帧单独计数，不将其当作正确跟踪。

身份核对先使用对应图片确认实际驾驶员与其他乘员，再按本样本观测到的、互不重叠的位置与面积区间批量统计：Face ID 与脱手中的实际驾驶员已发布脸框面积大于 40000 px²，后排脸小于该值；分心中主驾中心 x 大于 900，副驾在其左侧。该规则只用于这三组数据的证据核对，不是通用座位分类算法，也不等于逐帧人工标注。

三组最终回灌使用同一 SDK 和同一配置，每组均确认最后一张图片已有序列化输出。数据与有效输出规模如下：

| 工况 | 输入帧 | 基线有效输出 | 最终有效输出 | 最终主驾输出 | 最终无主驾输出 |
|---|---:|---:|---:|---:|---:|
| Face ID | 600 | 401 | 345 | 324 | 21 |
| 脱手 | 599 | 410 | 364 | 307 | 57 |
| 分心 | 600 | 411 | 398 | 394 | 4 |

前后多线程运行的有效时间戳不完全相同，因此身份误分配还按共同时间戳对照：

| 工况 | 共同时间戳数 | 后排误主驾：基线 → 最终 | 主驾误后排：基线 → 最终 |

最终 1107 帧有效输出中未发现目标身份误分配，也没有同帧多个 DRIVER。分心组 394 帧有效乘员输出中的副驾均保持 FRONT_PASSENGER。仍有 82 帧无主驾输出，涉及初始化、遮挡、检测不足及推理失败；这些帧不计为正确主驾跟踪。

基线也有 DNN 100 ms 超时：Face ID/脱手/分心分别为 0/2/1 条，最终运行分别为 2/2/1 条。回灌均继续到最后一张图片；这些运行异常单独保留在控制台日志，不把它们归因为跟踪类型门禁，也不宣称本次已修复 BPU 调度或检测召回。六份基线/最终归档的序列化记录均可解析，未发现重复时间戳或解析失败。
