# 1 结论

当前 `DmsTrack` 的外部深模块边界仍然合理，`DmsTrack::Init()` / `DmsTrack::Update()` 不需要拆成 public-facing 的 FaceTracker、BodyTracker、HandTracker。最新实现把重复的矩阵构造、dummy block、匹配解析统一收敛到一个内部 assignment 基础设施，主流程只保留阶段编排与状态更新。

推荐目标不是第一步拆成 public-facing `FaceTracker`、`BodyTracker`、`HandTracker`，而是在保持 `DmsTrack` 深接口的前提下形成三层内部结构：

1. `DmsTrack::Update` 和三个 `update*Tracks` 只负责阶段编排与状态容器选择。
2. 匹配、候选、生命周期、运动状态更新和发布由窄职责 helper 或 private/internal 协作对象承担。
3. loss、ROI、anchor、gate、sanitize 等无状态计算保持为匿名 namespace 内纯函数。

这里的“不拆 public-facing 子类”不等于“不要增加类型”。若新类型能够隐藏一组稳定规则、拥有清晰契约、不会把状态协调转移给调用方，则可以作为 private/internal 的深模块拼装单元。

重构必须保持：

- face track id 是 identity id 和 body/hand legacy map key。
- driver identity 只由稳定 face track 选择。
- body 仍然是 face-owned body evidence，但现在以统一 assignment 方式选择 owner-body 匹配。
- hand 只挂在允许的 driver owner 下，left/right 分槽并输出到原 legacy map。
- `m_faceTracks`、`m_bodyTracks`、`m_handTracks`、`m_retiredBodyTracks` 的生命周期语义不变。

# 2 主导可读性问题

## 2.1 流程编排与细节实现没有分层

- `Update` 已体现 `face -> driver selection -> body -> hand`，但 face identity 修正和 face 发布仍直接展开在入口中。
- `updateFaceTracks` 同时负责检测提取、预测、矩阵构造、gate、Hungarian、匹配解析、新轨迹建立和 miss 删除。
- `updateBodyTracks` 同时负责 owner 排序、tracking match、acquisition fallback、motion correction、类型投影、退休和发布。
- `updateHandTracks` 同时负责 owner 过滤、预测、first pass、second pass、slot 更新、miss、handoff 清理、过期删除和两轮发布。

## 2.2 相同机制重复，但语义差异隐藏在局部代码里

- Face、Body、Hand 现在都依赖同一个 `SolveAssignment`，差异只体现在 cost builder、gate 和命中后的状态更新。
- Face、Body、Hand 都有预测、hit/miss、删除和稳定输出门槛，但更新细节不同。
- Hand 的 slot-to-detection 逻辑仍有左右槽、owner/body gate 和 miss 推进的业务差异，需要通过 slot/owner 级别的命名保持可读性。
- 手部发布阶段仍保留 legacy 输出兼容逻辑，但不再承担核心匹配框架。

## 2.3 状态载体过于宽泛

`TrackInfo` 同时承载 box、predBox、person type、投票、生命周期和 motion state。它是公共结果类型，当前不适合为本次重构修改 ABI；但内部 helper 若都接收并任意修改整个 `TrackInfo&`，副作用边界仍不清晰。

应通过窄职责函数名和输入输出结构约束修改范围，而不是立刻拆公共类型。

## 2.4 “发布”含有隐藏生命周期副作用

`PublishSanitizedTrack` 在 sanitize 失败时会调用 `AdvanceMiss(track)`。因此它不是单纯的 map publish helper。若后续直接把它归入输出层，会继续混淆“输出失败”和“本帧跟踪未命中”。

推荐先拆为：

- `SanitizeTrackForPublish(...) -> SanitizeResult`
- `PublishTrack(...)`
- 由调用方显式决定 sanitize drop 是否推进 miss

在第一阶段只做等价拆分，仍保持当前 drop 后 `AdvanceMiss` 行为；是否应保留该算法语义另立行为变更任务。

## 2.5 owner 约束散落

Hand owner 条件同时存在于：

- `allowedHandOwners` 构造
- body map 查找
- `HandBelongsToBody`
- second pass 的 body fallback 查找
- publish 前再次检查
- retired body handoff 清理

这些判断本身合理，但缺少一个明确的 owner context，阅读者需要跨越约 300 行恢复约束。

# 3 应保留在主流程中的逻辑

## 3.1 `DmsTrack::Update`

只保留帧级业务顺序：

1. 校验初始化状态和输入。
2. 清空四类 legacy output map。
3. 更新 face identity tracks。
4. 选择唯一 driver face，并应用 driver role。
5. 发布稳定 face tracks。
6. 更新并发布 face-owned body evidence。
7. 更新并发布 driver-owned hand slots。
8. 输出帧级成功/异常日志。

`Update` 不应出现 cost matrix、卡尔曼细节、hit/miss 细节或 hand slot 细节。

## 3.2 三个 `update*Tracks`

每个函数保留该实例类型特有的阶段顺序和策略选择：

- Face：预测 -> 全局匹配 -> 命中更新 -> bootstrap -> miss/erase。
- Body：构建 bodyId 顺序 -> 统一 assignment（tracking/acquisition 取 min） -> 命中更新 -> retire -> publish。
- Hand：owner context -> predict -> 单次 slot assignment -> lifecycle cleanup -> handoff cleanup -> publish。

通用 helper 不应决定 driver-first、tracking-first、acquisition fallback 或 slot 发布细节；这些属于 DmsTrack 的业务编排。

# 4 适合抽取的内部单元

## 4.1 纯函数

- `CollectDetectionsByClass(detMap, classId)`
- `BuildFaceMatchScore(...)`
- `PassFaceMatchGate(track, detection, score, params, imageSize)`
- `FaceBelongsToBody(...)`
- `FaceAnchorLoss(...)`
- `HandBelongsToBody(...)`
- `HandAnchorLoss(...)`
- `HandMatchLoss(...)`
- `SameOccupantRegionByBodyAnchor(...)`
- `ShouldOutputTrackByHitCount(...)`
- `SanitizeDetectBoxToImage(...)`

现有大部分几何函数已经是纯函数，下一步重点是统一命名和让调用点表达“score / gate / selection”三个步骤。

## 4.2 小结构体和 private/internal 协作对象

建议先增加内部、局部语义稳定的结构体：

```cpp
struct AssignmentResult {
    std::vector<int> leftToRight;
    std::vector<int> unmatchedLeft;
    std::vector<int> unmatchedRight;
};

struct BodyMatchDecision {
    int detectionIndex = -1;
    enum class Source { None, Tracking, FaceAcquisition } source = Source::None;
    float trackingLoss = INF;
    float acquisitionLoss = INF;
};

struct HandOwnerContext {
    track_id ownerFaceId = -1;
    const TrackInfo* bodyTrack = nullptr;
    HandTrackState* handState = nullptr;
};

struct HandSlotRef {
    track_id ownerFaceId = -1;
    bool isRight = false;
};
```

不建议第一阶段引入继承层次、虚基类或通用 `Tracker<T>`。Face、Body、Hand 的 owner、bootstrap、motion model 和发布条件差异仍然较大。

但可以考虑 private/internal 协作对象，而不是 public-facing 子 tracker：

| 候选类型 | 隐藏的复杂性 | 可见性建议 | 约束 |
|---|---|---|---|
| `TrackAssignmentSolver` | dummy matrix 构造、Hungarian 调用、真实匹配解析 | private/internal | 不更新 track，不占用 detection，不打印业务日志 |
| `TrackLifecycleOps` | hit/miss/expired 的计数推进 | private/internal | 只封装机制，不决定何时 hit/miss |
| `TrackOutputSanitizer` / `TrackPublisher` | sanitize、clamp、publish 与 drop 处理 | private/internal | 第一阶段保持 sanitize drop 后 miss 的现有语义 |
| `BodyEvidenceMatcher` | driver-first owner order、tracking match、face-anchor acquisition | private/internal | 不改 owner 优先级，不改 body evidence key |
| `HandSlotMatcher` | left/right first pass、constrained second pass、slot 命中解析 | private/internal | 不放宽 owner gate，不改变 miss 推进次数 |
| `TrackConfigLoader` | DEFAULT + 车型覆盖、阈值/KF/ROI 解析 | private/internal | 不改配置路径与覆盖顺序 |

这些类型只有在后续出现跨模块复用、可替换策略或独立测试需求时，才考虑升级为半 public；当前默认不暴露给调用方。

## 4.3 匹配基础设施

推荐封装“带拒绝代价的一对一匹配”，但保留业务侧 cost callback 和 gate：

```cpp
AssignmentResult SolveAssignment(
    int leftCount,
    int rightCount,
    float rejectCost,
    const std::function<std::optional<float>(int, int)>& cost);
```

约束：

- helper 内部统一构造 `leftCount + rightCount` 方阵和 dummy blocks。
- `std::nullopt` 表示 forbidden edge，使用足够大的不可达代价。
- 只返回真实实体之间且 cost `< rejectCost` 的匹配。
- 不在 helper 内更新 track、占用 detection 或打印业务日志。

Hand first pass 当前使用 `max(2, candidateCount)` 方阵，而 Face/Hand second pass 使用 `m + n` dummy-augmented 方阵。 Hand second pass 需要同步成 Face 模式。

## 4.4 生命周期与运动更新

可统一机制，不统一策略：

- `PredictTrack(track, motionModel)`
- `MarkTrackHit(track, hitThreshold)`
- `MarkTrackMiss(track)`
- `IsExpired(track, missThreshold)`
- `UpdateFaceTrackFromDetection(...)`
- `UpdateBodyTrackFromDetection(...)`
- `UpdateHandSlotFromDetection(...)`

后三个仍应分开，因为：

- Face/Hand 命中后输出检测框。
- Body 命中路径包含当前的 correction/fusion 语义。
- Hand 首次初始化使用 CA，Face/Body 使用 CV。
- person type 投票和 owner type 投影不同。

# 5 分函数拆分建议

## 5.1 `updateFaceTracks`

推荐拆成：

1. `collectFaceDetections`
2. `predictFaceTracks`
3. `matchFaceTracks`
4. `applyMatchedFaceDetections`
5. `bootstrapUnmatchedFaces`
6. `advanceAndEraseMissedFaces`

推荐主流程：

```cpp
void DmsTrack::updateFaceTracks(...) {
    const auto detections = collectDetections(..., kFaceClassId);
    const auto faceIds = predictFaceTracks();
    const auto matches = matchFaceTracks(faceIds, detections, frameSize);
    applyMatchedFaceDetections(matches, detections, frameSize);
    bootstrapUnmatchedFaces(matches.unmatchedRight, detections, frameSize);
    advanceAndEraseMissedFaces(matches.unmatchedLeft);
}
```

低风险边界：

- 保持 `faceIds` 由 `std::map` 遍历产生的顺序。
- 保持 small-face reject、driver/non-driver distance gate 和 `< dummyLoss` 条件。
- 保持 `CorrectMotion` 调用后最终 `box = detBox`。
- 保持新 face id 分配顺序和 miss 删除时机。

## 5.2 `updateBodyTracks`

推荐拆成：

1. `collectBodyDetections`
2. `buildBodyOwnerOrder(driverFaceId)`
3. `matchExistingBodyTrack(owner, availableDetections)`
4. `acquireBodyFromFace(owner, availableDetections)`
5. `applyBodyMatch(owner, decision)`
6. `advanceAndRetireBodyTracks(matchedOwners)`
7. `publishStableBodyTracks(driverFaceId)`

`matchExistingBodyTrack + acquireBodyFromFace` 可返回 `BodyMatchDecision`，让主循环直接显示 tracking-first、acquisition-second：

```cpp
for (track_id owner : ownerOrder) {
    BodyMatchDecision decision = matchExistingBodyTrack(owner, detections, used);
    if (!decision.matched()) {
        decision = acquireBodyFromFace(owner, detections, used);
    }
    if (decision.matched()) {
        applyBodyMatch(owner, detections[decision.detectionIndex], decision.source);
    }
}
```

不要在第一阶段把 Body 改成全局 Hungarian。当前实现是 driver-first 的顺序贪心占用，改成全局匹配可能改变 detection ownership 和 owner 优先级。

## 5.3 `updateHandTracks`

Hand 应按阶段拆，不应先追求跨类型通用化：

1. `collectHandDetections`
2. `buildAllowedHandOwners`
3. `predictInitializedHandSlots`
4. `runOwnerLocalHandPass`
5. `collectUnmatchedAllowedSlots`
6. `runConstrainedHandSecondPass`
7. `advanceUnmatchedHandSlots`
8. `cleanupRetiredOwnerHandSlots`
9. `resetExpiredHandSlots`
10. `eraseEmptyHandOwnerStates`
11. `publishAllowedHandSlots`
12. `cleanupRetiredBodyAnchors`

重点约束：

- first pass 继续按当前 body output map 顺序处理 owner，并共享 `usedDetections`。
- second pass 只能处理 allowed owner 的 initialized unmatched slot。
- second pass cost 必须继续要求 `HandBelongsToBody`。
- slot hit helper 必须区分首次初始化和已初始化 correction。
- miss 只推进一次；拆分后要防止“first pass 未命中”和“second pass 未命中”各推进一次。
- publish 只遍历 allowed owner 一次。当前两段 fallback 发布可收敛成单个 `publishHandSlotIfEligible`，但必须保持 key 等于 owner face id。

# 6 推荐调用流程

```text
DmsTrack::Update
  clearFrameOutputs
  updateFaceTracks
    collect -> predict -> assign -> apply hits -> bootstrap -> miss/erase
  selectDriverFace
  applyDriverRole
  publishFaceTracks
  updateBodyTracks
    collect -> owner order -> tracking match -> acquisition -> apply -> retire -> publish
  updateHandTracks
    collect -> owner context -> predict
    -> owner-local pass -> constrained second pass
    -> miss/expire -> handoff cleanup -> publish -> retired-anchor cleanup
```

# 7 风险分级

## 7.1 低风险等价重构

- 检测按 class 收集 helper。
- 几何/loss/gate 纯函数整理。
- `FaceMatchScoreBreakdown`、`BodyMatchDecision`、`HandSlotRef` 等局部结果结构体。
- 将日志跟随对应阶段 helper 移动，日志内容和触发条件不变。
- 将 hit/miss/expired 判断封装为窄函数。
- 将重复 left/right 发布收敛为同一个 slot publish helper。
- 新增 private/internal 协作对象承载 assignment、lifecycle、publish、config 等内部机制，但不改变 public API。
- 将大函数按现有语句顺序提取为 private member helper，不改变容器类型和循环顺序。

## 7.2 中风险边界重组，需要回归测试保护

- 抽取统一 dummy assignment helper 或 `TrackAssignmentSolver`。
- 拆分 sanitize 与 publish 的副作用。
- 合并 Hand first/second pass 的 slot hit 更新。
- 将 `usedDetections` / `matchedSlots` 改成结果结构统一返回。
- 改变 helper 参数传递方式后，可能无意改变 `TrackInfo&` 的修改时机。

## 7.3 高风险行为或契约变更

- Body 顺序贪心改为全局 Hungarian。
- Hand first pass 与 second pass 合并为单次全局匹配。
- 改变 map 遍历顺序、owner 优先级或 driver-first 顺序。
- 改变矩阵维度、dummy block、forbidden edge 代价或 `< dummyLoss` 比较。
- 改变 hit/miss 推进次数、删除时机或 sanitize drop 的 miss 行为。
- 修改 `TrackInfo`、四类 output map、track id 分配或 owner key。
- 将 body/hand 拆成独立 public tracker 并复制状态，容易破坏 face-owned identity。
- 把 private/internal 协作对象升级为调用方必须编排的 public API。

# 8 分阶段实施顺序

## 8.1 Phase 0 行为基线

- 固化关键场景的输入检测序列与每帧四类 map 摘要。
- 记录 track id、box、hit/miss、stable type、owner key。
- 暂不修改算法。

## 8.2 Phase 1 纯函数与只读上下文

- 提取 detection collection、score/gate、owner context 查询。
- 增加 `BodyMatchDecision`、`HandSlotRef`。
- 不调整 update 内语句顺序。

## 8.3 Phase 2 状态更新 helper 与内部协作对象

- 分别提取 Face/Body/Hand 的 prediction、hit update、miss/expire。
- 保持三个实例类型的专用 detection update helper，不做泛型 tracker。
- 可先引入 `TrackLifecycleOps`、`TrackOutputSanitizer` 等无状态或低状态 private/internal 单元。

## 8.4 Phase 3 Face 与 Body 编排瘦身

- 先拆 Face，再拆 Body。
- 每次只移动一个阶段，并用基线比较输出。
- Body 保留 driver-first 顺序贪心策略。

## 8.5 Phase 4 Hand 分阶段拆分

- 先提取 owner、prediction、cleanup、publish。
- 再提取 first pass。
- 最后提取 second pass 和统一 assignment 基础设施。
- 每一步检查 miss 只推进一次、owner gate 未放宽、legacy key 未变化。

## 8.6 Phase 5 匹配基础设施统一

- 优先统一 Face 与 Hand second pass 的 dummy assignment。
- 可引入 private/internal `TrackAssignmentSolver`，但返回结果必须保持只描述匹配，不修改轨迹状态。
- 评估 Hand first pass 是否适合复用同一基础设施；没有充分测试时保留专用实现。

## 8.7 Phase 6 可选文件拆分

只有 `track.cpp` 在函数提取后仍明显过长时，再把匿名 namespace 的无状态算法移动到内部实现文件，例如：

- `track_geometry.cpp`
- `track_assignment.cpp`

不新增 public API，不暴露新的 public tracker 类，不拆散 `DmsTrack` 的状态所有权。private/internal 协作对象可以作为实现组织手段保留在模块内部。

# 9 最小测试范围

本轮未运行测试。后续实施前建议至少补以下 host-side 单元测试：

- assignment：空集合、1:1、矩形集合、forbidden edge、dummy reject、等价 cost。
- lifecycle：hit 饱和、miss 衰减、过期边界、每帧只推进一次。
- sanitize：合法框、clamp、非法框、完全越界框，以及当前 drop 后 miss 语义。
- Face gate：small face、driver/non-driver distance gate、size continuity。
- Body decision：existing tracking 优先、tracking reject 后 acquisition、driver owner 优先占用。
- Hand：left/right anchor、owner ROI、first pass、second pass、slot 初始化/命中/miss/expire、retired owner cleanup。
- frame regression：相同检测序列下四类 output map 的 key、box、type、hit/miss 与重构前一致。

若只做纯函数提取和等价移动，最小验证为相关单元测试加本地编译。若触及 assignment、生命周期次数、owner gate 或 publish 副作用，则需要视频回放；若输出行为变化，再单独设计板端验证。
