# 2 模块边界判断

`DmsTrack` 对调用方已经是深模块：public surface 只有 `Init()` 与 `Update(...)`，调用方不需要编排 face、body、hand 的顺序，也不需要理解内部 hit/miss、Hungarian、owner key、legacy map 投影或车型分流。

当前问题不在 public API，而在内部组织：

- `Update` 作为帧级 pipeline 已基本可读。
- `updateFaceTracks`、`updateBodyTracks`、`updateHandTracks` 是合理的 phase-level private 方法。
- 具体 phase 内部存在 solver、状态推进、输出投影、cleanup 和局部策略混杂，尤其 hand 阶段明显。
- 过去三笔 hand lambda 提交降低了局部重复，但没有解决不同抽象层级堆叠在同一函数的问题。

结论：

- 不建议改变 public API。
- 不建议把局部 hand 子步骤继续提升为大量 private header step helper。
- 后续优化应以 Face/Body/Hand 整体内部架构一致性为目标，而不是只围绕 `updateHandTracks` 局部提取。

# 3 Public API 深浅分析

| API | 高层意图 | 暴露的内部步骤 | 调用顺序约束 | 判断 |
|---|---|---|---|---|
| `Init()` | 初始化配置和历史状态 | 不暴露 | 必须先于 `Update` | 深接口，保持 |
| `Update(img, curResult)` | 按单帧检测结果更新所有 tracking 输出 | 不暴露 face/body/hand 内部阶段 | 每帧调用 | 深接口，保持 |

复杂性没有转移给调用方；内部可读性优化不应扩大 public surface。

# 4 Private Header Surface 审计

| private 类型或方法 | 长期状态/跨 phase 契约/phase-level 方法 | 是否只是单帧或单链临时细节 | 建议位置 | 判断 |
|---|---|---|---|---|
| `TrackParameters` | 长期配置状态 | 否 | header private | 保留 |
| `HandSideState` / `HandTrackState` | 长期 hand 状态 | 否 | header private | 保留 |
| `m_faceTracks` / `m_bodyTracks` / `m_handTracks` | 长期状态 owner | 否 | header private | 保留 |
| `updateFaceTracks` | Face phase | 否 | header private | 保留 |
| `selectDriverFace` | Driver face selection phase | 否 | header private | 保留 |
| `updateBodyTracks` | Body evidence phase，返回本帧 driver body snapshot | 否 | header private | 保留 |
| `updateHandTracks` | Hand evidence phase | 否 | header private | 保留 |
| collect owner / predict slot / publish slot / advance unmatched miss | 单 phase 内部机制 | 是 | 函数局部或 `.cpp` internal | 不提升到 header |

private surface 不应暴露完整执行脚本。当前 header 保留 phase-level 方法是合理的；后续如新增 helper，必须证明它表达完整 phase 而不是机械步骤。

# 5 主导可读性问题

1. Face/Body/Hand 三个 phase 的内部组织风格不一致：Face/Body 更像“一个 phase 内部完整实现”，Hand 被局部 lambda 进一步切碎但仍在一个函数中堆叠多个层级。
2. 局部 lambda 改善了重复代码，却没有让主流程显式表达 phase：读者仍需在 `updateHandTracks` 内同时理解 owner 策略、candidate、Hungarian、hit/miss、cleanup、publish。
3. 过去方案把“避免 private API surface”错误地执行成“尽量压成局部 lambda”，忽略了主流程可读性、依赖显式性和 phase 边界。

# 6 复杂性来源

| 类别 | 当前表现 | 必要领域复杂性 | 可降低的结构复杂性 |
|---|---|---|---|
| 业务规则与编排 | face identity -> body evidence -> hand evidence | Face-owned identity、driver-bound evidence 必要 | 主流程应显式表达阶段，不混入 solver 细节 |
| 数据转换与计算 | detection 过滤、几何 loss、Hungarian 矩阵 | 必要 | pure helper 和局部机制可隔离 |
| 策略变化 | 2m/5m profile、driver selection、body/hand owner 收缩 | 必要 | profile 与 owner 策略应在 phase 边界清晰体现 |
| 状态与生命周期 | hit/miss、retire、hand slot reset | 必要 | lifecycle 推进应集中，避免 publish/cleanup 交错 |
| 兼容与横切关注点 | legacy output map、sanitize、stage tag | 必要 | output projection 应与 state update 分层 |

主要复杂性镜头：状态密集 tracking pipeline。

# 7 核心约束与模型

- state/identity owner：Face track 是身份 owner；body/hand 是 owner face 下的 evidence/cache。
- 生命周期与状态流：
  - Face 负责身份延续和 driver selection 输入。
  - Body 只为 selected driver face 提供本帧可发布 evidence。
  - Hand 只消费本帧 driver body evidence，不反读 legacy body output map。
- 关键不变量：
  - `left/right hand map key == owner face id`。
  - 非 driver owner 不发布 body/hand。
  - publish 不应改变匹配候选域或 owner migration。
  - 2m profile 不输出陈旧 body/hand。

# 8 应保留在主流程中的逻辑

推荐主流程仍保留在 `DmsTrack::Update`：

```text
Update
  -> clear legacy output maps
  -> updateFaceTracks
  -> selectDriverFace
  -> publish current face output
  -> updateBodyTracks or clear body state by profile
  -> updateHandTracks or clear hand state by profile
```

Face/Body/Hand phase 内部后续应按下列结构评估，而不是直接继续拆小 lambda：

```text
updateFaceTracks
  -> collect face detections
  -> predict existing face tracks
  -> solve/apply detection-to-face assignment
  -> bootstrap unmatched detections
  -> advance/erase unmatched tracks

updateBodyTracks
  -> collect body detections and eligible driver owner
  -> track/acquire driver-bound body evidence
  -> advance/retire non-current body cache
  -> publish finalized driver body evidence snapshot

updateHandTracks
  -> collect hand detections and allowed driver hand owners
  -> predict existing hand slots
  -> update driver-owned left/right hand slots
  -> recover/miss unmatched slots under driver body constraints
  -> cleanup orphan/expired hand state
  -> publish driver-bound left/right hand output
```

Phase-level 与 step-level 判断：

| 候选函数 | 完整领域动作或独立契约 | 是否只能与相邻步骤固定组合 | 独立复用/测试/失败边界 | 建议 |
|---|---|---|---|---|
| `updateFaceTracks` | 是 | 否 | phase 行为可独立审查 | phase-level 保留 |
| `updateBodyTracks` | 是 | 否 | phase 行为可独立审查 | phase-level 保留 |
| `updateHandTracks` | 是 | 否 | phase 行为可独立审查 | phase-level 保留 |
| `publishHandSlot` | 否，局部 publish 条件 | 是 | 无独立失败边界 | 局部机制，可保留但不是架构目标 |
| `advanceUnmatchedSlotMiss` | 否，局部 miss 定位 | 是 | 无独立失败边界 | 局部机制，可保留但不是架构目标 |
| `collectAllowedHandOwners` / `predictHandSlot` / `collectBodyConstrainedHandCandidates` | 否，局部准备机制 | 是 | 无独立失败边界 | 局部机制，可保留但不是架构目标 |

# 9 新增抽象必要性审计

现有表示足够：

- `TrackInfo`、`HandTrackState`、`HandSideState` 足以表达长期状态。
- `std::map<track_id, TrackInfo>` 足以表达本帧 driver body evidence snapshot。
- `std::set<track_id>`、`std::set<int>`、`std::vector<DetectBox>` 足以表达局部候选和占用状态。

建议保留或新增的深抽象：

```text
无新增类型建议 / 无需交接清单
```

建议降级或避免提升的抽象：

| 抽象 | 当前可见性 | 建议位置 | 降级理由 |
|---|---|---|---|
| hand owner/candidate/publish/miss 小 lambda | 函数局部 | 函数局部或合并进更清晰 block | 不承载新不变量，不应提升为 private header |
| `FrameHandView` / `HandPublishPayload` / `LifecycleContext` | 未新增 | 不新增 | 只会搬运局部事实，不能隐藏复杂性 |

不建议新增抽象的场景：

| 场景 | 原拟新增类型 | 建议复用的表示 | 原因 |
|---|---|---|---|
| hand publish 输出投影 | `HandPublishPayload` | `HandSideState` + output map + owner id | 不增加不变量 |
| hand owner candidate | `HandOwnerView` | `driverBodyEvidence` + `std::set<track_id>` | 只是已有 map 的筛选 |
| lifecycle 批处理上下文 | `LifecycleContext` | member state +局部集合 | 容易混合 solver index、状态指针和输出约束 |

# 13 结论

已由代码证实的事实：

- public `Init/Update` 未暴露内部 phase。
- Face/Body/Hand 当前均在 `DmsTrack` 内部维护状态。
- 三笔 hand lambda 提交行为等价验证通过，但没有形成整体 phase 边界。

设计判断：

- 当前优化目标应从 `updateHandTracks` 局部改为 DmsTrack 整体内部架构可读性。
- 低可见性不等于更好抽象；局部 lambda 不应承载完整 phase。
- 三笔 hand lambda 提交应保留追溯并被本方案 supersede。

尚需验证的假设：

- 后续是否需要在 Face/Body/Hand 内新增 `.cpp` internal helper 或 private helper，必须由具体 diff 和 review 决定。
- 运行效果仍未通过 replay、单元测试或板端验证闭合。
