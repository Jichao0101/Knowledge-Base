# 车型配置增量读取与双路径车型来源

## 摘要

本记录沉淀 DMS 项目中 `track`、`fatigue`、`face_id` 三个后处理模块的车型配置读取方案。当前决策是：模块自行解析车型并读取自身配置文件，配置按 `DEFAULT + 具体车型节点` 增量覆盖；车型节点不存在时返回失败，不静默回退。

- 覆盖模块：

- 覆盖配置：

  - `etc/face_id_params.json`
  - 回灌路线的 `etc/fillback.json`

## 当前决策

1. `FuseAlgorithm` 不再负责把车型或车型配置喂给下游后处理模块。
2. `BaseAlgorithm::SetVehicleModel()` 和 `VehicleState` 下传路径不再作为三类后处理配置来源。
3. `track`、`fatigue`、`face_id` 在各自 `Init()` 中解析车型，再读取各自 JSON。
4. 配置合并方式为先应用 `DEFAULT`，再应用具体车型节点，具体车型节点可以为空对象，表示完全继承 `DEFAULT`。
5. 具体车型节点缺失时必须报错返回，不能 fallback 到 `DEFAULT`。
6. 其他非目标模块暂时保留自身 fallback/default 行为，不纳入本次强约束。

## 双路径车型来源

公共车型解析器负责统一解析车型字符串：

- 动态库 / 外部 interface 路线：通过 `VehicleCgf` 读取车配中的 `car_type`。
- 可执行程序 / fillback 回灌路线：通过 `etc/fillback.json` 中手动配置的 `car_type`。

车型映射：

- `1` -> `C1UL-2`
- `2` -> `NCLB`
- `3` -> `E2YB`
- `4` -> `E2LB-2`
- `5` -> `358-2`
- `6` -> `L232`
- `7` -> `NBUB`

非法或缺失 `car_type` 必须初始化失败。

## 相机类型约束

当前车型相机类型规则：

- `C1UL-2`、`358-2`、`L232` 为 `2m`
- `DEFAULT`、`NCLB`、`E2YB`、`E2LB-2`、`NBUB` 为 `5m`

`track_params.json` 中 2m 车型需要显式写入来自 `track_params_2m.json`、且不同于 5m 默认值的 `presets`，避免依赖单独的 2m 配置文件完成主路径配置选择。
