# 1 从功能可行性到项目可交付性的通用分析框架 v0

## 1.1 候选状态

本文是一套重新设计的通用项目分析框架候选，用于把“功能是否可实现”的技术分析，扩展为“项目能否在明确边界和约束下形成可验收交付”的系统分析。

本文不来源于对某个单一项目文档结构的复述，也不包含特定项目的功能、工时、里程碑、风险或结论。当前状态为 `pending_review`，只能作为分析脚手架使用，不应被视为已经验证的最佳实践。

## 1.2 核心判断

功能方案和项目分析面对的是不同问题：

- 功能方案主要回答：目标功能如何实现，技术路线是否可行。
- 项目分析主要回答：在什么目标、范围、依赖、资源、验收和治理条件下，整体交付承诺是否可信。

项目分析的基本单位不是功能列表，而是**可追溯、可估算、可分配、可验收的工作包**。完整的项目分析应形成以下闭环：

```text
目标与成功定义
  → 承诺边界与假设基线
  → 交付物与工作包
  → 验收证据
  → 依赖与关键路径
  → 角色容量与动态排期
  → 风险、决策和变更治理
  → 执行反馈、重新预测与重新基线
```

## 1.3 框架目标

该框架用于帮助项目分析者完成三次转换：

1. 从“需求存在”转换为“项目承诺明确”。
2. 从“功能能够实现”转换为“端到端交付系统能够闭环”。
3. 从“一次性排期”转换为“能够随证据持续更新的交付预测”。

最终产物应使参与者能够判断：

- 当前承诺是什么，明确不承诺什么。
- 达成交付需要完成哪些工作并获得哪些外部条件。
- 谁在什么时候提供什么产物或作出什么决策。
- 使用什么证据判断阶段完成和最终准出。
- 哪些变化会影响承诺，何时必须重新基线化。

# 2 八个分析模块

## 2.1 目标与成功定义

### 2.1.1 需要回答

- 项目要解决什么问题，预期改变什么结果？
- 谁是结果的使用者、验收者和最终决策者？
- 哪些结果属于业务成功，哪些属于工程完成？
- 时间、成本、质量、合规和体验之间如何取舍？

### 2.1.2 最小输出

- 项目目标与非目标。
- 关键干系人与决策权。
- 可观测的成功指标。
- 不可突破的时间、成本、质量或合规约束。

### 2.1.3 完成门槛

目标能够被验证，主要干系人对成功含义和取舍原则没有关键歧义。

## 2.2 承诺边界与假设基线

### 2.2.1 需要回答

- 本阶段明确承诺哪些结果？
- 哪些内容只是候选、储备、预研或明确不做？
- 承诺依赖哪些尚未验证的假设？
- 哪些范围变化必须触发重新评估？

### 2.2.2 最小输出

- `Committed / Candidate / Deferred / Out of Scope` 范围表。
- 版本、对象、环境和场景边界。
- 假设清单及其 Owner、验证方式和失效日期。
- 范围变更的影响分析与批准规则。

### 2.2.3 完成门槛

所有进入计划和资源基线的内容都具有明确承诺状态；未决事项不会被隐式计入交付承诺。

## 2.3 交付系统与工作包拆解

### 2.3.1 需要回答

- 用户或系统最终获得哪些可验证交付物？
- 每个交付物由哪些技术和非技术能力共同构成？
- 哪些能力可以复用，哪些需要适配、新研或外部提供？
- 如何拆到可以估算、分配和跟踪的工作包？

### 2.3.2 最小输出

- 交付物分解结构。
- 功能、系统、数据、平台、集成、测试和发布等工作包。
- 工作包的输入、输出、Owner、完成定义和依赖。
- 共享能力与项目特有适配的边界。

### 2.3.3 完成门槛

不存在只有功能名称、无法判断完成证据或责任边界的计划项。

## 2.4 验证与准出体系

### 2.4.1 需要回答

- 每个交付物如何证明完成？
- 需要哪些测试、评审、测量、演示或发布证据？
- 阶段性验证与最终验收如何衔接？
- 哪些场景必须通过，哪些缺陷会阻断准出？

### 2.4.2 最小输出

- 需求或目标到验收证据的追溯关系。
- 场景矩阵、指标定义和测试方法。
- 各阶段入口与出口条件。
- 缺陷分级、豁免、回归和发布规则。

### 2.4.3 完成门槛

任何“已完成”判断都能指向可复查的证据；里程碑不以任务完成百分比替代准出条件。

## 2.5 依赖与关键路径

### 2.5.1 需要回答

- 哪些工作存在强前后依赖，哪些可以并行？
- 哪些外部输入、平台、接口、数据、设备或决策控制项目节奏？
- 每项依赖最晚何时必须满足？
- 依赖延迟会影响哪些下游交付物和节点？

### 2.5.2 最小输出

- 依赖网络和关键路径。
- 外部依赖的 Owner、所需产物和最晚满足时间。
- 依赖未满足时的替代方案、降级方案或停止条件。
- 对下游范围、成本、质量和时间的影响关系。

### 2.5.3 完成门槛

项目日期能够由工作量、依赖顺序和资源约束推导，而不是只由目标日期倒填。

## 2.6 角色容量与动态排期

### 2.6.1 需要回答

- 各工作包需要哪些角色和能力，而不仅是多少人？
- 不同阶段的投入峰值、并行冲突和切换成本是什么？
- 估算中包含哪些复用、不确定性和返工假设？
- 当前预测日期与目标日期之间有多大余量？

### 2.6.2 最小输出

- 工作包级区间估算及估算依据。
- 按角色和时间展开的容量装载。
- 目标日期、基线日期和当前预测日期。
- 关键路径缓冲、风险储备和置信度。

### 2.6.3 完成门槛

计划能够解释“为什么需要这些角色、为什么是这个日期、变化后如何重新计算”，而不是只给出总工时或平均人数。

## 2.7 风险、决策与变更治理

### 2.7.1 需要回答

- 哪些不确定性可能影响目标或承诺？
- 哪些问题已经发生，哪些只是风险或假设？
- 谁必须在什么日期前作出什么决策？
- 什么变化需要局部调整，什么变化必须重新基线？

### 2.7.2 最小输出

- 风险、假设、问题、依赖和决策记录。
- 每项记录的 Owner、影响、应对措施、触发条件和截止时间。
- 决策权和升级路径。
- 范围、指标、资源、依赖或节点变化的变更控制规则。

### 2.7.3 完成门槛

高影响未决事项都有责任人和最晚决策时间；关键变化不会通过静默改表进入项目承诺。

## 2.8 执行反馈与重新基线

### 2.8.1 需要回答

- 哪些执行证据用于更新预测？
- 如何识别进度完成但交付风险未下降的情况？
- 预测偏差达到什么阈值需要调整范围、资源或日期？
- 如何保留基线变化及其原因？

### 2.8.2 最小输出

- 周期性的完成证据、质量趋势和依赖状态。
- 当前预测与既有基线的差异。
- 重新预测和重新基线触发条件。
- 基线版本、变更原因、批准记录和影响说明。

### 2.8.3 完成门槛

项目状态由交付证据和剩余风险驱动；计划能够随着事实变化而更新，同时保留历史可追溯性。

# 3 跨模块追溯主线

八个模块不应成为彼此独立的文档。项目需要维护一条最小追溯主线：

```text
项目目标
→ 需求或结果
→ 承诺版本与范围
→ 交付物
→ 工作包
→ 依赖
→ 验收证据
→ 里程碑
→ Owner
→ 当前状态与预测
```

追溯关系的作用不是增加文档量，而是支持三类判断：

1. 需求变化时，能够定位受影响的工作、测试、资源和节点。
2. 节点风险出现时，能够回溯影响的交付物和项目目标。
3. 声明完成时，能够找到对应的验收证据和责任记录。

# 4 通用分析流程

## 4.1 建立项目画像

确认项目目标、交付窗口、干系人、决策权、硬约束和主要不确定性。若目标和成功定义尚未对齐，不进入详细排期。

## 4.2 建立承诺基线

区分已承诺、候选、延期和范围外内容，显式记录所有影响承诺可信度的假设。只有已承诺且边界明确的内容进入主计划。

## 4.3 构造交付模型

从最终交付物反向拆解工作包、验证证据和依赖，再识别共享能力、并行工作及关键路径。拆解深度以能够估算、分配和验收为准。

## 4.4 形成资源与进度模型

使用工作包区间估算、角色容量和依赖网络计算计划，区分目标日期、基线日期和当前预测日期，并显式记录置信度和缓冲。

## 4.5 建立治理闭环

为风险、假设、问题、依赖和决策指定 Owner、触发条件和最晚处理时间；根据执行证据持续更新预测，在达到阈值时重新基线。

# 5 最小项目分析检查表

在项目计划进入评审前，至少回答以下问题：

1. 项目成功具体意味着什么，由谁验收？
2. 当前明确承诺、候选、延期和范围外内容分别是什么？
3. 主要假设是什么，谁在何时用什么证据验证？
4. 最终交付物能否拆成可估算、可分配、可验收的工作包？
5. 每个关键里程碑的产物、证据、Owner和出口条件是什么？
6. 关键路径和外部依赖是什么，最晚满足时间是什么？
7. 资源计划是否体现角色组合、投入峰值、并行冲突和返工储备？
8. 当前预测日期与目标日期有何差异，置信度是多少？
9. 重大风险和未决决策是否有 Owner、触发条件和截止时间？
10. 哪些变化会触发影响分析或重新基线，历史如何保留？

# 6 使用原则

1. **承诺优先于清单**：需求被提出不等于已经进入项目承诺。
2. **交付物优先于活动**：用可验证产物描述进展，不用“开发中”描述状态。
3. **证据优先于百分比**：完成度必须能够映射到阶段出口证据。
4. **依赖决定节奏**：日期应由工作量、依赖和容量共同推导。
5. **角色容量优先于平均人数**：资源计划必须反映能力结构和阶段峰值。
6. **预测与目标分离**：目标日期表达期望，当前预测表达基于现有证据的判断。
7. **假设必须可失效**：假设需要 Owner、验证方式和最晚验证时间。
8. **计划随证据更新**：允许重新预测和重新基线，但必须记录原因和影响。

# 7 适用范围与边界

## 7.1 适用范围

- 存在多个专业角色、团队或外部协作方的研发项目。
- 具有明确交付窗口和阶段验收要求的软件、算法、平台、数据或系统集成项目。
- 范围、资源、依赖或技术成熟度存在不确定性的项目早期规划和持续控制。
- 需要从功能方案评审升级为整体可交付性评审的场景。

## 7.2 不适用或需要裁剪的场景

- 单人、短周期、低依赖且容易回滚的小任务，可只保留目标、交付物和完成定义。
- 纯探索性研究在尚无交付承诺时，不宜强制建立完整排期，但仍可维护假设、证据和停止条件。
- 本框架不替代具体领域的架构设计、测试标准、安全规范、合规流程或组织级项目治理制度。
- 框架只能暴露承诺所需条件，不能替项目决策者自动作出范围、资源和风险接受决策。
- 早期高度不确定的内容应使用区间、假设和置信度，不应被包装成精确承诺。

# 8 后续验证与提升条件

考虑提升为正式知识前，至少需要：

1. 在三个以上不同类型的真实项目中应用，建议覆盖算法或模型、软件或平台、跨系统集成等不同形态。
2. 验证八个模块能否支持范围决策、依赖识别、资源估算、阶段准出和重新基线。
3. 记录哪些模块被裁剪、哪些问题仍无法覆盖，并据此补充不适用边界。
4. 形成至少一个经过实践验证的轻量模板，而不只是概念框架。
5. 对框架使用成本进行评估，避免为低复杂度任务制造不必要的文档负担。
6. 完成人工评审，确认其与现有项目管理、系统工程和质量流程的关系。

在上述条件满足前，本文只作为 `03_Inbox` 中的通用方法候选，不进入正式知识区。
