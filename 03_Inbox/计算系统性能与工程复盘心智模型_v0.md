# 计算系统性能与工程复盘心智模型 v0

## 1 摘要

这是一个学习中的候选框架，用于在复盘工程问题时追问：问题主要受哪类计算系统约束主导，以及这些约束如何随规模、数据流和资源调度变化。

当前阶段只作为 `draft / knowledge candidate / learning scaffold` 保留，不作为正式知识引用。

## 2 核心判断

理论上，许多值得复盘的工程问题都可以映射到以下维度之一，或多个维度的组合：

- 计算约束
- 内存约束
- 数据流约束
- 数值约束
- 调度约束
- 规模化约束

这个框架的目标不是提前抽象出完整理论，而是在遇到具体问题时提供一组复盘入口。

## 3 维度草稿

### 3.1 Computation

- Complexity
- Parallelism

- Utilization

### 3.2 Memory

### 3.3 Dataflow

- Copy

### 3.4 Numerical

- Precision
- Dynamic range
- Quantization
- Overflow / Underflow
- Error propagation

### 3.5 Scheduling

- Concurrency
- Pipeline
- Critical path
- Resource contention

### 3.6 Scaling

- What grows with N?
- O(N)
- O(N²)
- Communication scaling
- Memory scaling

## 4 使用方式草稿

遇到一个值得复盘的工程问题时，先不要急着归类为“代码问题”或“架构问题”，而是追问：

1. 什么随 N 增长？
2. 当前瓶颈更接近计算、内存、通信、同步还是调度？
3. 数据在哪里产生、复制、等待、消费？
4. 数值表示是否足以支撑目标精度和动态范围？
5. 关键路径在哪里，哪些资源发生争用？
6. 这个问题能否通过一个真实案例挂到上述维度下？

## 6 边界与风险

- 当前框架仍偏概念索引，缺少足够技术深度，不能替代具体 profiling、测试、数值分析或系统设计证据。
- 过早展开可能导致只收集高层词汇，而没有形成可执行的判断能力。
- 不同领域的主导约束不同；例如算法复杂度、GPU kernel、分布式训练、数据库查询和端侧推理不能直接使用同一套优先级。
- 只有在经历多个真实案例复盘后，才能评估是否抽象成正式知识。

## 7 提升条件

考虑提升到 `01_Knowledge` 前，至少需要：

- 3-5 个真实工程问题复盘案例。
- 每个案例能明确对应一个或多个主导维度。
- 形成稳定的复盘流程，而不只是概念列表。
- 补充适用范围、不适用范围、反例和验证方法。
- 完成人工审核。
